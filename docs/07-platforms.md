# 7. Platforms and rendering

The two first targets are **desktop** (macOS, Windows, Linux) and **Android**, with the goal of looking and behaving as Kotlin Compose does on each. Compose draws with Skia on both: through Skiko on desktop, and through the system renderer (HWUI, built on Skia) on Android. So this design uses Skia too, in the way each platform makes possible:

| | Desktop | Android |
|---|---|---|
| Drawing | Skia through `skia-safe` (prebuilt binaries), on the GPU | the system `android.graphics.Canvas`, through a display-list replayer: no Skia shipped |
| Text | Skia's paragraph module (SkParagraph: HarfBuzz shaping, ICU line breaking and bidi) | Android's own text stack (`TextPaint`, `StaticLayout`) through JNI |
| Host | a winit window (`run_app`) | a custom `View`, usable inside a Kotlin Compose UI through `AndroidView` |
| Matches | Compose Desktop's drawing and text | Android Compose's drawing and text, pixel for pixel, since both use the system renderer |

## The rendering interface

`compose-ui` never draws directly. Its draw pass records a **display list**, and a `Renderer` backend replays it.

- **Display-list operations** are a subset of the `Canvas` API that both Skia and Android's `Canvas` support directly:
  - `save` and `restore`;
  - clips: rectangle, rounded rectangle, path;
  - transforms: translate, scale, rotate, matrix;
  - shapes: `draw_rect`, `draw_round_rect`, `draw_path`, `draw_image`;
  - text: `draw_paragraph`;
  - a `Paint` with colour, stroke, shader (gradients) and blend mode.

  Keeping to that subset makes both backends a straightforward translation.
- **Paragraphs** are created and measured by the `TextMeasurer` backend, and drawn by handle. The same platform object that measured a text draws it, so measurement and drawing can never disagree.
- **Backends:**
  - `SkiaRenderer` on desktop, with a GPU surface for windows and a CPU raster surface for tests and screenshots;
  - `AndroidCanvasRenderer` on Android;
  - later, if wanted, a native Skia renderer on Android (see below).

## Text

```rust
pub trait TextMeasurer {
    fn layout(&mut self, text: &AnnotatedString, style: &TextStyle, constraints: Constraints) -> ParagraphHandle;
    fn metrics(&self, paragraph: ParagraphHandle) -> ParagraphMetrics; // size, baselines, line metrics
    fn hit_test(&self, paragraph: ParagraphHandle, position: Offset) -> TextPosition; // for selection and the cursor
    fn max_intrinsic_width(&self, paragraph: ParagraphHandle) -> Option<f32>; // the text's own width
    fn relayout(&mut self, paragraph: ParagraphHandle, constraints: Constraints) -> Option<ParagraphHandle>; // the same text at new constraints
    fn restyle(&mut self, paragraph: ParagraphHandle, style: &TextStyle) -> Option<ParagraphHandle>; // the same layout in a new paint
    fn release(&mut self, paragraph: ParagraphHandle);
}
```

- **Desktop:** SkParagraph with the system font manager, as Compose Desktop uses through Skiko; tests measure with a fixed-advance measurer by default, so headless measurements are identical on every machine (no fonts are bundled: D94).
- **Android:** a Kotlin-side cache of layouts keyed by handle, chosen as Compose's `TextLayout` chooses (D330): a `BoringLayout` for a single left-to-right line that fits its width (API 33+; its metrics give the text's width, so no second measure), else a `StaticLayout`. Rust asks for a layout once per changed text, through one JNI call that returns the metrics; new constraints for the same text are one smaller call (`relayout`: the widths), which Kotlin lays out from what it kept of the text (its spans, paint, boring metrics and own width, as Compose's `ParagraphIntrinsics`: D550). Drawing calls `layout.draw(canvas)` in the replayer, through a canvas whose clip bounds reach down without end, as Compose's `TextAndroidCanvas` (D646): `Layout.draw` draws only the lines within the clip bounds, and a render node's recording reports the node's size when it was recorded, which a layer can outgrow while its record stays the same bytes (D323). This is the text stack Android Compose itself draws with, so line breaks, hyphenation, fallback fonts and emoji match exactly. Whether lines were cut (`did_exceed_max_lines`) comes back with the metrics: more lines than the max, or the last one ellipsized, as Compose's `TextLayout`.
- `BasicText` keeps its `ParagraphHandle` on the node, so recomposing with the same text lays out nothing, and a new color or decoration only draws the kept layout in the new paint (`restyle`, D555); new constraints lay it out again as Compose's `newLayoutWillBeDifferent` decides (any new width bound; a new height only when it clips the paragraph: D550, [06](06-ui.md) "Text"), and with D551's optimization (on by default, in the recommended set: D610) only when the width it's laid out at changes.

## Desktop (`compose-desktop`)

- **One thread.** `application` creates the winit event loop on the main thread, owns the compositions, and runs everything there: no frame mailbox or input channel.
- **Windows** are Compose Desktop's: `application(App)`, where `#[composable] fn App()` holds `Window!(on_close_request = …, title = …, state = remember_window_state(size), { … })`s (a composable function, so the call macros memoize the windows' content lambdas). The application's content is a composition of its own whose nodes are windows (`WindowApplier`); each `Window` in it is opened, its content composed in the window's own `UiHost` and reading the application's state like any content, and closed (its composition disposed) when it leaves the composition. `visible = false` hides it, keeping its composition. The application recomposes before any window's frame, so a window never shows values from both sides of a change. The close button, Cmd+W and Ctrl+W call the window's `on_close_request`, which removes it or not. Cmd+Q (the macOS app menu's Quit) ends the application, as Compose Desktop's default quit. `exit_application()` ends it, as it ends once no window is left. A `WindowState` holds the window's size: the window follows it (applied at the loop's next turn), and it follows the user's resizing. Animations step on one window's frames; the others draw when what they show changes. `run_app(options, content)` is one window whose close request exits.
- **Skia surfaces** on the GPU: Metal on macOS, Vulkan or OpenGL on Linux, Direct3D on Windows. The binaries are prebuilt by `skia-safe`, so building the app doesn't compile Skia. On Linux they link the system's FreeType and Fontconfig, so building needs their development packages and `pkg-config`; compose-skia's build script warns, with the install command, when pkg-config can't find them. This is the same size trade-off Compose Desktop makes by shipping Skiko.
- **The frame loop**, driven by winit's `about_to_wait` and `RedrawRequested`:
  1. **Events:** pointer, key and text events are dispatched; handlers run and write state, which invalidates scopes and schedules a frame.
  2. **Recompose** invalid scopes.
  3. **Layout and draw** from dirty nodes, recording the display list.
  4. **Render and present** through Skia, only when something was drawn (or the window resized): the display list is rendered in place on Skia's CPU raster surface and its pixels copied straight into the window's buffer (softbuffer), so a warm frame allocates nothing.
  5. **Prefetch** while waiting (`about_to_wait`), when no frame has work: `UiHost::prefetch` until the next frame is due (the last one plus a refresh interval; a whole interval when nothing animates), so lazy lists that scrolled compose and measure their next items; work left wakes the loop at the deadline for another try.

  The loop sleeps (`ControlFlow::Wait`) until there's a reason to work: an idle window costs 0% CPU. Tasks ([04](04-runtime.md)) wake it through an event-loop proxy from any thread; a pending `delay` makes it wake at its end (`WaitUntil`); and frames only animations wait for come one display refresh interval apart (the monitor's rate, 60 Hz otherwise), since the CPU raster surface has no vsync.
- **HiDPI.** Layout is in logical pixels (`Dp`), and rendering happens at the window's scale factor.
- **The platform's values.** `LOCAL_CONFIGURATION` is the window's size in dp and density, and the system's light or dark appearance as winit reports it (`ThemeChanged` updates it); window insets are zero; Escape that nothing focused takes goes back (dialogs close on it); images decode with Skia's codecs.
- **Platform services and logging.** `LOCAL_CLIPBOARD_MANAGER` is the system clipboard (`arboard`; one in memory if it can't be opened); `LOCAL_URI_HANDLER` opens a link `PlatformUriHandler` checked (allowed schemes only, D283) with `open` (macOS), `xdg-open` (Linux, BSDs) or `rundll32 url.dll,FileProtocolHandler` (Windows, the URI given verbatim with `raw_arg`), never through a shell, its input and output closed; `LOCAL_HAPTIC_FEEDBACK` does nothing. `application` installs a stderr logger for the `log` crate (`COMPOSE_LOG` filters it by level and target) unless the app set one (D280, D281).
- **Input mapping:** pointer move, press, release and wheel (a cancelled touch cancels its gesture); keys with modifiers; committed text (sent whether or not the key was consumed: a focused text field consumes its typed keys, unless Ctrl or Cmd is held) and IME preedit (shown by the focused field; the candidate window is placed at its cursor with `set_ime_cursor_area`); focus, occlusion, resize, scale changes and close. Closing via the close button, Cmd+W or Cmd+Q (Ctrl+W elsewhere) ends `run_app`. A drag goes on outside the window. When a field commits a composition itself, the host resets the input method (`set_ime_allowed` off and on).
- **Accessibility** through AccessKit (`accesskit_winit`): the window is shown once the adapter is attached; while a screen reader is on, a frame that changed something rebuilds the AccessKit tree from the merged semantics tree (roles, labels from content descriptions or text, values, toggled, selected, disabled, bounds in physical pixels, the focus on the semantics node holding the focused node). A selected radio button is checked (`toggled`), a dialog is a modal `Dialog` node, and a slider a `Slider` with its numeric value, range and step. A screen reader's Click, Focus, Increment, Decrement and SetValue come back as semantics actions (`SemanticsAction::OnClick`, `RequestFocus`, `SetProgress`: a step, or a twentieth of a continuous range), performed by the node's semantics modifier nodes, as Compose's `SemanticsActions`. With no screen reader on, nothing is built.
- **Screenshots and statistics.** `COMPOSE_SCREENSHOT=path.png` renders the last frame through Skia's CPU raster backend. `COMPOSE_FRAME_STATS=1` reports events, recomposition, layout, draw and render times, input-to-present, and allocations per frame (with the `compose-test` counting allocator).

## Android (`compose-android`)

compose-rs draws on Android through the public `Canvas` and `RenderNode` APIs, which HWUI then renders with Skia on the GPU; it doesn't call `libhwui` or Skia directly. [13](13-android-drawing-paths.md) explains why, what a device's `libhwui.so` exposes, and the alternatives.

### Embedding

The main use is a compose-rs UI **inside an ordinary Kotlin Compose UI**:

```kotlin
@Composable
fun Screen() {
    Column {
        Text("Kotlin Compose above")
        AndroidView(factory = { context -> ComposeRsView(context, ComposeRs.entry("todo_app")) })
    }
}
```

`ComposeRsView` is a plain `View` that draws in `onDraw(canvas)`. So it's composited exactly as Compose content is: Compose's transforms, clipping, alpha, scrolling and z-order apply to it. A `ComposeRsActivity` wraps the same view for full-screen apps.

**Rejected:** a `SurfaceView` with its own renderer. It's composited as a separate layer that Compose's transforms, clipping and scrolling don't reach reliably, which makes it unfit for embedding.

### Drawing without shipping Skia

The NDK offers no C API for `Canvas`: drawing with the system's Skia means the `android.graphics` API. The system's own Skia library is private to the platform, and apps can't load it. To keep crossings into Java (JNI) to a constant number per frame:

1. **On a Choreographer frame callback**, Kotlin calls Rust **once**. Rust recomposes, lays out and draws, writing the display list into a direct `ByteBuffer` that Rust and Kotlin share without copying: a tag and operands per operation, little-endian. Paths and images are defined once by id, their definitions queued until `onDraw` takes them with the frame, so a frame drawn twice or skipped loses none (D152). It returns whether anything changed, and Kotlin calls `invalidate()` if so.
2. **In `onDraw(canvas)`**, a small Kotlin replayer reads the buffer and issues the `Canvas` calls: the same calls Android Compose's own drawing makes, with only one extra crossing.

**Groups and layers in the buffer** (D157). Each repaint boundary's group is a `GROUP` record carrying its key and version (a `u64` each) and its content without its layer's operations. A frame's buffer starts with a `LAYERS` section listing every group's layer (key, alpha, pivot, scale, rotation, translation, clip, whether it overlaps, and its bounds, `LayerProperties::bounds`: its size at its origin), so no record holds a layer, and a key and a version always stand for the same bytes. Rust keeps each group's record by key and copies it while the version stays; the frame still carries every group's bytes, so Kotlin records a group again from them whenever the system dropped its recording, without asking Rust. Kotlin keeps a node by key and version (stored once a recording completes), sets each listed layer on its group's node before the replay, only when its entry's bytes differ from the last ones set (a kept parent's nested ones too), and resets a node no longer listed. A `SaveLayerAlpha` around a group isn't folded into its drawing. A `SaveLayerAlpha` carries its bounds (`DrawScope::save_layer_alpha(bounds, alpha)`), as Compose's `Canvas.saveLayer(bounds, paint)`: the replayer bounds the offscreen layer by them, not by the recording's size, which a recording kept as its node grows outlives (D646). A `LAYERS` entry is 103 bytes (D525): key, alpha, pivot, scale, rotation, translation, whether it clips, its outline (kind: none, rectangle, rounded; bounds; four radii), elevation, ambient and spot colors, compositing (`Auto`, `Offscreen`, `ModulateAlpha`) and bounds, its offsets named on both sides (`serialize::layer_entry`, `Replayer`'s `ENTRY_` constants) and checked equal by a test. The replayer sets a property only when its bytes change, as Compose's `GraphicsLayerV29` does: an outline when the layer clips or casts a shadow (`setRoundRect` in whole pixels for a rectangle or equal corners, `setPath`, or `setConvexPath` on API 29, for corners that differ, at the layer's alpha, as Compose's `configureOutlineAndClip`), `setClipToOutline(clip)`, `setUseCompositingLayer(strategy == Offscreen)` and `setHasOverlappingRendering(strategy != ModulateAlpha)`; a node no longer a layer is reset to a render node's defaults. An outline that can't clip (`Outline.canClip`: a path before API 33) clips its node's recording to the path instead, as Compose's `usePathForClip` (`GraphicsLayerOwnerLayer.updateOutline`): `clipPath` first in the recording, built from the group's own entry and recorded again when it changes; a node no longer a layer loses it before the frame's records are read (`retireLayers`). Layer properties stay out of every record, so a layer-only change, its outline included, changes no version. A layer's node is positioned from the group's origin to the layer's far corner (the layer's own bounds when it's at the group's origin, the usual case, as Compose's `RenderNodeLayer`; not moved to the layer's origin, which a recording would bake in), so its alpha's offscreen layer is bounded by them, as Compose's; a group without a layer has the view's size. A software draw applies each layer as operations, its alpha layer bounded the same way.

**Path resources** (D532). The serializer keeps each path's contents still held under an id (`Resources::paths`, by identity and generation, with weak references to the contents). A write starts by noting the ids whose contents nothing holds any more (`Resources::free`): new contents of a path take one of its free ids, defined again in place (`DEFINE_PATH` with that id, no drop), or a new id; the free ids no contents took are dropped once the write is over. So a cached record always names the contents it was written with, and finding a path's id is constant time however many contents the path has (2,000 shapes from one reset path serialize in 0.17 ms in release, where linear searches took 3.0 ms). Each id's last definition is numbered (`Resources::serial`), and a record naming an id defined again since it was recorded gets a new version though its bytes are the same, since the replayer keeps a node by key and version (in any write, `write_groups_ahead`'s included; a test replaying the bytes as Kotlin keeps them checks that no key and version ever draws other contents). Definitions not taken are a list compacted once cancelled ones are half of it, one per id. Ids are 32-bit; once they wrap round (after 4 billion definitions) a new one skips those a path or an image holds. The replayer rewinds and refills that id's `android.graphics.Path` (`definePath`), recycling its masks, as Kotlin's `reset`: the stress waves' 50 contents keep 50 ids and `Path`s, refilled every frame. The desktop renderer keeps Skia's paths by identity and generation, forgetting gone ones when its cache reaches twice its size after the last sweep.

**Clips and gradients** (D210). `CLIP_PATH` (tag 17) names a path resource (the same ids as `DRAW_PATH`) and its offset; `Replayer.kt` clips to the path moved by a copy (`Path.offset`), not by translating the canvas there and back, and an unknown id clips everything out. A paint ends with its shader: a kind byte (0 none, 1 linear, 2 radial, 3 sweep), then the gradient's whole definition (tile mode, geometry, colors, stops) and its alpha, never `DisplayList::shaders`' index, so a cached record holds its content wherever it's copied. Colors are interpolated premultiplied on both backends: HWUI builds gradients with `kInterpolateColorsInPremul_Flag`, Skiko's `GradientStyle.DEFAULT` too, so compose-skia passes `InPremul::Yes`. One color is written twice, and stops not matching the colors are left out, as compose-skia does. What Skia makes no shader for (no colors, a position not finite, a negative radius) is written as none, so the paint's color (the average) paints; a radial radius of (nearly, Skia's 1/32768) 0, which `RadialGradient` refuses, is written as Skia's degenerate gradient: a solid color at the shader's alpha, the last color when clamped, the stop-weighted average (Skia's `average_gradient_color`) when repeated or mirrored, transparent with decal. With a shader the paint's color is black at the shader's alpha, as compose-skia's; a folded layer multiplies that alpha, so folding stays exact. Kotlin keeps up to 16 `Shader`s by their definition's bytes and the drawing's local transform (a path's scale and offset, undone by the shader's local matrix as compose-skia does; such a path isn't drawn from its mask, which is tinted by a color), the oldest replaced, so a static frame builds no shader (a NaN transform, equal to no key, is built and not kept). `TileMode::Decal` is `DECAL` on API 31+, `CLAMP` below. The serializer exports `operand_bytes`, the one reader of an operation's length the tests share.

### The rest of the platform glue

A thin Kotlin layer (`android/compose-rs`, an AAR) and `crates/compose-android` (the JNI functions, the display list's serializer, the text measurer). The JNI goes through the `jni` crate (0.22 since D621): the native methods take the caller's `EnvUnowned` and run their bodies without catching panics (`with_env_no_catch`), so a panic still aborts at the boundary (D361); a call back into Kotlin during one (text layout, a frame request, an event) runs in the main thread's top local frame, as before; the executor's wake and the image decoder attach another thread for good when they run on one, detached when it ends (the crate has no daemon attachments); `export_apps!`'s `JNI_OnLoad` takes the VM's raw pointer.

So while a `ComposeRsView` with `isPerformanceHintEnabled` (the `performance_hint` optimization: on by default, in the recommended set, D610; off at parity) shows, on API 33+, the RenderThread and the main thread are also in a session of compose-rs's own (the NDK's `APerformanceHint`, looked up at run time): each `frame` reads the RenderThread's and the main thread's CPU time (their thread CPU clocks) and reports what both used since the last frame against 8.33 ms, one 120 Hz interval (`TARGET_NANOS`) (after more than 25 ms without a frame, nothing: the time since isn't one frame's). Under the target, the power HAL's vote settles where the reports' mean is about 0.4 of the target, so the frame's whole work against one interval makes the vote follow the load (D500: 53 animating the feed, 261 scrolling it, 332 on the stress list); the RenderThread's time alone against 6.5 ms (D390) held its frames near 2.6 ms of CPU time on every screen, and a lighter screen got less boost. One session per process (the RenderThread is the process's), made at the second frame after such a view shows (not on the window's first traversal; the RenderThread found by name in `/proc/self/task`, then checked by name), closed when the last one hides or goes, made again if its thread stops being the RenderThread. The main thread (the one calling `frame`) is in it too: once the RenderThread is boosted, HWUI's session hardly boosts the main thread any more, which then ran 79 % of its time on the little cores on the stress list (D440). The power HAL gives a thread the highest vote of the sessions it's in (D390) | none: in `frame`, two `clock_gettime`s and the report (about 6 µs of main-thread work a frame) |
| Tracing | the frame's phases as `ATrace` sections (`compose-rs: recompose`, `layout`, `draw`, `text layout`, `serialize`, `replay`, `prefetch`, and within it each item's `prefetch compose` and `prefetch measure`; `record paragraphs`, `record ahead`, and within it `draw ahead` and `serialize ahead`), beside the system's in Perfetto | none |

The **frame and composition thread** is Android's main thread. Choreographer drives frames only while scopes are invalid or animations run and the window is visible, so an idle or hidden view costs nothing: a frame asked for while the window is hidden (`windowVisibility` turns `GONE` when the activity stops or the screen goes off) is made when it shows again, in the traversal that shows it, after its layout and before it draws (D342): `requestFrame` notes the frame, `onWindowVisibilityChanged` removes a posted frame callback (and the prefetch's) when the window hides, and when it shows asks for the noted frame through a one-shot `OnPreDrawListener`, so a size changed while hidden applies first and the frame shows the state as of now; prefetch work left when it hid is scheduled again. Animations go on from that frame's time (Rust's frame clock is the time itself), as Compose's do after its `PausableMonotonicFrameClock` resumes on `ON_START`. A view hidden by its own visibility (`INVISIBLE`, `GONE`) in a window that shows keeps its frames, which compose and are written for Kotlin, which draws nothing, as Compose's `AndroidComposeView` keeps composing there; its pending resource definitions stay one per id (D536). Rendering is the system's: a hardware-accelerated view's `Canvas` is recorded by the UI thread and drawn by the render thread on the GPU (Vulkan on recent devices), as Compose's is.

**Packaging:** the app's Rust library (its root composables named with `compose_android::export_apps!`) builds as a `cdylib` for arm64 with `android/build-rust.sh` (the NDK's linker, no `cargo-ndk` needed; segments aligned for 16 KB pages, as Android 15+ requires), run by Gradle on each build as a task whose output directory is the variant's `jniLibs` (D300), and stripped by the Android Gradle plugin with the NDK the apps pin (`ndkVersion = "30.0.16248370"`, r30 since D623, r27c's 27.2.12479018 before; D301: AGP strips native libraries only when it knows the NDK, and skipped it silently before, so bench-rs's APK went from 3,236,063 to 1,985,087 bytes, its library from 3,134,488 to 1,883,512, and the demo's debug APK from 34,126,521 to 32,160,441, its library from 4,909,024 to 2,933,048; the unstripped copy stays in `build/intermediates/merged_native_libs` and `target/` for profilers, and tombstones show Rust frames as offsets, which `ndk-stack -sym <that copy's directory>` symbolizes; `build-rust.sh` links with the NDK `ANDROID_NDK_HOME` names, else the pinned one when installed (Gradle passes it as `ANDROID_NDK_VERSION`), else the newest installed, and warns that Gradle won't strip the library whenever the pinned NDK isn't installed); `ComposeRsView(context, "name")` shows one of its apps. Debuggable variants build it with Cargo's `android` profile (release, with `panic = "abort"`) and the others (release) with `android-release` (also fat LTO and one codegen unit: a 1.40 MB library instead of 1.89, and a framework edit rebuilds it in about 5 s instead of 2); a panic aborts where it happens, after the panic hook logs it to logcat (`compose-rs: panic: …`, then SIGABRT with the panic as the tombstone's abort message), in debug builds as in release ones, also one unwinding would have let go: in background work nobody awaits, on an app's own thread, under an app's own `catch_unwind` (D361; desktop unwinds). The library ships a Baseline Profile (`android/compose-rs/src/main/baseline-prof.txt`: every class and method of `rs.compose.android`), which the Android Gradle plugin merges into each app's (wildcards, as AndroidX writes them: `Lrs/compose/android/**;` and `HSPLrs/compose/android/**->**(**)**`, every method hot, startup and post-startup, since ART's own record of the benchmark's screens marks only 9 of the about 120 methods run hot; D360); an install compiled from it (Play's, or androidx.profileinstaller's for other installs, which the app adds itself, as most do through AndroidX) runs the glue compiled ahead of time rather than in the interpreter and the JIT: the replay 37 % shorter than without (D360). `android/demo` hosts the examples (its counter tab reads the Kotlin tab as a property and sends Kotlin an event shown in a toast); `android/bench-compose` and `android/bench-rs` are the same app in Kotlin Compose and compose-rs, measured by `android/bench/measure.py` ([12](12-android-performance.md)).

### compose-rs's own optimizations

What compose-rs does beyond Compose's work is a flag of `Optimization::ALL` (`compose_ui::platform`, optimizations.rs; D520), set per host: `UiHost::set_optimizations`, Android's `ComposeRsView.optimizations` (`ComposeRsOptimizations`' bits; bench-rs's `-e optimizations none|recommended|all|default|<names>`), desktop's `WindowOptions::optimizations` and `COMPOSE_OPTIMIZATIONS`. The default is the recommended set, on the user's decision (D610, revising D581's parity default): `Optimizations::defaults()`, and so `Default`, `parse("")` and `parse("default")`, is `Optimizations::recommended()`, as Kotlin's `ComposeRsOptimizations.DEFAULT` is `RECOMMENDED`, for `ComposeRsView`'s constructors without optimizations (the demo app's), a new `UiHost`, `WindowOptions::default()` (`run_app`'s), `application`'s windows without `set_optimizations`, an unset or empty `COMPOSE_OPTIMIZATIONS`, the test rules' hosts (so tests exercise what ships; a test of Compose's own behaviour sets `Optimizations::NONE` with `compose_test::use_optimizations` or the host's `set_optimizations`), and bench-rs without `-e optimizations`. Parity, the work Compose does, is `none` (`Optimizations::NONE`, `ComposeRsOptimizations.NONE`): a benchmark against Compose passes it, so it measures the same work (docs/15, "Parity mode"; measure.py always passes bench-rs its list, `none` for `parity`), and measure.py's `--optimizations each` measures each flag alone against it as a candidate for Compose ([14](14-performance-opportunities.md), "Backport candidates"). An app can also pick `all`, or its own list. The headless benchmarks (`benchmarks/benches`) run at parity, `lazy`'s unless `LAZY_BENCH_OPTIMIZATIONS` names a set. The list (default, what it does, decision):

| Flag | Default | What it does (Compose instead) |
|---|---|---|
| `single_drawing_fade` | on | fades a layer holding one drawing by its paint, `ModulateAlpha`-like (an offscreen layer, `Auto`) (D521) |
| `performance_hint` | on | the main thread and the RenderThread in a hint session of compose-rs's own (HWUI's session only) (D390, D500, D568, D581, D610) |
| `reuse_paragraph_at_same_layout_width` | on | keeps a paragraph when new width bounds lay it out at the same width (lays it out again) (D551) |
| `prefetch_two_ahead` | off | prefetches two items (grid lines) ahead (one) (D156, D560) |
| `prefetch_budget_recent_maximum` | off | budgets a step by the larger of its average and a fading recent maximum, a 0.5 ms margin and the idle time's pace, gives a request short of time up until the next scroll, and runs to the vsync on the frame time's phase (the average, 0 when urgent; kept queued; the last frame's time plus an interval) (D340, D341, D381, D561) |
| `prefetch_at_rest` | off | prefetches after a layout at rest too (on scrolls only) (D470, D562) |
| `keep_items_behind` | off | keeps two items behind the scroll composed, disposes those beyond between frames, and lists their groups so Android keeps their recordings (deactivates in the measurement that leaves them) (D375, D380, D563) |
| `draw_prefetched_ahead` | on | Android: draws and records a prefetched item's groups, and its paragraphs, in the same idle time (nothing records before a frame places it) (D322, D350, D564) |
| `grid_lines_beyond` | off | grids compose and place two lines beyond each side (the lines in view) (D456, D565) |
| `flush_layers_before_dropped_paths` | on | Android: a frame dropping a stroked path draws a 1 x 1 compositing layer first, so HWUI flushes its layers (no such layer) (D510, D566) |
| `paragraph_render_nodes` | off | Android: each paragraph recorded once into a render node of its own, drawn by reference (drawn into its layer's recording each time it records) (D153, D567) |

The default set is `recommended` (`Optimization::RECOMMENDED`, D601, D610): `performance_hint`, `draw_prefetched_ahead`, `single_drawing_fade` with its companion `flush_layers_before_dropped_paths`, and `reuse_paragraph_at_same_layout_width`, the flags with a gain measured alone ([14](14-performance-opportunities.md), "Backport candidates"). Against `all` on the device it was as fast or faster at every frame percentile on every screen ([12](12-android-performance.md), "Recommended against all"); the six others measured no gain, or a small cost (`paragraph_render_nodes`, `keep_items_behind`).

**The mechanism** (D520). Each flag is a constant of the table with a bit, a name, a default and a summary; a set is an `Optimizations` (its bits; `parse` takes `none`, `all`, `recommended`, `default` or names, `-name` taking one out; `Debug` names them; an empty list, `COMPOSE_OPTIMIZATIONS=` or `-e optimizations ""`, is the defaults, the recommended set). The tree keeps the host's set, and renderers read `UiHost::optimizations`. Each flag says whether it `draws`: changing one that does draws everything again and writes every record again (`GroupCache::set_optimizations`: folds change bytes), and one that doesn't (the hint) touches nothing drawn. On Android, `ComposeRsView.optimizations` is a `Long` of `ComposeRsOptimizations`' bits (also a constructor parameter; a `@Volatile` field set on the main thread, posted there from others), passed to Rust at `create` and by `setOptimizations`, names parsed by Rust's table (`ComposeRsOptimizations.parse`, JNI `parseOptimizations`); `isPerformanceHintEnabled` is the `PERFORMANCE_HINT` bit. Desktop also has `compose_desktop::set_optimizations`. Adding a flag takes a constant and a row in Rust and a bit in Kotlin; the test `the_kotlin_constants_are_rusts` checks the bits, `DEFAULT` (`RECOMMENDED` while Rust's defaults are the recommended set), `RECOMMENDED` and `ALL` (and the `LAYERS` entry's offsets); `android_hosts_default_to_the_recommended_set`, `windows_default_to_the_recommended_set`, `a_host_defaults_to_the_recommended_set` and `the_rules_default_to_the_recommended_set` check each host's default.

Not flags, as Compose does the same: icons drawn from an `ALPHA_8` mask rasterized once per size (D190, D411: Compose's `VectorPainter` caches a tinted vector in an `Alpha8` `ImageBitmap`, `VectorComponent.draw` and `tintableWithAlphaMask`; compose-rs masks any small filled path, where Compose draws a path drawn outside an icon: no benchmark screen has one), and lazy items as repaint boundaries (D155).

### Later option: native Skia on Android

If profiling ever shows the replayer as a bottleneck (very heavy custom drawing), a `SkiaRenderer` can render natively into an `AHardwareBuffer`. The buffer is wrapped once as a `Bitmap` (`Bitmap.wrapHardwareBuffer`, API 29+) that `onDraw` draws, so the view is still composited like Compose content. The costs are shipping Skia (roughly 10 MB per ABI), pixels and text that may differ slightly from the system's, and managing a GPU context of its own. The `Renderer` interface keeps this a local change.

## Later platforms

- **iOS:** Skia on Metal inside a `UIView`, with UIKit glue for input, keyboard and accessibility.
- **Web:** CanvasKit (Skia compiled to WebAssembly), or a Canvas2D replayer like Android's.
