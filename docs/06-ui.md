# 6. UI (`compose-ui`, `compose-foundation`, `compose-material3`)

This follows Compose UI's structure: layout nodes with chains of `Modifier.Node`s, a public `Layout` primitive that `Column` and `Row` are written on, measure and place with constraints, and a draw pass. Text is measured and drawn by each platform's own stack, as in Compose.

## Nodes

- **`LayoutNode`**: one per UI element, owned by the `UiTree` arena behind `Copy` generational `NodeId`s. A node holds:
  - its `MeasurePolicy` (an `Rc<dyn MeasurePolicy>`, compared by pointer);
  - its modifier, and the chain of modifier nodes built from it;
  - its children;
  - its measurement: one *layer* per layout modifier, outermost first, then its own content, each with a size and an offset in the layer outside it (Compose's node coordinators).
- **`UiTree`** is the composition's applier (the `UiApplier` of earlier drafts): it implements the runtime's `Applier` for `LayoutNode`s (insert, move, remove, and release at the end of the pass, rule R1), and runs measurement, drawing, input, focus and semantics. Composables update their node's policy and modifier through `with_applier`. It never runs application code while the runtime holds its state.

## Modifiers: `Modifier.Node`, no `composed`

A `Modifier` is an **ordered chain of elements**. Call order matters, exactly as in Compose: `Modifier.padding(8.dp()).background(Color::RED)` differs from the reverse.

```rust
pub struct Modifier { elements: SmallVec<[Element; 6]> }     // Clone; ComposeArg (element-wise)

enum Element {                         // private: the built-ins, no allocation (D260)
    Padding(PaddingValues), Size(SizeSpec), FillMax(Axis, f32), Background(Color, Shape),
    Border(Dp, Color, Shape), Clickable(ClickableSpec), Toggleable(ToggleableSpec),
    Weight(f32, bool), Align(Alignment), Semantics(SemanticsSpec), …,
    Custom(Rc<dyn ModifierNodeElement>),                     // user-defined modifiers
}

pub trait ModifierNodeElement: Any {
    fn create(&self) -> Box<dyn ModifierNode>;
    fn update(&self, node: &mut dyn ModifierNode);           // in place: node state survives
    fn same(&self, other: &dyn ModifierNodeElement) -> bool; // through a downcast
}

pub trait ModifierNode: Any {   // optional capabilities, as Compose's Modifier.Node delegates
    fn as_layout(&mut self) -> Option<&mut dyn LayoutModifierNode> { None }
    fn as_draw(&mut self) -> Option<&mut dyn DrawModifierNode> { None }
    fn as_pointer_input(&mut self) -> Option<&mut dyn PointerInputModifierNode> { None }
    fn as_semantics(&mut self) -> Option<&mut dyn SemanticsModifierNode> { None }
    fn as_focus_target(&mut self) -> Option<&mut dyn FocusTargetModifierNode> { None }
    fn as_key_input(&mut self) -> Option<&mut dyn KeyInputModifierNode> { None }
    fn on_detach(&mut self, context: &mut DetachContext) {}  // release resources (paragraphs)
}
```

- **Diffing** happens on recomposition. When the kinds are the same, in the same order (the usual case: a value changed), each element updates its node in place, allocating nothing. Otherwise old and new elements are matched by kind in order (a longest common subsequence, as Compose's chain diff): matched ones update their node in place, so `clickable`'s pressed state and a text field's focus survive elements added or removed around them; the others' nodes are created or detached. A pointer gesture in progress follows its node to its new place in the chain.
- **The built-in modifiers are methods of `Modifier`** in `compose-ui` (`padding`, `size`, `width_in`, `height_in`, `fill_max_width`, `offset`, `weight`, `align`, `z_index`, `background`, `border`, `clip`, `clip_to_bounds`, `clickable`, `toggleable`, `selectable`, `selectable_group`, `focusable`, `on_focus_changed`, `on_key_event`, `test_tag`, `semantics`), with their nodes; a few are custom elements of `compose-ui` (`aspect_ratio`, `wrap_content_width`/`height`/`size`, `default_min_size`, `layout`, `on_size_changed`, `on_globally_positioned`, `combined_clickable`, `hoverable`, `draw_behind`, …). Rust has no extension functions, so an inherent method is what lets `Modifier.padding(…)` work with nothing imported; `compose::foundation` re-exports them where Compose has them. The scope tokens (`RowScope`, `ColumnScope`, `BoxScope`) live there too, with hidden constructors for the layouts that make them.
- **No `Modifier.composed`.** Elements are plain data. State a modifier needs (pressed, hovered, focused, later ripples) lives in its `ModifierNode`, owned by the `LayoutNode`, never in composition slots, and no modifier composes or `remember`s.
- **Handlers** live inside elements as `Callback`s (`Rc<dyn Fn>`). A closure argument in a modifier chain rooted at `Modifier` (`Modifier.clickable(move || count.update(…))`) is memoized by the macro like a call-macro argument ([03](03-composable-macro.md)), so a modifier rebuilt in a pass is `same` as the previous one, and a composable receiving it still skips. An `Rc` with identity is all it takes.
- **Allocation.** Built-in elements are enum variants in an inline `SmallVec`, so typical chains of up to six elements allocate nothing. Longer chains spill once.
- **Spelling.** `Modifier` is a type and also a `const` of that type, so code writes `Modifier.padding(16.dp())` as in Kotlin, and `modifier: Modifier = Modifier` as a default.
- **Representation.** `Element` and the chain's elements are private, so built-in modifiers can change their data without a breaking change; a user-defined modifier is added with `then_custom(element)` (D260).

## Layout

```rust
#[composable]
pub fn Layout(
    #[default(Modifier)] modifier: Modifier,
    measure_policy: Rc<dyn MeasurePolicy>,
    content: impl Fn() + 'static,
);

pub trait MeasurePolicy: 'static {
    fn measure(&self, scope: &mut MeasureScope, measurables: &[Measurable], constraints: Constraints) -> MeasureResult;
    // intrinsic sizes later, with default implementations
}

impl MeasureScope<'_> {
    fn measure(&mut self, measurable: Measurable, constraints: Constraints) -> Placeable;
    fn place(&mut self, placeable: &Placeable, x: i32, y: i32);
    fn layout(&self, width: i32, height: i32) -> MeasureResult;
    fn parent_data(&self, measurable: Measurable) -> ParentData;   // weight, alignment
    fn density(&self) -> Density;
    fn text_measurer(&mut self) -> &mut dyn TextMeasurer;
}
```

- **A closure is a policy**: `MeasurePolicy` is implemented for `Fn(&mut MeasureScope, &[Measurable], Constraints) -> MeasureResult`, and `measure_policy(|scope, measurables, constraints| …)` makes one for `Layout` with the argument types inferred, as Kotlin's `MeasurePolicy { measurables, constraints -> … }`: `Layout!(modifier = …, measure_policy = measure_policy(|scope, measurables, constraints| { … }), { … })`. A new closure is a new policy (measured again), as a Kotlin lambda; `remember` one that doesn't change (D176).
- **One measure-and-place pass with constraints**, as in Compose, except that a policy places its children in the same call that measures them, rather than in a placement block run afterwards. A layout modifier (`LayoutModifierNode::measure(scope, content, constraints)`) measures and places the content it wraps the same way.
- **Incremental.** Updating a node's policy or modifier, or inserting, moving or removing children, marks it for measuring and its ancestors as having a dirty descendant. The next layout measures from the root, but a node with unchanged constraints and nothing dirty returns its size at once; one with only dirty descendants measures them again in place, and runs its own policy only if one of their sizes changed. So a change climbs to the first ancestor whose size holds. A frame where nothing changed measures and draws nothing.
- **Rules.** A policy may measure a child only once per measurement, as in Compose: measuring it again panics. A panic in a policy or a layout modifier node leaves the tree whole (each node's children and modifier nodes are put back as the panic unwinds) and the node marked for measuring again. Pixel rounding is Kotlin's `roundToInt` (halves up), and `Constraints::offset` adds, as Compose's.
- **Outside the constraints.** A measured size is coerced into the constraints for the parent; the node keeps its measured size and is centered in the coerced one, as Compose does (`required_size` past the parent's bounds).
- **The root** measures its children with the window's constraints loosened, and places them at the origin.
- **Layout modifiers** as Compose's: `aspect_ratio(ratio)` and `aspect_ratio_with(ratio, match_height_constraints_first)` (Compose's search: the maximum width, the maximum height, the minimums, then the same past the constraints), `wrap_content_width()` (and `wrap_content_width_with(align, unbounded)`), `wrap_content_height` and `wrap_content_size` (the content at its own size, aligned in the size imposed), `width_in`/`height_in` (`size_in` on one axis), `default_min_size` (a minimum only where the constraints set none), and `Modifier.layout(|scope, measurable, constraints| …)`, a closure measuring and placing the content (a new closure is a new modifier, as Compose's lambda; state it reads measures it again).
- **Layout callbacks.** `on_size_changed(|size| …)` reports the size of what follows it in the chain when first measured and when it changes; `on_globally_positioned(|coordinates| …)` reports a `LayoutCoordinates` (a snapshot: `size`, `position_in_root`, `position_in_window`, and `bounds_in_root` clipped by the clipping modifiers around it, a scroll's viewport) after each layout that changed it (through the graphics layers' transforms on its path, as Compose's `localToRoot`; a layer-only change doesn't report), as `GlobalPositionAwareModifierNode`s the tree registers; an intrinsic probe doesn't call `on_size_changed`. Both run once the layout is over, outside the tree, before drawing: state they write is composed and laid out again in the same frame. A measurement reading state another wrote while laying out (a lazy list's viewport size, read by `fill_parent_max_*`) is measured again within the same layout (`UiHost::lay_out`, twice at most).
- **Drawing order.** Children are drawn, and hit, in the order their parent placed them, sorted by `z_index` first (several on one node add up), as Compose's.
- **Nested scrolling** (D188): `Modifier.nested_scroll(connection)` lets a `NestedScrollConnection` (as Compose's) take part in the scrolls of the scrollables inside it: foundation's scrollables offer each drag, wheel and fling delta to the connections around them before scrolling (the outermost first) and what's left after (the innermost first), and their flings' velocities before and after; Material's top app bars collapse and its bottom sheets drag this way.
- **State read in measurement and drawing is observed**, as Compose's `SnapshotStateObserver` does: a node's policy and its custom layout modifiers measure, and its custom draw nodes draw, under an observation keyed by the node, so a write to what they read measures or draws that node again at the next frame without recomposing (built-in nodes read no state and aren't observed). `vertical_scroll` keeps its offset in state this way.
- **`Box`, `Column`, `Row` and `Spacer` are ordinary composables** in `compose::foundation::layout`, each a `Layout` with its own `MeasurePolicy`. That's Compose's split: layout is library code on a public primitive, not built into the node kinds.
- **Arrangements** (D262) are typed per axis, as Compose's `Arrangement.Horizontal`, `Vertical` and `HorizontalOrVertical`: `HorizontalArrangement` (what `Row` and `LazyRow` take: `Arrangement::START`, `END`), `VerticalArrangement` (`Column`, `LazyColumn`: `Arrangement::TOP`, `BOTTOM`), and `HorizontalOrVerticalArrangement` (`Arrangement::CENTER`, `SPACE_EVENLY`, `SPACE_BETWEEN`, `SPACE_AROUND`, `spaced_by(8.dp())`), which converts to either (`.into()`, where two branches must agree: `if expanded { Arrangement::START } else { Arrangement::CENTER.into() }`), so `Row!(horizontal_arrangement = Arrangement::TOP)` doesn't compile. The constants are SCREAMING_CASE, as `Alignment::TOP`. Compose's overloads take one argument: `Arrangement::spaced_by((8.dp(), Alignment::END))` is a row's, `spaced_by((8.dp(), Alignment::BOTTOM))` a column's, and `Arrangement::aligned(alignment)` likewise. A custom arrangement implements `HorizontalArrangementPolicy` or `VerticalArrangementPolicy` (`spacing`, `arrange`) and is wrapped by `HorizontalArrangement::custom(…)`, compared by the policy's `same` (by default: the same zero-sized type; a policy with data compares it), else by reference. `LazyVerticalGrid`'s cells fill its width, so it takes only an arrangement's spacing. There is no `Arrangement.Absolute` yet.
- **Scoped modifiers.** `weight` and `align` exist only inside `Row`/`Column`/`Box` content, as in Compose. Rust has no context receivers, so a content lambda receives its scope as a `Copy` zero-sized token, and those modifiers take it:
  ```rust
  Row!(modifier = Modifier.fill_max_width(), |row| {
      Text!("Title", modifier = Modifier.weight(row, 1.0));
      Text!("Done");
  });
  ```
  A `RowScope` value can only come from `Row`, so misuse is a compile error at zero runtime cost. Compose's `Modifier.weight(1f)` reads slightly cleaner; this is the closest checked equivalent. `Box` the composable lives in the value namespace and `std::boxed::Box` in the type namespace, so they don't clash.

**Lazy lists.** `LazyColumn` and `LazyRow` compose and place only the items in view, as Compose's (`beyondBoundsItemCount` 0), and compose a few more between frames (below): `LazyColumn!(state = list_state, |scope: LazyListScope| { scope.items_keyed(todos.len(), move |index| ids[index], |index| TodoRow(…)); })`, with `item`, `items` and `items_keyed` (an item keeps its state when items before it come and go), and over a list (an `ImmutableList`, shared, or a `Vec`, an array or a slice, copied into one) `items_list`, `items_list_keyed`, `items_indexed` and `items_indexed_keyed` (Compose's `items(list)` and `itemsIndexed`, named apart: Rust has no overloads), each with a `_with` form taking Compose's `contentType` after the key (`items_keyed_with(count, key, content_type, content)`, D432), whose content receives the `LazyItemScope` (the others get it from `scope.item_scope()`) for `Modifier.fill_parent_max_width(&scope)`, `fill_parent_max_height`, `fill_parent_max_size` and their `_fraction` forms (the viewport less the content padding, as Compose's); content padding, arrangement, and the cross-axis alignment (a column's `HorizontalAlignment`, a row's `VerticalAlignment`, as `Column`'s and `Row`'s). `reverse_layout` lays the items out from the end (the first item at the bottom, or the right of a row in left to right) and reverses drags, the wheel and bring-into-view; the arrangement stays physical, as Compose's (`Arrangement::TOP` places a short reversed list's last item at the top), but its default stays `TOP` where Compose's becomes `Bottom` (D171). `user_scroll_enabled = false` keeps drags and the wheel from scrolling (the state and bring-into-view still do). `sticky_header(|scope| …)` (and `sticky_header_keyed`) adds a header that sticks at the list's start over the items after it, pushed out by the next one, as Compose's `stickyHeader`: the measurement writes which header is over the first visible item, which the items' composition keeps composed (wherever it is), and places it last, so it's drawn over the items and hit first. Keys are hashed to 64 bits; debug builds check the composed items' keys and panic on a duplicate (as Compose throws) or on a hash collision of different keys (which would share their state), comparing the full keys (D170). Compose composes items while measuring; here composition can't run inside layout (the tree is borrowed), so the list composes a range of items, and its measurement, which fills the viewport from the `LazyListState` (the first visible item and its offset), writes the range it needs when the composed one falls short. It asks for as many items as the room left takes at the size of those in view (their average, the first of them left out when others follow it), but never more than 4, or as many as it placed, or twice what it asked for the round before (a scroll past the composed items, none placed, D492), and 512 at most (zero-height items), a round: what it asks for then doubles round to round while it lacks items, so whatever the sizes it asks for at most about twice what it turns out to need, and the frame's rounds (up to 16) are as many as doublings (D487); estimates alone kept breaking on some sizes (a header, a 1 px divider after a card, a spacer and a divider: D475, D481): a first layout knowing only a small header would compose dozens of items it then drops (the stress list's 81 px header once made it compose 87 items, rows and the carousels' tiles, where 15 show; D472). `UiHost::frame` then recomposes and measures again within the frame, up to 16 times (D487), so a scroll never shows an empty frame; what such a round composed asks for no other frame (D474). To keep that work out of frames, a list **prefetches** between frames as Compose 1.12.1's default `LazyListPrefetchStrategy` and `LazyLayoutPrefetchState` (D560; docs/15, "Compose's defaults" (a), (b), (f); `lazy/prefetch.rs`). After each layout that settled (nothing missing), its measurement runs the strategy: Compose's `onVisibleItemsUpdated` cancels a request whose item isn't the next one the last scroll's way any more, and `onScroll`, with the scrolling since the last such layout (Compose's sign, negative towards the end), requests the item after the last one in view (before the first, scrolling back), none behind, cancelling what it held when the direction turns, and marks the request urgent when the same delta again would reach the item (`lastItem.offset + size + spacing - viewportEndOffset < -delta`); items coming or going after a scroll request the next one too. A request (`PrefetchRequest`, given to the host's `PrefetchScheduler`, `LOCAL_PREFETCH_SCHEDULER`) runs when the platform is idle, `UiHost::prefetch(deadline)` (`prefetch_with`: the first request without a deadline, as Compose's `isFrameIdle`): it composes its item (one more in the composed range, recomposed outside the frame) with a paused composition, as Compose's default (D595): the item's content is `PausableContent` ([04](04-runtime.md), "Pausable composition"), so the composition pauses at its pause points once the time left is no more than the item's content type's averages of a stretch of composition and a pause, resumes after the next frame, and is applied once complete (its nodes attached, its effects run); then it composes the first items of the lazy lists composed in it (two, then the parent's running average, for the item's content type, of the smallest nested list's visible count; nested lists note themselves in their item's `LOCAL_PARENT_LIST`, whoever composes it, as Compose finds them by `traversablePrefetchState`), and measures it with the items' constraints (`PrefetchRequestScope::premeasure`, composing and measuring again what that wrote, a nested list's items, a `BoxWithConstraints`' content). Each step runs only while the time left exceeds that step's running average for the item's content type (`current / 4 * 3 + new / 4` in integer nanoseconds, divided first, the first sample taken as is; any time left for an urgent request): composing, a stretch's and a pause's (the time between pause points, and to stop at one); applying and measuring, their own; a step that doesn't fit, or a composition that paused, leaves the request queued, to go on after the next frame, as Compose's `AndroidPrefetchScheduler`. An item whose paused composition isn't applied is one the layout lacks: a frame wanting it asks for the paused composition to be completed and composes its items in a round, whose pass completes and applies it first (D592); a request cancelled with its composition paused (the scroll turned, the list left) discards it, its nested lists' requests' too, and the layout has the items composed again, which lets the item go (D593); an item leaving while its content is paused is discarded with it, not completed. Without pausable composition (`ComposeFoundationFlags::set_pausable_composition_in_prefetch_enabled(false)`, Compose's flag) a request composes its item in one step, gated on the whole composition's average. The composed items are those the layout wants, those requests hold next to them (composed by the request, or already), and the next one the layout's estimate composed ahead of them in the scroll direction (the unit a scroll that way requests: disposing it would compose it again when it comes; none once a focus search is over, whose rows go, D482); the others are deactivated (kept for reuse, a request's item too, as Compose's precomposed slot; disposed if never measured) by the next composition: the frame's, when it composes items anyway, else the first request of the next idle time with any time left, whatever else waits, so a frame where items only leave runs no composition, as Compose's measurement deactivates them without composing (D575). A grid's first layout asks for a few lines at a time, as a list's (D578). A grid's line before the first in view is requested from its end, each item next to the composed ones (D577). compose-rs's own behaviours are optimizations of the host's, off by default ([07](07-platforms.md), "compose-rs's own optimizations"): two items ahead (`PREFETCH_TWO_AHEAD`, D156), D341 and D381's budget (the larger of the average and a fading recent maximum, a 0.5 ms margin, scaled by the idle time's slowest step, a request short of time given up until the next scroll: `PREFETCH_BUDGET_RECENT_MAXIMUM`; with pausable composition, an item's composition starts once its whole composition's estimate fits, and pauses by the stretch and pause averages at that pace and margin, D596), prefetching after a layout at rest too (`PREFETCH_AT_REST`, D470), two composed items kept behind the scroll, those beyond disposed between frames by the next request's composition, and their groups listed (`KEEP_ITEMS_BEHIND`, D375, D380), and drawing prefetched items ahead (`DRAW_PREFETCHED_AHEAD`, D350, below). Items composed beyond the wanted range aren't placed, as Compose's prefetched items: nothing draws them, `first_visible_item_index` and the rest don't move, and the frame that scrolls them into the wanted range finds them composed and measured; each is a repaint boundary, so that frame draws it for the first time and the items that stay keep what they drew (D155). With `DRAW_PREFETCHED_AHEAD`, a platform that records each group (Android's render nodes) draws a prefetched item ahead too, in the same idle time (`UiHost::draw_ahead`, D350): its group and those nested in it are drawn then, in their own coordinates, and the frame placing the item shares what they drew, versions unchanged (placing a boundary draws its parent again, not it), so that frame neither draws nor records it; a write to what it read draws it again, as any boundary. Items measured ahead and not drawn ahead are forgotten once placed or gone, or when the platform gives them up (`cancel_draw_ahead`: an idle time with nothing else in it was too short for one). With `KEEP_ITEMS_BEHIND`, an item a frame drew that stays composed and is no longer placed keeps its group listed in each frame (`DisplayList::kept`, below, "Repaint boundaries"), so the frame placing it again after a reversal finds it recorded too (D380), and a frame that composes items keeps those composed next to the wanted ones, two on each side (a jump keeps none). A prefetched item that takes the focus (an autofocused field) is placed with the others and, as any node focused before its first placement, scrolled into view once laid out. Items outside the range leave the composition (their state goes, as in Compose without `rememberSaveable`), but the focused one, pinned by key, which stays composed and placed (Compose's pinning). **Reuse** (D430): as Compose's lazy layouts, an item that leaves isn't disposed but deactivated and kept for reuse, and an item coming in (in a frame, or prefetched) is composed in its place: the list composes each item in a slot (a keyed group holding a reusable group keyed by its item, `compose_slot`), and keeps up to 7 deactivated slots per content type (`LazyLayoutItemReusePolicy`, the newest), an item taking the slot it had if it's still kept, else the newest of its content type (those without one sharing Compose's `null`), else a new one; a slot whose item leaves goes to an item coming in the same pass. An item that leaves without ever having been measured (composed beyond what a first layout's estimate then wanted, or prefetched and left before its measurement) is disposed, not kept: Compose, composing items as its measurement reaches them, never composes it (D460). The reused content runs anew, its remembered values computed again and its effects disposed and launched again, and keeps its layout nodes: `UiTree` resets their modifier nodes (`ModifierNode::on_reset`, as `Modifier.Node.onReset`: a press, a gesture, a focus, an animation under way) and keeps them for the new elements to update (D431). Kept slots' nodes stay the list's children, after the items'. A deactivated node, in any layout, isn't one of its parent's measurables, so it's never measured, placed, drawn, hit, focused (its focus requesters detached) or in the semantics, whatever it read, until reused; its modifier nodes are reset after the pass, outside composition (D434). A list in a reused item keeps its slots (`platform::remember_across_reuse`, as Compose keeps the reused node's `SubcomposeLayoutState`), so a feed of carousels reuses the carousels' items too. A focus search (Tab, or a direction) from inside the list looks inside it first, as Compose's focus groups; finding nothing more, it asks the list for the next item that way, as Compose's `BeyondBoundsLayout` (`ModifierNode::lay_out_beyond_bounds`, D477): the list composes and places it beyond its bounds at the next layout (in the frame), the search is made again, and again one item further while it finds nothing focusable (Tab past unfocusable rows), until it finds one or the list ends; then the list around it is asked (a carousel's row in a list, D483), then the window; a container with no more that way isn't asked again in the search, and a search lays out at most 200 items in all, so it ends within about 25 frames whatever the tree (D486). Keys pressed meanwhile wait their turn; the frame shows the item found, scrolled in (D485); once the search is over the items laid out for it go, disposed rather than kept for reuse (D482). A focused node is brought into view by its scrolling ancestors (`ModifierNode::bring_into_view`, as `BringIntoViewResponder`; `vertical_scroll` does it too). The scroll position follows the first visible item by key when items come and go before it, and so do the items composed: when the items change, the composed range moves as the first visible item did, found by key, widened for the other composed items found near it, so they stay composed (their state kept) rather than leaving and coming back (D453, D458). It keeps fractions of a pixel, and steps over items only once they are composed (their sizes known), but for jumps of hundreds of items, which it estimates from the average size (Compose composes every item in between). Keys are looked for within a window around their last index; items are found by binary search over the intervals. An empty first layout (data still loading) keeps the initial position; an emptied list starts again at its top. Content shorter than the viewport is placed by the arrangement. How far it can scroll each way is known where its ends are laid out, else estimated from the average size: a scroll (`scroll_by`, a drag, a fling) past an estimated end isn't cut there, the measurement takes it all and stops at the end it reaches, composing in the frame what it passes, as Compose's measurement consumes a delta (D476); what it couldn't use of user input then goes to the nested-scroll parents around (their post-scroll, after the layout, in the frame: D479; the start followed by key, D488; a grid's too, D490; and a list as the parent of a scrollable inside it passes on what it couldn't use of that one's rest, D489), where Compose's synchronous remeasurement gives it at once. An emptied list takes no scroll (D480). Its semantics say how far it's scrolled and can be (`vertical_scroll_axis_range` or `horizontal_…`, as Compose's `ScrollAxisRange`) and offer `SemanticsAction::ScrollBy` (positive: towards the content's end), which accessibility services scroll it with a page at a time, as `vertical_scroll`'s and `horizontal_scroll`'s do; Android's directions map onto it as Compose's accessibility delegate does (`accessibility::scroll_actions` and `scroll_amount`: forward towards the end, paired with right, or left right to left, or down; reversed layouts flipped) (D478, D491). The wheel and drags scroll it: the innermost scrollable takes a drag past the slop (8 dp from the press; scrolling what moved beyond it), and a wheel delta a list can't use goes on to the scrollables around it; `scroll_to_item` jumps; at the end, the last item ends the viewport.

**Constraints and grids.** `BoxWithConstraints` (as Compose's) gives its content the constraints it's measured with (`BoxWithConstraintsScope`: `max_width()` and friends in `Dp`). Compose composes it while measuring; here it first composes for the constraints it'll likely get (`LOCAL_CONSTRAINTS_HINT`: the window's at the root, a lazy list's items', a grid's cells'), and the measurement writes those it got as state, composing it again within the frame if they differ.

**Lazy grids.** `LazyVerticalGrid(columns, …)` and `LazyHorizontalGrid(rows, …)` (`GridCells::Fixed(n)` or `Adaptive(min)`, as Compose's) lay their items out in lines: a vertical grid's rows, a horizontal one's columns. As Compose's, a grid composes item by item (D450): its items are composed by the lazy list's item composition (`LazyItems`), each in a slot of its own with its key (state kept by key, the scroll position following the first visible item's key, saveable state by key), reused by an item of its content type once it left (up to 7 per type, as a list's, D430), and prefetched one at a time between frames; its measurement (`LazyGridLayout`, as Compose's `measureLazyGrid`) works in lines: the line holding the first visible item, filled to the viewport, and, as Compose's `LazyGridPrefetchStrategy`, the next line the scroll's way prefetched, a request for each of its items, cancelled and urgent by the list's rules (D560, D565); with `GRID_LINES_BEYOND`, `BEYOND` (2) lines composed and placed beyond each side too (D456), and with `KEEP_ITEMS_BEHIND` lines kept behind: the measurement gives prefetching those limits in items, so a frame trims what's composed to the same, whatever the spans. Its items' sizes are kept by item (what tells a slot leaving was measured, D460) and its lines' apart (what its estimates use), each with a running sum (D456). Cells are as large as Compose's across the grid (the room less the spacing divided evenly, the remainder a pixel each to the first cells); an item is measured fixed across its cells (Compose's `Constraints.fixedWidth`, or `fixedHeight` for a horizontal grid), unbounded along, and a line is as long as its longest item, its items at its start. The `LazyGridScope` has the list's forms (`item`, `items`, `items_keyed`, `items_list`, `items_indexed`, keyed or not), each with a `_with` form taking Compose's `contentType` after the key, as a list's (`items_keyed_with(count, key, content_type, content)`), and a `_with_span` form taking Compose's `span` and `contentType` (`items_keyed_with_span(count, key, span, content_type, content)`, D454): a span (`GridItemSpan(cells)`) is worked out from the `LazyGridItemSpanScope` (`max_line_span`, `max_current_line_span`, the cells left in the line) and the item, kept within 1 and the line's cells; an item that doesn't fit the cells left starts the next line, its span asked again for a whole line, as Compose's `LazyGridSpanLayoutProvider`. Which items a line holds is arithmetic without spans; with spans, the items are walked from the first only as far as a measurement asks (kept while the items and the cells are the same: a caller recomposing with the grid's content lambda unchanged skips the grid; a content that changed walks them again, as Compose's, D454), the line count estimated from the items not walked. `LazyGridState` counts in items (`first_visible_item_index` is the first item of the first visible line; `scroll_to_item` scrolls to the item's line), so a new cell count keeps the first item in view. Right to left, a vertical grid's first column is at the right, and a horizontal grid's first column too, as a `LazyRow`'s first item. A grid needs a bounded size along and across its axis. The items of a not yet measured grid compose for a cell's constraints in the space around (`LOCAL_CONSTRAINTS_HINT`), then for those of a one-cell item. No `reverse_layout`, `user_scroll_enabled`, sticky headers, `GridCells.FixedSize`, or staggered grids.

**Gestures.** `Modifier.pointer_input(key, |scope| async move { … })` (as `pointerInput(key) { … }`) runs a coroutine over the pointer events reaching its node: `scope.await_pointer_event(pass)` gives each one as a `PointerInputChange` it can `consume()`. The coroutine is an executor task polled at once as each event reaches the node (`platform::poll_now`, as Compose resumes it undispatched), so what it consumes the handlers after it see consumed; its timeouts are executor timers. It starts at the first event and starts over when its key changes, its gesture is cancelled or its node leaves; a block that returns stays done. Each change carries its pointer's id and time (`uptime_millis`), and `Enter`/`Exit` go through the three passes as other events. Compose's detectors are there, with their rules: `await_first_down`, `wait_for_up_or_cancellation` (up once no pointer is down; cancelled when a move is consumed, in the main pass or by a parent by the final pass, or leaves the node), `await_touch_slop_or_cancellation`, `with_timeout`, `detect_tap_gestures(TapGestures)` (tap, double tap within 300 ms but not sooner than 40 ms, long press after 400 ms, press; a cancelled or held second press still reports the first tap) and `detect_drag_gestures(DragGestures)` (past the 8 dp touch slop, following the pointer that crossed it, its first amount what's past the slop; a parent that takes the moves first keeps the gesture); their callbacks run once the event's dispatch is over. `PointerInputDriver` runs a block for custom pointer nodes. Foundation's `Modifier.draggable(state, orientation, …)` (its `on_drag_stopped` given the release's velocity, from the last 100 ms of moves as Compose's `VelocityTracker`) with `remember_draggable_state(on_delta)` reports drags along an axis as deltas, as Compose's: a node of its own that calls its newest callbacks, and calls `on_drag_stopped` when the drag is cancelled too.

**More clicks.** `combined_clickable(on_long_click, on_double_click, on_click)` (and `combined_clickable_with(options, …)`), as Compose's `combinedClickable`: its presses go through `detect_tap_gestures` (with `on_double_click`, a click waits out the 300 ms double-click timeout; with `on_long_click`, holding 400 ms long-clicks), its indication shows while a press is held, and its keys, focus, hover and semantics are `clickable`'s, plus a long-click action (`SemanticsAction::OnLongClick`, `long_clickable`) with `on_long_click`. `selectable(selected, on_click)` is a clickable whose semantics say `selected`, and `selectable_group()` marks the group, as Compose's. `hoverable(interaction_source, enabled)` reports a mouse over the node to the source.

**Hover.** A mouse's hit path is tracked: when it changes, what the mouse left hears `PointerEventType::Exit` and what it came over `Enter`, as Compose's (not while a button is held: a drag stays with what it pressed); leaving the window (`UiHost::send_pointer_left`, from winit's `CursorLeft`) is an exit, and content moving under a resting mouse moves the hover (a hit test after each layout, as Compose Desktop's synthetic move). Clickables show Material's hovered state layer (8 %; 10 % pressed or focused). `Modifier.pointer_hover_icon(icon)` (as `pointerHoverIcon`) sets the mouse pointer's look over a node (`PointerIcon::Text`, `Hand`, `Crosshair`; the innermost on the hovered path wins); text fields show an I-beam, and the desktop window sets its cursor from `UiHost::pointer_icon`.

**Tooltips.** `TooltipArea(tooltip, …, content)` (as Compose Desktop's) shows `tooltip` in a popup at the mouse pointer, 16 dp below it (`TooltipPlacement`), or above it where there's no room below, once it has rested over the content for 500 ms (moving starts the wait again), and hides it when the pointer leaves the area (resting on the tooltip inside the area keeps it) or presses; Material's `PlainTooltip` is its look (the small body text on the inverse surface).

**Scrollbars.** `VerticalScrollbar` and `HorizontalScrollbar` (as Compose Desktop's) show a thumb for a `ScrollbarAdapter` (`remember_scrollbar_adapter(scroll_state)`, exact; `remember_lazy_list_scrollbar_adapter(list_state)`, from the average item size): its length the viewport's share of the content (at least 16 dp), dragged to scroll, a press on the track paging toward it, hidden while everything fits; `ScrollbarStyle` and `LOCAL_SCROLLBAR_STYLE` as Compose's defaults (8 dp, black at 12 %, 50 % while dragged). The thumb darkens while hovered or dragged.

**Layout direction.** Each layout node takes `LOCAL_LAYOUT_DIRECTION` (as `LocalLayoutDirection`) where it's composed; the host provides the window's (`UiHost::set_layout_direction`, `WindowOptions::layout_direction` on desktop), and `CompositionLocalProvider` changes it for a subtree. `MeasureScope::layout_direction`, `DrawScope::layout_direction` and `EventContext::layout_direction` read it. In right-to-left, as Compose: `place_relative` mirrors a child in the width its layout reports (once that's known); the root, `padding`, `offset`, the size modifiers, scrolling containers, lazy lists and Material's layouts place relatively; a `Row`'s arrangement and `Box`'s and `Column`'s alignments run from the right (a `Column`'s arrangement still runs from the top); a horizontal scroll or lazy row starts at the right and a drag, a wheel or a focused child's bring-into-view goes the other way; a text field lays its text out again when the direction changes; popups align with their anchor's start and offset toward its end, and menus try the anchor's right first; a slider and a switch are drawn mirrored (and the slider's pointer and arrow keys follow); text with no strong character runs in the layout's direction.

## Text

- **`TextMeasurer`** is the interface layout uses: it lays out a paragraph and returns a handle with its metrics. Each platform implements it with the text stack Compose uses there ([07](07-platforms.md)):
  - **desktop:** Skia's paragraph module (HarfBuzz shaping, ICU line breaking and bidi), as Compose Desktop;
  - **Android:** Android's own `StaticLayout`, as Android Compose.

  Kerning, ligatures, complex scripts, fallback fonts and emoji come from the platform stack.
- **Tests** use a fixed-advance measurer by default, so measurements are identical on every machine and don't depend on fonts; the Skia measurer (the system's fonts, no bundled ones: D94) can be given to a test host.
- `BasicText`/`Text` keep the paragraph handle on the node, so a recomposition with the same text measures nothing. New constraints lay it out again as Compose's `ParagraphLayoutCache` decides (`newLayoutWillBeDifferent`, D550; [15](15-android-stress-benchmark.md), "Compose's defaults" (g)): always for a new minimum or maximum width, for a new height only when the paragraph is taller than it or cut at its maximum lines; a new text, density, direction, or style attribute that lays text out (`TextStyle::has_same_layout_affecting_attributes`, as Compose's) lays it out anew. A new color or decoration only keeps the layout and draws it in the new paint (`TextMeasurer::restyle`, D555), as Compose's `updateDraw`; where the measurer can't (the desktop's), the text is laid out anew. A layout for new constraints goes through `TextMeasurer::relayout` where the measurer keeps what it measured of the text, as Compose's `ParagraphIntrinsics`: Android's (`TextMeasurer.kt` keeps the spans, paint, boring metrics and own width, so a new width doesn't measure the text's own width again; its `StaticLayout` still measures what it breaks); the desktop's lays the text out anew. An intrinsic probe (`max_intrinsic_width`, `max_intrinsic_height`) whose constraints would lay the text out differently measures a paragraph of its own, kept for the next probe, and leaves the measured one and its constraints alone (D554), as Compose's intrinsics have caches of their own; on Android it's laid out from the measured paragraph's kept intrinsics and never recorded ahead. A probe fills no measurement cache: a node it measured is measured again for real (D556).
  - **A compose-rs-only optimization, off by default** (D551): with the host's `Optimization::REUSE_PARAGRAPH_AT_SAME_LAYOUT_WIDTH` (D520), a new width bound keeps the paragraph when the width it's laid out at (Compose's `finalMaxWidth`: the text's own width within the bounds, or the maximum when the minimum equals it) is the same, and the paragraph fit: its own width within the line width limit, so no line broke to fit, and no line past its maximum. A measurer lays a text out from that width alone, so the layout is the one a new layout would make: a short label in a container whose width changes keeps its paragraph; a text across the whole width (`fill_max_width`), wrapped, ellipsized, or held wider by a minimum width that changes is laid out again. Measurers report the text's own width (`TextMeasurer::max_intrinsic_width`); without it, Compose's rule applies.
- **Styles.** `TextStyle` has Compose's color, size, weight, style (italic), family (sans-serif, serif, monospace, cursive, or a system family by name, falling back to the default), letter spacing, decoration (underline, line-through), alignment (start, end, left, right, center, justify) and line height; what isn't set comes from the style it's merged over (`merge`), and Material's `Text` takes each as a parameter over `LOCAL_TEXT_STYLE`, as Compose's. `overflow` (as `TextOverflow`) clips by default, ends the last line with "…" (`Ellipsis`; one line without soft wrap, as Compose's), or draws past the bounds (`Visible`). **Styled spans** come from `AnnotatedString` (as Compose's): text with `SpanStyle`s (color, size, weight, style, family, letter spacing, decoration, background) over byte ranges, built with `AnnotatedString::build(|builder| { builder.append(…); builder.with_style(…, |builder| …); })`; `BasicAnnotatedText` and Material's `AnnotatedText` show one, each run laid out in its style (SkParagraph's styled runs). Link annotations aren't there yet.
- **Line bounds and layout results.** `min_lines` makes a text at least that many lines high (as `heightInLines`; `0 < min_lines <= max_lines`, else it panics, as Compose's `validateMinMaxLines`), and `on_text_layout` hears each new layout (the paragraph laid out again for a new text, style or width, or a new size; not a measurement that changed nothing, and a new listener only swaps the old one) as a `TextLayoutResult` (as Compose's, a snapshot of its metrics without its queries: `size`, `line_count`, the baselines, `did_overflow_width`, `did_overflow_height` with the lines cut by `max_lines`, `has_visual_overflow()`), called after the layout as `on_size_changed` is (`MeasureScope::run_after_layout`), so what it writes is laid out within the frame; an intrinsic probe isn't reported. Whether lines were cut comes from `TextMeasurer::did_exceed_max_lines` (Skia's `didExceedMaxLines`, `StaticLayout`'s line count and ellipsis on Android; a measurer that can't tell says no) (D233, D250).

## Drawing

A draw pass records a **display list**: a subset of the `Canvas` API (clips to rectangles, rounded rectangles and paths, transforms, rectangles, rounded rectangles, arcs, lines, paths, images, shadows, paragraphs drawn by handle, paints with gradient shaders; no blend modes yet). Draw modifier nodes record into it in chain order: `DrawModifierNode::draw` before the content (the rest of the chain and the children), `draw_after` after it, in reverse order, which is Compose's `drawContent()` split in two (`background` draws before, `border` after; `clip` is a graphics layer, below). A node draws at the size of the layer its draw node is in, so `padding(8).background(…)` fills inside the padding. A platform `Renderer` replays the list: Skia on desktop, Android's `Canvas` on Android ([07](07-platforms.md)). Tests dump it as text or render it to PNG through Skia's CPU raster backend. The list is assembled whenever anything changed, into a buffer kept from frame to frame (so a warm frame allocates nothing): what's outside every repaint boundary is drawn again, and each boundary's group refers to what it kept, drawn again only if something it drew from changed (below, "Repaint boundaries").

**Paths and vector images.** `Path` is Compose's mutable path (D530): built with `move_to`, `line_to`, `quadratic_to`, `cubic_to`, `arc_to`, their `relative_` forms, `add_rect`, `add_oval`, `add_round_rect` (a `RoundRect`), `add_arc`, `add_path` and `close` (shapes counterclockwise unless given a `PathDirection`, as Compose's), moved with `translate` and `transform` (a `Matrix`), combined with `op` (a `PathOperation`: computed by Skia when it's called on desktop, kept as steps that Android's replayer computes with `android.graphics.Path.op`, D535), emptied with `reset` (keeping its fill type) or `rewind`, with `fill_type`/`set_fill_type`, `get_bounds`, `is_empty` and `is_convex`; or parsed from SVG path data (`Path::from_svg`, arcs converted to curves). It is a shared reference, as Kotlin's (`Rc`; a clone is the same path, `!Send`), so code remembers one (`remember(Path::new)`) and resets it in a drawing block each frame, as Compose code does. Drawing it (`DrawScope::draw_path`, `clip_path`) records its contents as they are then: a `PathData` in an `Arc` (shared, never changed: a change after drawing makes new contents), with the path's identity and a generation each change bumps, in a `DrawPath` op with a scale and offset (an `ImageVector`'s viewport fitted to its size; an `ImageVector` holds `Arc<PathData>`s). A recording keeps the contents it drew: changing a path draws nothing again, as in Compose, and a drawing run again for its own reasons (state it read) draws the path as it is (D531), so a group's key and version name one drawing (D157). On Android a path changed in place is defined again under the id of its old contents once nothing holds them, and the replayer refills the same `android.graphics.Path` (D532). Material's `Icon` draws an `ImageVector`; `icons::filled::add()` and friends are material-icons-core's filled icons.

**Interactions.** `MutableInteractionSource` (as Compose's, with `collectIsPressedAsState`, `collectIsFocusedAsState` and `collectIsHoveredAsState` as `is_pressed`, `is_focused` and `is_hovered`, state reads) is where `Modifier.clickable_with` reports its press, focus and hover, so something else can show them: a navigation item's show on its pill only. A clickable's own indication (`Indication`, as Material's ripple without its animation) is a state layer over its bounds, or an unbounded circle (`Indication::unbounded(color, radius)`, as `ripple(bounded = false, radius)`: checkboxes and radio buttons).

**Custom drawing.** `Modifier.draw_behind(|scope| …)` draws under the content and `Modifier.draw_with_content(|scope| { …; scope.draw_content(); … })` around it, drawing the rest of the node and its children where `draw_content` is called (or not at all), as Compose's; foundation's `Canvas(modifier, |scope| …)` is a node to draw in. Their lambdas are observed: state they read draws again, without recomposing or measuring. `Modifier.draw_with_cache(|cache| cache.on_draw_behind(…))` (or `on_draw_with_content`), as Compose's `drawWithCache`, builds what it draws with (paths, brushes) from the `CacheDrawScope`'s size, and keeps it until the size, density or direction changes or state the build read does: the build runs under an observer of its own (whose write bumps a state the drawing reads, so the node draws again), and what the drawing lambda reads only draws again.

**`DrawScope`.** Besides rectangles, rounded rectangles, lines, paths and images: `draw_circle(center, radius, paint)`, `draw_oval(oval, paint)` (a whole turn of an arc, so no new operation) and `draw_arc_with(…, use_center, paint)` (a pie slice); `center()`; a paint that draws nothing (a transparent color without a shader, as Material's transparent containers) records nothing, as Skia drops it (D251); and the scoped transforms and clips of Compose's `DrawScope` extensions, each restoring after its block: `rotate(degrees, pivot, |scope| …)` and `scale(scale_x, scale_y, pivot, |scope| …)` (a save and a `Transform`), `translate(left, top, |scope| …)` and `inset(left, top, right, bottom, |scope| …)` (moving the scope's origin, and shrinking its size: no operation), `clip_rect(rect, |scope| …)` and `clip_path(&path, |scope| …)` (a `ClipPath` operation). Geometry comes before the paint, as the scope's other calls (Compose's put the color or brush first). `draw_path` takes a `&Path` (its contents now, shared) or a `&Arc<PathData>` (contents that never change). `Paint::with_alpha` multiplies a paint's opacity, as the draw calls' `alpha`.

**Brushes.** `Brush` is Compose's: `Brush::Solid`, `linear_gradient`, `horizontal_gradient`, `vertical_gradient`, `radial_gradient`, `sweep_gradient`, each taking colors or `(stop, color)` pairs (`ColorStops`), the short forms with Compose's defaults and the `_with` forms with the positions and a `TileMode`; positions are in the drawing's coordinates, `Offset::INFINITE`, `Offset::UNSPECIFIED` and an infinite radius standing for its size, center and half its smaller side, as Compose's. `DrawScope::brush_paint(&brush, alpha, style)` resolves it for the scope into a `Shader` the display list keeps (`DisplayList::shaders`) and returns a `Paint` naming it (`Paint::shader()`, an index hosts read; `Paint` stays `Copy`), usable with any draw call; `Modifier.background(brush)` and `background_with(brush, shape)` are Compose's `background(color, shape)` and `background(brush, shape, alpha)` (a color converts to a brush; the alpha is `brush.with_alpha(alpha)`). Each recording (the frame's own, each repaint boundary's kept one) has its own shaders, its paints naming its table's, so a frame refers to a kept recording without re-indexing anything (D270); `flatten` appends them, shifting the indices. Skia paints the gradients (interpolated premultiplied, as Android's HWUI and Skiko's: D210). A brush paint's `color` is the gradient's average, what a renderer without the shader would paint; Android's replayer builds the gradient (D210).

**Arcs and caps.** `DrawScope::draw_arc` (as `drawArc`) draws part of an oval; a stroke's `cap` (`StrokeCap::Butt`, the default as Compose's `Stroke`, `Round` or `Square`) shapes open ends. Material's progress indicators draw with them, their caps `Round` by default as Material 3 1.4's (D320): `CircularProgressIndicator(progress)` and `LinearProgressIndicator(progress)` (40 dp and 240 × 4 dp, as Compose's), and `IndeterminateCircularProgressIndicator` and `IndeterminateLinearProgressIndicator` (Compose's no-progress overloads, named apart since Rust has no overloads), whose keyframed animations are computed from one infinite clock read while drawing, so each frame only draws again (each is a repaint boundary of its own, so what's around it isn't drawn again: D323).

**Snackbars.** `SnackbarHostState::show_snackbar(message)` (or `SnackbarVisuals`; `show_snackbar_with(message, action_label, with_dismiss_action, duration)` with Compose's optional parameters) is a coroutine, as Compose's: snackbars asked for show one at a time, in order; it returns `ActionPerformed` or `Dismissed` (after 4 or 10 seconds, or never for `Indefinite`), and cancelling it takes its snackbar away. `SnackbarHost` shows the current one, faded and scaled in; `Scaffold`'s `snackbar_host` slot places it above the bottom bar and the FAB, centered. The color scheme has Material 3's inverse, container, scrim and bright/dim roles.

**Shadows.** `Modifier.shadow(elevation)` and `shadow_with(elevation, shape, clip, ambient_color, spot_color)` are a graphics layer with that elevation, shape and clip, as Compose's (none without an elevation or a clip; `clip` defaults to an elevation above 0). The layer casts its outline's shadow under its content, even with nothing in it: on Android a render node's elevation, outline and shadow colors, drawn by HWUI in the reordering section (`enableZ`) its parent's recording puts around it, lit by the window's light, as Compose's (D524); on desktop a `DrawShadow` op in the layer's operations, Skia's `ShadowUtils` with Compose Desktop's light (300 dp above the window's top, 600 dp up, 800 dp wide) and alphas (3.9 % ambient, 19 % spot, faded with the layer). Material's `Surface` is Compose's `Modifier.surface`, in its order: a layer casting its `shadow_elevation`'s shadow (not clipping), its border, its color (`tonal_elevation` tints the surface color with the primary color, summed through nested surfaces, as `surfaceColorAtElevation` and `LocalAbsoluteTonalElevation`), then `clip(shape)` around its content (D526). A card is one clipping layer, an elevated card adds its 1 dp shadow's; the FAB has its 6 dp shadow and menus their 3 dp one; a button's or card's elevation follows its press, hover and focus, animated and read in composition as Compose's (`animateElevation`).

**Images.** `ImageBitmap` holds premultiplied RGBA pixels in an `Arc`, made from raw pixels or decoded by the backend (`compose_skia::decode_image`, PNG, JPEG, WebP, …, as the desktop's `decodeToImageBitmap`). `DrawScope::draw_image` records a `DrawImage` op (a source and destination rect and an alpha); Skia makes its image once per bitmap and forgets it the frame after the bitmap is dropped; a source rect is sampled strictly (nothing from outside it bleeds in), and a header claiming more than 2^28 pixels isn't decoded. Foundation's `Image(bitmap, content_description, modifier, alignment, content_scale, alpha)` is its pixels' size within the constraints scaled by its `ContentScale` (as Compose's painter node), draws scaled by a `ContentScale` (`Fit`, `Crop`, `FillBounds`, `FillWidth`, `FillHeight`, `Inside`, `None`) and aligned, clipped to its node, and reads as `Role::Image` with its description.

**Graphics layers.** `Modifier.graphics_layer(|layer| …)` applies `GraphicsLayerScope`'s properties to what follows it in the chain and the children, as `graphicsLayer`: alpha, scale, rotation, translation, a shadow (`shadow_elevation` in pixels, `ambient_shadow_color`, `spot_shadow_color`), a `shape` and whether it `clip`s to it, and a `compositing_strategy` (Compose's names and defaults; the block reads the layer's `size` and `density`). Its block runs while drawing, so the state it reads (an animation's value) changes the drawing without recomposing or measuring. `alpha`, `scale`, `rotate`, `clip`, `clip_to_bounds` and `shadow` are layers, as in Compose (`clip(shape)` is `graphicsLayer(shape = shape, clip = true)`, `alpha(a)` one clipping to its bounds, none at 1; `rotate(0)` and `scale(1)` none, D523). Each layer is a group of the display list (below), as each of Compose's is a layer: when it is its node's first drawing modifier (nothing drawn before it in the chain), its properties are its node's repaint boundary's, as a `RenderNode`'s: its block's reads are observed apart, and a write to them computes the properties again without drawing the layer's content again (no version changes). A layer after a drawing (`background(…).clip(shape)`, a surface's) is an inner layer: a group of its own inside its node's drawing, holding what follows it in the chain and the children, drawn by reference where it is (its key flagged, `render::INNER_LAYER_KEY`); what draws its node draws the drawings before it, and a change inside it (its block's reads, a child's drawing or move, its node's measurement for a state it read) draws it again, not them, and a state read before it draws them again, not it (D522). `CompositingStrategy::Auto` draws an alpha below 1 offscreen (Android: `setHasOverlappingRendering(true)`, HWUI's save layer; desktop: `SaveLayerAlpha`), `Offscreen` always (a compositing layer), `ModulateAlpha` never (each drawing's alpha multiplied: Android's `setHasOverlappingRendering(false)`, desktop's walk fading paints, text and shadows in layers of their own). A clip clips hit testing too, as Compose's layer's `isInLayer`. On Android, a clip to an outline whose corners differ (a path) clips the node's recording to the path on API 29 to 32, where an outline path can't clip, as Compose's `usePathForClip` (D525). The block isn't memoized by the macro (its closure takes a `&mut` scope, which a `Callback` can't hold): remember the modifier for a callee to skip. Hit testing doesn't follow the transform yet. Clips inside a drawing (`DrawScope`'s `clip_rect`, `clip_path`) stay operations of it, as Compose's canvas clips.

**compose-rs's optimizations.** What compose-rs does beyond Compose's rendering is a flag of `Optimizations` (`compose_ui::platform`, one table: `Optimization::ALL`), each with a default: off where it changes what's drawn or how relative to Compose, so a benchmark against Compose measures the same rendering. A host sets them (`UiHost::set_optimizations`; Android's `ComposeRsView.optimizations`, desktop's `WindowOptions::optimizations`, `set_optimizations` or `COMPOSE_OPTIMIZATIONS`), and renderers read them. `single_drawing_fade` (off) fades an `Auto` layer holding one drawing with a paint by that paint instead of offscreen, the same pixels (D153, D157, D521); `performance_hint` (on) is Android's hint session (D390); `reuse_paragraph_at_same_layout_width` (off) keeps a text's paragraph at the same layout width (D551). D520 records the mechanism.

**Repaint boundaries.** A node whose first drawing modifier is a graphics layer is a repaint boundary, as Compose's layer (a `RenderNode` on Android); so is one with `Modifier.repaint_boundary()`, a layer without properties, and every lazy item; an inner layer is a group of its own too (above). What a boundary draws, its children included, is a group of the display list (`DisplayList::groups`), in its own coordinates: a renderer can keep the group's recording while its operations stay the same, so a scrolled item, or one beside an animation, isn't recorded again (Android's replayer does, D154, D157).

Each boundary keeps what it drew, as Compose's layers keep their recordings (D155): a draw records what's outside every boundary, the boundaries in it by reference (`DisplayList::boundaries`: where each is drawn), then lists each boundary's group, nested boundaries included, without running its draw code. A group holds its boundary's recording by reference (`DrawGroup::content`, an `Arc` shared with the boundary, which records into it in place once the frames sharing it are gone), not a copy of its operations (D270): the frame is a tree, the groups listed depth first (`descendants`), which renderers walk. Skia draws a group's content where its boundary is, in a save of its own (an unbalanced clip stays in it, as in a render node); Android's serializer copies a kept group's record without reading its operations. `DisplayList::flatten` copies it all into one list (`FlatDisplayList`, each group a range of its operations), for tests and dumps (`UiHost::display_list` and `dump` give it). A boundary is drawn again only when something it drew from changed: a state read while drawing a node in it (up to the boundaries inside it) is written; a node in it is measured, or moves inside it, or its modifier changes; a child is added or removed; a handler asks (`EventContext::invalidate_draw`: a press, a focus, a selection); the density changes; or `UiTree::invalidate_draw` asks for everything. Moving the boundary itself (a scroll) is its parent's operations and keeps it. State written while laying out (a lazy list's or a scroll's measured state, a hover the layout moved) is applied just before drawing, so it's drawn in the frame that wrote it; a measurement it invalidates waits for the next frame. Data passed from one node's measure to another node's drawing without state (an `Rc<Cell>`) is stale when the writer and the reader are in different boundaries: measuring the writer draws its own boundary again, not the reader's. Material's `TextField` (its label's width and start, for the outline's cut) and `TabRow` (its tabs' positions, for the indicator) keep the writer and the reader in one node. Its group's `version`, from a counter of the tree, changes when it's drawn again or a boundary inside it changed version, so a renderer keeps a recording by key and version without comparing operations. A graphics layer's properties are its group's `layer`, outside its content: Skia applies them as operations around it (`LayerProperties::operations`: `Save`, `Transform`, `ClipRect`, `SaveLayerAlpha`, each if needed, then their restores; a flattened group has them at `layer_start..start` and `end..layer_end`); Android sets them on the group's render node, so a layer-only animation records nothing again (D157). A boundary a frame drew that is composed and no longer placed (a lazy list's item kept beside the wanted ones, D375; any unplaced child left composed) has its group and its nested ones listed apart in each frame while it stays so and none of them changed (`DisplayList::kept`, outer before inner; the 8 most recent), for a platform that asks (`UiHost::set_keep_unplaced_groups`: Android): no boundary draws it, nothing in it runs, and Android keeps its render nodes recorded, so the frame placing it again draws them by reference (D380). One that changed (it or a nested one), or went, is no longer listed: the frame placing it draws it.

## Animation

`compose::animation` is Compose's `animation` and `animation.core`. An `Animatable` holds its value in state and animates it with tasks ([04](04-runtime.md)): `animate_to(target, spec).await` takes a step each frame (`with_frame_nanos`) along a spec, `tween` (duration, delay, easing), `spring` (Compose's damped-spring equations, keeping the velocity across interruptions), `snap`, `keyframes(duration, |frames| { frames.at(time, value).with(easing); })` (as Compose's `keyframes { value at time with easing }`; the spec stays `Copy`, its keyframes interned per thread and shared when equal, D150), `repeatable` or `infinite_repeatable` (of a tween or keyframes), per component of the value's vector (`f32`, `i32`, `Dp`, `Offset`, `IntOffset`, `Size`, and `Color` in Oklab, as Compose's converters). A new animation interrupts the running one, which ends with `AnimationEndReason::Interrupted` where Compose throws a cancellation. `animate_float_as_state(target)` and its siblings follow a target, `remember_infinite_transition()` animates forever (one task per transition sets all its values each frame, as Compose's `InfiniteTransition`; a value starts at the first frame after it enters the composition, and again when its values or spec change, D420), and `AnimatedVisibility(visible, enter = fade_in() + expand_vertically(), …)` animates content in and out, keeping it composed while it leaves; `Crossfade(target_state, …)` fades one state's content into the next's; `AnimatedContent(target_state, …)` has the new state's content enter as the old one's exits (`transition_spec(initial, target)` gives an `enter.together_with(exit)` `ContentTransform`, Compose's default fading and scaling in after 90 ms while the old fades out, the container's size animating, or as large as the largest content without a size transform; contents are measured with the container's constraints; each content keeps the enter and exit of the change that brought it in or took it out), keeping the last three states' contents while they animate; `update_transition(target_state, label)` animates several values together on one state's change (`transition.animate_dp(spec, |state| …)` and friends, each from its value for the state the transition is at), its `current_state` reaching the target once they all end (on an interruption, the state the change was heading for, which is where the next change's spec starts), `is_running` a state read, and a value interrupted mid-way going on along a default spring (unless its spec is a spring), as Compose's `interruptionSpec`; `Modifier.animate_content_size()` animates a node's size to its content's. Animated values are read where they are used: in a graphics layer's block (a redraw) or a layout (a re-measure), not in composition, so a frame recomposes nothing.

## Popups and dialogs

`Popup` and `Dialog` (`compose::ui`, as Compose's `ui.window`) show content over the rest of the window. Compose gives them windows or layers of their own; here they are **overlays**: nodes composed where they are called (so composition locals, state and remembered values follow) whose modifier (`Modifier.overlay(provider, …)`) makes the tree place them in the root after layout, with a position provider (`PopupPositionProvider`: `AlignmentOffsetPositionProvider` for `Popup(alignment, offset)`, a menu's below-or-above provider), from their anchor's bounds and the window's size. The anchor is the layout around the popup inside its modifiers (as `parentLayoutCoordinates`), and popups are measured with the window's size, again when it changes. They are drawn after everything else and hit before it (a point in an overlay is its, handled or not); in semantics they are roots of their own, never merged into what's around their anchor. A popup with `on_dismiss_request` gets an outside catcher under it, dismissing it on a press outside: a focusable popup takes that press (what's beneath gets nothing while it shows), a non-focusable one lets it through, as Android's non-focusable popup windows. A focusable popup is modal for input whatever its dismiss settings, takes the focus, and back (Escape on desktop) dismisses it (`dismiss_on_back_press`), as on Android a popup window that takes focus gets the back key; a non-focusable one doesn't take back. A dialog is modal: its content centered (24 dp from the window's edges) over a scrim that takes every event (a click on it dismisses), taking the focus. While a dialog or focusable popup shows, Tab cycles through its focusables only (the overlay itself isn't a stop), keys stay in it (they never reach the handlers around its host), and with nothing focused they go to it, as a window of its own; back goes to it before what's beneath (D220); opening it scrolls nothing around its host, and once it's gone, what had the focus before gets it back. Non-focusable popups take no focus. `LOCAL_DENSITY` (as `LocalDensity`) gives composition the window's density. Material's `AlertDialog`, `DropdownMenu` and `DropdownMenuItem` are built on them; a menu is as wide as its widest item (112 to 280 dp, asked with `MeasureScope::max_intrinsic_width`), scrolls when taller than the window, and is placed as Compose's `DropdownMenuPositionProvider` (at the anchor's start, else its end, else the window's; below, else above, keeping 48 dp from the window's top and bottom, and always within the window); its `scroll_state` is remembered where it's called, so a reopened menu keeps its scroll.

## Back, saved state and the platform's values

- **Back.** `BackHandler(enabled, on_back)` (`compose::ui`, as AndroidX's `BackHandler`) registers with the host's `OnBackPressedDispatcher` (`LOCAL_ON_BACK_PRESSED_DISPATCHER`) while it's in the composition; a back press goes to the innermost enabled one: those in dialogs and focusable popups first (the deepest first, as their own windows get back before the window beneath), then the one registered last (composed last), as AndroidX's dispatcher (D220). The platform calls `UiHost::on_back_pressed()` (Android's back gesture or button), and Escape that no focused node consumes goes back too (`send_key`), which is how desktop dialogs close on Escape. Where `LOCAL_BACK_HANDLERS_ENABLED` is `false` (a `NavHost` entry fading out), handlers are disabled. `has_enabled_back_handlers()` tells the platform whether to intercept back at all: Android lets the activity finish when no handler is enabled. A `Dialog` and a focusable `Popup` take back while they show (their own always-enabled handler), dismissing only if `dismiss_on_back_press`: back never goes past them. Material's components go through it, so Android's back works as Escape does (D241): an open `ModalNavigationDrawer` closes (its handler is composed after the content's and before the sheet's content, so it goes before the content's handlers and after those in the drawer, as Compose's `DrawerPredictiveBackHandler`); a `ModalBottomSheet` (a focusable popup) goes from expanded to half way, then hides and is dismissed; a `DropdownMenu` (a focusable popup) is dismissed before what's beneath it.
- **Saved state.** `remember_saveable(|| mutable_state_of(0))` (`compose::runtime`, as Compose's `rememberSaveable`) remembers as `remember` does, and registers the value (a remembered `OwnedState`'s value) with the host's `SaveableStateRegistry` (`LOCAL_SAVEABLE_STATE_REGISTRY`) while it's in the composition. `UiHost::save_state()` collects every registered value as a `SavedState` (`to_bytes` encodes it: booleans, integers, floats, strings and lists, what an Android `Bundle` holds); a new host given it (`restore_state`, before its first frame) hands each value back to the `remember_saveable` at the same place, found by `current_composite_key_hash()` (the keys of the groups from the root, as Compose's `currentCompositeKeyHash`: a composable's key, a `key(…)`'s value, a branch's region), values at the same place told apart by their order (D223). Values convert with a `Saver` (`saver(save, restore)` with `remember_saveable_with(saver, init)`); the `Saveable` types (integers, floats, `bool`, `char`, `String`, `Option`, `Vec`, tuples) need none (`AutoSaver`, Compose's `autoSaver`). A value that can't be restored (saved by another version of the app) is computed again. `remember_lazy_list_state`, `remember_lazy_grid_state` and `remember_scroll_state` are saveable, as Compose's; text fields hold no state of their own to save (their value is the app's, which `remember_saveable` keeps, as in Compose).
- **Saveable state holders.** `remember_saveable_state_holder()` (`compose::runtime`, as Compose's `rememberSaveableStateHolder`) keeps the saveable state of content that leaves the composition, by key: `holder.SaveableStateProvider(key, || …)` composes content with a `SaveableStateRegistry` of its own, provided to it; when the content leaves, the holder keeps what that registry saves, and gives it to the content next composed with the key; `holder.remove_state(key)` forgets it (content in the composition then leaves nothing behind). The holder saves what it keeps, and what its content in the composition holds, across the host's recreation. Values in a provider are found by their composite key hash *within* it (the walk stops at the provider's group, unlike Compose's), so content that leaves and comes back under another parent (an animated container's next slot) finds them; content moved within one pass doesn't, as in Compose. Each lazy list item's content is in a provider of its key (Compose's `LazySaveableStateHolder`), so items scrolled away and back keep their `remember_saveable` values, saved with the list across recreation; as in Compose, they're kept for the list's life, so thousands of items with saveable state grow the saved state (an Android `Bundle` holds about 1 MB). A key composed at two places at once panics in debug builds, as Compose throws (D290). A provider is a `ReusableContent(key)`, as Compose's (D430): matched by its place, not its key, so content with another key composed in its place reuses its groups and nodes (its values computed anew); providers in a loop need a `key(…)` each to move with their keys, as in Compose.
- **Navigation.** `compose::navigation` (the `compose-navigation` crate, as Navigation Compose): `remember_nav_controller(start_destination)` is a `NavController<D>` (a `Copy` handle) whose back stack holds entries (`NavBackStackEntry`: an id and a destination) of the app's destination type `D` (an enum, `Saveable` so the stack is saved), and `NavHost!(nav_controller, |destination: D| match destination { … })` composes the top entry in a `SaveableStateProvider` keyed by its id (random, so unique across controllers and processes), removing the states of entries gone from the stack (the ids it last saw are saved, so a stack that couldn't be restored leaves nothing behind), with a `BackHandler` popping while there's an entry under the top; an entry fading out has its back handlers disabled. Navigating writes state: from handlers and effects, not composition. `navigate`, `navigate_with(destination, NavOptions { pop_up_to, pop_up_to_inclusive, launch_single_top })`, `pop_back_stack`, `pop_back_stack_to`; `current_destination()` and the stack are state reads. `enter_transition` and `exit_transition` animate the change through `AnimatedContent` (none by default). Material's `remember_drawer_state` and `remember_top_app_bar_state` are saveable, as Compose's, so a screen comes back with its drawer and bar as they were (D291, D293).
- **The configuration.** `LOCAL_CONFIGURATION` (`Configuration`: the screen's width and height in dp, its orientation, the font scale, the density, and night mode: the parts of Android's `Configuration` apps read) is the host's (`UiHost::set_configuration`); foundation's `is_system_in_dark_theme()` reads its night mode, so `MaterialTheme!(color_scheme = if is_system_in_dark_theme() { dark_color_scheme() } else { light_color_scheme() }, …)` follows the system, as the gallery and feed examples do (D225).
- **Window insets.** The host's insets (`UiHost::set_window_insets`: status bars, navigation bars, caption bar, keyboard, display cutout, in pixels; zero on desktop) are what foundation's `WindowInsets` (`system_bars()`, `status_bars()`, `navigation_bars()`, `caption_bar()`, `ime()`, `display_cutout()`, `safe_drawing()`, with `union` and `only(WindowInsetsSides::…)`) resolve to. `Modifier.window_insets_padding(insets)` and its shorthands (`system_bars_padding`, `status_bars_padding`, `navigation_bars_padding`, `ime_padding`, `display_cutout_padding`, `safe_drawing_padding`, from `WindowInsetsModifiers`) read them while measuring (a change measures them again; nothing recomposes); `insets.as_padding_values()` reads them in composition (`LOCAL_PLATFORM_WINDOW_INSETS`). They don't consume what they pad: nested paddings of the same insets add up (D222).
- **Images.** `decode_image_bytes(bytes)` decodes an encoded image with the platform's `ImageDecoder` (Skia's codecs on desktop, `BitmapFactory` on Android; the host sets it with `set_image_decoder`), and `remember_image_resource(include_bytes!("icon.png"))` decodes a bundled one once where it's composed, as `ImageBitmap.imageResource` (named `remember_…` so the composable transform sees the slots it takes, D224).
- **Properties and events.** An app embedded in a platform UI reads the properties the platform passes (`LOCAL_HOST_PROPS`: `props.string("tab")`, `number`, `boolean`; read in composition, a change recomposes the reader) and sends it events (`LOCAL_HOST_EVENTS.current().send(name, payload)`); the host's side is `UiHost::props().set(…)` and `set_event_listener` (D226).
- **Platform services.** As Compose's, content reaches the platform's services through composition locals (`compose::ui`): `LOCAL_URI_HANDLER.current().open_uri("https://…")` (`UriHandler`: Android starts an `ACTION_VIEW` intent, desktop asks the OS: `open`, `xdg-open`, Windows' URL handler; headless, it logs the link; the platform's is a `PlatformUriHandler`, which opens only well-formed URIs of `http`, `https`, `mailto` and `tel`, see below), `LOCAL_CLIPBOARD_MANAGER.current()` (`ClipboardManager`: `get_text`, `set_text`, `has_text`, plain text; the same clipboard text fields and `SelectionContainer` use) and `LOCAL_HAPTIC_FEEDBACK.current().perform_haptic_feedback(HapticFeedbackType::LongPress)` (`HapticFeedback`: Android's `View.performHapticFeedback`, nothing on desktop). The values are `Rc<dyn …>`; the host sets the platform's on its tree before composing (`UiTree::set_uri_handler`, `set_clipboard`, `set_haptic_feedback`), and the locals' defaults read the composing tree's (as `LOCAL_FOCUS_MANAGER`), so a test or a subtree provides a fake with `CompositionLocalProvider(LOCAL_URI_HANDLER.provides(Rc::new(Fake)), …)`. **Links are checked** (D283): `PlatformUriHandler` refuses, with a warning naming only the scheme and host, a URI whose scheme isn't allowed (`DEFAULT_URI_SCHEMES`; `file:`, `search-ms:` and the like could launch programs through the OS's opener), a scheme of one letter (a Windows drive path), and whitespace, control characters, quotes or backslashes. A subtree widens it with `PlatformUriHandler::current().with_schemes(&["https", "myapp"])`, provided as `LOCAL_URI_HANDLER`; `compose::ui::check_uri` is the check. A URI from an untrusted source (a server, a message) should still be validated by the app: an allowed scheme can lead anywhere. `combined_clickable`'s long click performs `LongPress` feedback, as Compose's (`hapticFeedbackEnabled`'s default; the feedback is the local's where the modifier is made in composition). There are no touch selection handles yet, so nothing performs `TextHandleMove` (D281).
- **Calling the app's own Kotlin.** There is no `LOCAL_CONTEXT`: an app embedded in an Android UI calls its own Kotlin (share a text, start an activity, ask for a permission) through host events, and hears back through properties (D226, D282). The content sends `LOCAL_HOST_EVENTS.current().send("share", &text)` from a callback; Kotlin's listener runs it with the activity at hand, posted after the call into Rust returns, and answers with `view.setProp("permission", true)`, which recomposes whoever reads `LOCAL_HOST_PROPS.current().boolean("permission")`:

  ```kotlin
  view.setOnEventListener { name, payload ->
      when (name) {
          "share" -> startActivity(Intent.createChooser(
              Intent(Intent.ACTION_SEND).setType("text/plain").putExtra(Intent.EXTRA_TEXT, payload), null))
          "ask_camera" -> cameraPermission.launch(Manifest.permission.CAMERA) // its result: view.setProp(…)
      }
  }
  ```

  On desktop the same events reach `UiHost::set_event_listener`, so the app's Rust can do the platform's part there.
- **Logging.** compose-rs logs through the `log` crate (re-exported as `compose::log`), and apps may too: `compose::log::info!("loaded {} items", items.len())`, `warn!`, `debug!`. Android's host installs a logcat logger (`__android_log_write`, tagged with the logging crate's name: `adb logcat -s my_app compose_runtime`), desktop's (`application`, `run_app`) and the test rule a stderr one (`compose::ui::platform::install_stderr_logger`), each at `debug` in debug builds and `info` in release ones, unless the app set a logger of its own first (`env_logger`, say, before `run_app`). On desktop and in tests `COMPOSE_LOG` filters, as `RUST_LOG` does: `COMPOSE_LOG=warn,my_app=debug,compose_runtime::state=off` (`LogFilter`; an invalid value is warned about once and ignored). On Android the logger is installed by `JNI_OnLoad`, before any of the app's code; `export_apps! { logger = false; "main" => App }` leaves it to the app (`android_logger`, in a `JNI_OnLoad` of its own calling `compose_android::on_load_with`). The runtime's debug warnings (a stale handle's, D240) go through it (D280).

## Input, focus and semantics

- **Pointer input.** A pointer event hit-tests through the node tree as Compose does: each pointer-input node is hit inside its own layer's bounds, a node's bounds don't limit what's hit inside it (an `offset`'s content, children placed outside), a `clip` does (to its outline), and at each level the topmost child with a hit wins. It collects the pointer-input modifier nodes under it, outermost first. It is dispatched in Compose's three passes: `Initial` down the path, `Main` up from the target, `Final` down again, and a handler consuming it hides it from those after. A press captures the path: the pointer's moves and release go to the same nodes. `clickable` follows Compose's tap detection: it clicks on a release inside, and moving out, a release outside or another handler consuming the events cancels. `toggleable` builds on it.
- **Handlers run after dispatch.** Application callbacks a node triggers (`on_click`, `on_value_change`) are queued as actions and run once the tree is free, so they can do anything a callback may. `on_key_event` handlers run during dispatch, since their result decides where the event goes: they may write state but not reach the tree.
- **Focus.** One node has focus. A focus target is a modifier node (`focusable`, and `clickable`, which is focusable when enabled, as on desktop Compose). Tab and Shift-Tab move through the focus targets in tree order, wrapping around (Compose's one-dimensional focus search), stepping over those outside a clipping container's bounds (a lazy list's items beyond its viewport) unless the focus is already inside it, and Enter or Space clicks a focused clickable. `FocusRequester` (`remember(FocusRequester::new)`, attached with `Modifier.focus_requester`; a `Copy` id, D240) moves focus from application code, as Compose's: `request_focus()` from a callback or an effect focuses its node's focus target, or the first below it, once the tree is free (after the event, or at the next frame); a requester on several nodes focuses the first attached. `LOCAL_FOCUS_MANAGER.current()` (as `LocalFocusManager`) is the tree's `FocusManager`: `clear_focus(force)` clears the focus (nothing captures it here, so `force` changes nothing), and `move_focus(direction)` moves it, `FocusDirection::Next` and `Previous` through Tab's order, `Up`, `Down`, `Left` and `Right` to the nearest focusable that way (Compose's two-dimensional search over the focus targets' own rectangles, as `focusRect()`, after what's before them in the chain: a candidate in the focused node's beam beats one out of it, else the nearest by `13 × major² + minor²`; with nothing focused, from the window's top-left or bottom-right corner). It acts once the tree is free, as `FocusRequester`, and returns whether a tree was there to ask (Compose returns whether the focus moved). The local's value is the composing tree's (read from the composition's applier), so no host provides it (D230). `on_focus_changed` reports whether the focus target after it in the chain, or a node below, has focus (Compose's `FocusState.hasFocus`), once when it attaches and then on every change. A focus target that is removed or can no longer take focus (disabled) loses it, and is told. Key events go to every key input node of the focused node, those after its focus target included, as Compose's `lastLocalKeyInputNode`.
- **Keyboard and text.** Key events go to the focused node's key input nodes, from its focus target outward, then to its ancestors', until one consumes them; committed text follows the same path. `BasicTextField` is value-based, as Compose's `BasicTextField(value, onValueChange)` (D96): it consumes the keys that type text (down and up, so an ancestor's single-key shortcuts and a clickable row's Space don't take them), edits by grapheme clusters, and follows Compose Desktop's key mappings: arrows (visually in right-to-left text), Up and Down by visual line keeping the horizontal position, words with Option (macOS) or Ctrl, line ends with Cmd on macOS and Home/End, the text's ends with Cmd+Up/Down or Ctrl+Home/End, word and line deletion, select all, copy, cut and paste through the platform's clipboard, and undo and redo (Cmd/Ctrl+Z, Shift+Cmd/Ctrl+Z, Ctrl+Y; typing within 5 s is one step). A plain Tab types a tab in a multi-line field; Shift+Tab moves focus. On macOS, Ctrl moves and deletes as Cocoa's Emacs-style bindings (Ctrl+A, E, B, F, P, N, D, H, K). The pointer places the cursor and drags a selection; a double-click selects a word and a triple-click a line, and a drag after them extends by words or lines (there is no Shift+click yet: pointer events carry no modifiers). An input method's composition shows in place of the selection, underlined, until committed; keys are the input method's meanwhile (but Tab), and a click or a focus change commits it, asking the platform to reset its input method so it isn't committed twice. Losing focus collapses the selection to its end. A single-line field scrolls horizontally, a multi-line one vertically, to keep the cursor in view, and text that overflows is clipped, as Compose's. `SelectionContainer(content)` makes the texts in it selectable, as Compose's: a press and drag selects from where it went down to the pointer across the texts in order (placement order below the container), a double-click a word, a triple-click a text (a drag after them extending by words or texts); Cmd+A (Ctrl+A) selects all and Cmd+C (Ctrl+C) copies, joined by new lines; a click elsewhere in it or its losing focus clears the selection; `DisableSelection` leaves texts out. The texts are `Selectable` modifier nodes the tree finds below the container when a gesture asks, as it finds focus targets (D151); the selection's ends name their texts, so it stays on them as others come and go, and is dropped when a text it ends in changes or leaves. A press in a nested container is that container's. `keyboard_options` (`KeyboardOptions { capitalization, auto_correct_enabled, keyboard_type, ime_action }`, with `KeyboardCapitalization`, `KeyboardType` and `ImeAction` in `compose_ui::text_input`, as Compose's `ui.text.input`) and `keyboard_actions` (`KeyboardActions::new().on_done(…)`) are Compose's. The focused field gives its options to the host as `ImeOptions` (`KeyboardOptions::to_ime_options(single_line)`), for an on-screen keyboard. Enter in a single-line field, or the input method's action key (`UiHost::perform_ime_action`, any action the keyboard showed, a single line's `Default` being `Done` as on Android), performs the field's action for it; without one, as Compose's default actions, `Next` and `Previous` move the focus and `Done` hides the on-screen keyboard; `Default` on desktop does nothing. `LOCAL_SOFTWARE_KEYBOARD_CONTROLLER.current()` (as `LocalSoftwareKeyboardController`, `None` only outside a `UiTree`'s composition) shows or hides the on-screen keyboard (`show()`, `hide()`; `EventContext::show_software_keyboard` and `hide_software_keyboard` from a handler). A tap on a focused, editable field (on its text or its decoration) asks to show it again, as Compose's `tapToFocus`, so a keyboard `Done` hid comes back; desktop ignores the request. A multi-line field is between `min_lines` and `max_lines` lines high (as `heightInLines`: the heights of one and two lines of "H" in its style give the first line's and each next one's), its text scrolling within; a single line is one line high. `visual_transformation` (`impl Into<VisualTransformation>`, so a `PasswordVisualTransformation` needs no `.into()`, D232) changes how the text shows without changing it, as Compose's `VisualTransformation` with an `OffsetMapping` (byte offsets here): `PasswordVisualTransformation` masks each character with •, its semantics say `password` with the masked text, and it can't be copied or cut. Its `decoration_box` lays out what surrounds the text (Material's container, label and placeholder) and calls `inner_text_field` where the text goes; the field's modifier, semantics node and taps are the decoration's, as `CoreTextField`'s (D102).
- **Semantics.** Semantics modifier nodes build a semantics tree, merged or unmerged as in Compose: a node merging its descendants (`clickable` does) takes their text and state and hides them, unless they merge themselves. Tests find nodes through it (`on_node_with_text`, as Compose testing does), and it feeds AccessKit on desktop, for screen readers. A node's own modifiers apply from the innermost to the outermost, so an outer one's values win, lists (text, content descriptions) included (as `collapsedSemantics` and `set`); a role never merges up into a parent. A dialog's content sits in a node of its own, as large as it, marked `is_dialog`. `Modifier.clear_and_set_semantics` (as `clearAndSetSemantics`) hides what's inside a node (an icon next to its label). Semantics actions (`SemanticsAction::OnClick`, `RequestFocus`, `SetProgress`, as `SemanticsActions`) are what screen readers and `perform_semantics_action` ask of a node instead of input: `clickable` and `toggleable` click, a node that's focusable (its own focus target, or a part's: a text field's inner field) takes the focus, and a slider (its own merged node, with its `ProgressBarRangeInfo`) moves to a value snapped to its steps. A dialog's node is marked `is_dialog`.

## The host

`UiHost` (in `compose::ui::platform`, D260) is a composition of a `UiTree` in a root of a given size and density, with its text measurer: the core every platform host wraps, and what tests drive headless. `frame()` recomposes invalid scopes, then measures and draws what changed; `send_pointer`, `send_key` and `send_text` dispatch events and run their actions; `needs_frame()` says whether a frame would do anything, and a waker tells the platform when state changes. It owns what the platform gives content: the back dispatcher, the saveable state registry, the configuration, the window insets, the properties and the event listener (above). Between frames, `has_prefetch_work()` says whether lazy lists wait for idle time, and `prefetch(deadline)` gives them the time until `deadline` (the next frame's start; `prefetch_with(deadline, true)` gives the first request no deadline, Compose's idle frame); it does nothing while a frame has work (`has_pending_work`: state changed, a scroll), asks for no frame itself (what it composes isn't placed, what it disposes wasn't), unless measuring wrote state for others, and returns whether work is left. After it, with `DRAW_PREFETCHED_AHEAD`, `has_draw_ahead_work()` and `draw_ahead()` draw the items it measured, one at a time, and `cancel_draw_ahead()` gives them up (above). `compose-test` builds Compose's test rule on it ([09](09-testing.md)).

What a platform with an on-screen keyboard reads from it (D234): `text_input_area()` is `Some` while a focused node takes text (its cursor, where a candidate window goes); `text_input_options()` gives that field's `ImeOptions` (keyboard type, action key, capitalization, auto-correction, single line), read when the field takes the focus to configure the keyboard (Android's `EditorInfo` in `onCreateInputConnection`: input type and IME options); `perform_ime_action(action)` is the keyboard's action key (Android's `performEditorAction`); `take_software_keyboard_request()` returns what the content last asked (`Some(true)` to show the keyboard for the focused field, `Some(false)` to hide it), taken after each frame and event, the asking having woken the host; `take_input_method_reset()` says a field committed its composition itself. Desktop reads the area and the reset; Android reads them all (its `EditorInfo`, `performEditorAction`, `showSoftInput`/`hideSoftInputFromWindow`, D250).

**What apps use, what hosts use (D260).** Each module's top level is the app-facing surface. The plumbing hosts and the toolkit's crates use sits in a `platform` module beside it, outside semver: `compose::runtime::platform` (the `Composer` and `current`, `Applier`, `NodeRef` and `NodeTree`, the executor's driving functions (`run_ready`, `poll_now`, `fire_timers`, `dispatch_frame`, `set_wake_handler`, the manual clock), `ReadObserver`, `flush_derived_states`, and the counting hooks `bodies_run`, `track_recompositions`, `recomposition_counts`, `live_state_count`) and `compose::ui::platform` (`UiHost`, `UiTree`, `LayoutNode`, `NodeId`, `DisplayList`, `DrawOp`, `Renderer`, `TextMeasurer` and its paragraph types, `FixedTextMeasurer`, `ImageDecoder`, `SemanticsNode`, the platform's window insets, `trace`). Apps' tests reach the counting hooks through `compose::test`. The built-in modifier representation and foundation's text nodes are private.

**Types that grow.** Enums Compose keeps extending are `#[non_exhaustive]`: `Role`, `Key`, `SemanticsAction`, `ImeAction`, `KeyboardType`, `KeyboardCapitalization`, `PointerType`, `PointerEventType`, `PointerIcon`, `TextAlign`, `TextOverflow`, `AnimationSpec`; a match on them needs a `_` arm (`DrawOp`, a platform type outside semver, isn't, so the hosts match it exhaustively). `Paint` is `#[non_exhaustive]` too (built with `Paint::fill` and `Paint::stroke`). Structs that stand for a Compose constructor with all-optional parameters keep public fields and are built with struct update from their default, which is the supported way: `TextStyle { font_size: 20.sp(), ..TextStyle::DEFAULT }`, `KeyboardOptions { ime_action: ImeAction::Done, ..KeyboardOptions::DEFAULT }`, `ButtonColors { container_color: Color::RED, ..ButtonDefaults::button_colors() }`; a field added later is a minor change for code written so (a literal naming every field, or a pattern without `..`, is not supported).

Parameter names, order and defaults follow Compose, in snake_case. Deviations Rust forces, documented per composable:
- text parameters take `impl Into<SharedString>` (a `#[format]` one, as `Text`'s, converts whatever it is given): a `&'static str` (kept as is), a `String` or `&String` (copied into an `Rc<str>`), an `Rc<str>`, `&Rc<str>` or `&SharedString` (shared). A borrowed `&str` converts through `to_string()`: `From<&'a str>` would conflict with the literals' conversion, which allocates nothing;
- scopes are explicit tokens;
- there are no overloads (D263): overloads that differ by an argument's type are one function taking `impl Into<T>` where a type fits (`padding(impl Into<PaddingValues>)` takes `8.dp()`, `(16.dp(), 8.dp())`, `(start, top, end, bottom)` or `PaddingValues { start: 8.dp(), ..PaddingValues::ZERO }`; `size` and `required_size` take a `Dp` or `(width, height)` as a `DpSize`; `background` a `Color` or a `Brush`; the gradients `&[Color]` or `&[(f32, Color)]` as `ColorStops`), or else a trait their argument implements (`Arrangement::spaced_by`, `Arrangement::aligned`, `RoundedCornerShape`), a tuple standing for several arguments. Overloads that only add Compose's optional parameters keep the Compose name for the short form (Compose's required parameters), and `<name>_with` takes the rest, the one variant suffix (`fill_max_width_with(fraction)`, `weight_with(scope, weight, fill)`, `background_with(brush, shape)`, `border_with(width, color, shape)`, `shadow_with`, `semantics_with(merge_descendants, properties)`, `focusable_with(enabled)`, `hoverable_with`, `aspect_ratio_with`, `wrap_content_*_with`, `fill_parent_max_*_with`, the gradients' `_with`, `Paint::stroke_with`, `spring_with`, `fade_in_with`, `mutable_state_of_with`, `remember_saveable_with`): positionally in Compose's order, or, for the clickable family (`clickable_with`, `toggleable_with`, `selectable_with`, `combined_clickable_with`), a `ClickableOptions` built by struct update from `ClickableOptions::DEFAULT`. `_keyed` marks the overloads taking Compose's `key`s (`remember_keyed`, `items_keyed`). A function whose parameters are all optional in Compose takes them all, with no `_with` (`offset(x, y)`, `default_min_size(min_width, min_height)`).
