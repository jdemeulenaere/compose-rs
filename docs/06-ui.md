# 6. UI (`compose-ui`, `compose-foundation`, `compose-material3`)

This follows Compose UI's structure: layout nodes with chains of `Modifier.Node`s, a public `Layout` primitive that `Column` and `Row` are written on, measure and place with constraints, and a draw pass. Text is measured and drawn by each platform's own stack, as in Compose.

## Nodes

- **`LayoutNode`**: one per UI element, owned by the `UiTree` arena behind `Copy` generational `NodeId`s. A node holds:
  - its `MeasurePolicy` (an `Rc<dyn MeasurePolicy>`, compared by pointer);
  - its modifier, and the chain of modifier nodes built from it;
  - its children;
  - its measurement: one *layer* per layout modifier, outermost first, then its own content, each with a size and an offset in the layer outside it (Compose's node coordinators).
- **`UiTree`** is the composition's applier (the `UiApplier` of earlier drafts): it implements the runtime's `Applier` for `LayoutNode`s (insert, move, remove, and release at the end of the pass, rule R1), and runs measurement, drawing, input, focus and semantics. Composables update their node's policy and modifier through `with_applier`. It never runs application code while the runtime holds its state.

## Modifiers: `Modifier.Node`, no `composed`

A `Modifier` is an **ordered chain of elements**. Call order matters, exactly as in Compose: `Modifier.padding(8.dp()).background(Color::RED)` differs from the reverse.

```rust
pub struct Modifier { elements: SmallVec<[Element; 6]> }     // Clone; ComposeArg (element-wise)

enum Element {                         // private: the built-ins, no allocation (D260)
    Padding(PaddingValues), Size(SizeSpec), FillMax(Axis, f32), Background(Color, Shape),
    Border(Dp, Color, Shape), Clickable(ClickableSpec), Toggleable(ToggleableSpec),
    Weight(f32, bool), Align(Alignment), Semantics(SemanticsSpec), …,
    Custom(Rc<dyn AnyModifierNodeElement>),                  // user-defined modifiers
}

pub trait ModifierNodeElement: 'static {   // as Compose's ModifierNodeElement<N>
    type Node: ModifierNode;
    fn create(&self) -> Self::Node;
    fn update(&self, node: &mut Self::Node);  // in place: node state survives
    fn same(&self, other: &Self) -> bool;     // Compose's equals
    fn inspectable_properties(&self, info: &mut InspectorInfo) { … }  // for dumps
}
// AnyModifierNodeElement: its object-safe form, implemented for every element (the one
// downcast is in that blanket impl).

pub trait ModifierNode: Any {   // optional capabilities, as Compose's Modifier.Node delegates
    fn as_layout(&mut self) -> Option<&mut dyn LayoutModifierNode> { None }
    fn as_draw(&mut self) -> Option<&mut dyn DrawModifierNode> { None }
    fn as_pointer_input(&mut self) -> Option<&mut dyn PointerInputModifierNode> { None }
    fn as_semantics(&mut self) -> Option<&mut dyn SemanticsModifierNode> { None }
    fn as_focus_target(&mut self) -> Option<&mut dyn FocusTargetModifierNode> { None }
    fn as_key_input(&mut self) -> Option<&mut dyn KeyInputModifierNode> { None }
    fn should_auto_invalidate(&self) -> bool { true }       // as Compose's shouldAutoInvalidate
    // The lifecycle, as Modifier.Node's: each callback gets its NodeContext.
    fn on_attach(&mut self, cx: &mut NodeContext) {}
    fn on_detach(&mut self, cx: &mut NodeContext) {}
    fn on_reset(&mut self, cx: &mut NodeContext) {}
    fn on_density_change(&mut self, cx: &mut NodeContext) {}
    fn on_layout_direction_change(&mut self, cx: &mut NodeContext) {}
    fn on_release(&mut self, cx: &mut ReleaseContext) {}     // dropped: give back paragraphs
}
```

- **The chain** is a vector of entries, as Compose's `NodeChain`: each holds its node, its *kinds* (`NodeKinds`, Compose's `NodeKind` masks: layout, draw, semantics, pointer input, focus target, key input, position-aware, …, and compose-rs's own: observed, graphics layer, overlay, focus requester, selectable, repaint boundary), its *aggregate* (its kinds and those of every entry after it) and a stable `EntryId`. Kinds are probed once, when the node is created; walks test bits (the node's aggregate first, so a chain without the kind is skipped whole) instead of asking each node or downcasting it (D1150).
- **Diffing** happens on recomposition. When the kinds are the same, in the same order (the usual case: a value changed), each element updates its node in place, allocating nothing. Otherwise old and new elements are matched by kind in order (a longest common subsequence, as Compose's chain diff): matched ones update their node in place, so `clickable`'s pressed state and a text field's focus survive elements added or removed around them; the others' nodes are created or detached. A pointer gesture in progress follows its node to its new place in the chain.
- **Auto-invalidation by kinds**, as Compose's (`NodeKind.kt`): a chain change invalidates what its updated, inserted and removed nodes' kinds say, nothing more. A layout node measures its layout node again (which draws it), a draw node (a graphics layer too) draws it again, a parent data change measures the parent, an overlay lays out again (the layout positions overlays); a semantics node's change is told in the frame's stats (`FrameStats::semantics_changed`, which both platforms' accessibility read, D1158), a pointer node come or gone (not one only updated) has the resting mouse's hover refreshed, as a layout does (D1159), and focus is revalidated by the chain change. So a `background` colour change, or an `animate*AsState` driving one, draws without measuring, and a new `clickable` callback invalidates nothing. A node whose `should_auto_invalidate` says no invalidates itself (D1152).
- **The lifecycle**, as Compose's `Modifier.Node` (D1153): a node is attached while its layout node is in the tree and active (`NodeContext::is_attached`). compose-rs applies changes as composition goes, where application code can't write state (D434), so the callbacks are queued and run when the pass ends (`on_end_changes`, lifecycle.rs), in Compose's orders: a subtree attached in the pass is marked attached first, then its `on_attach`s run children before parents, head to tail in a chain (`LayoutNode.attach`); a subtree removed has its `on_detach`s run parents first, tail to head, every node still attached, then marked detached (`LayoutNode.detach`; a subtree released before the pass's end is detached then); a chain change attaches its new nodes and detaches its removed ones (then releases them); a reused node is reset, detached and attached again, a deactivated one reset and detached (`resetModifierState`); only attached nodes are reset, as Compose's, so a node reused from the kept pool isn't reset again, and a node showing its value (a switch) shows the new one from its `on_attach` (D1156). The reset runs after the new content's `update`, where Compose's runs before (D434: documented on `ModifierNode::on_reset`). The nodes' side effects (`NodeContext::side_effect`) run as soon as the host has released the tree after the composition pass (each round's, and the prefetch's), before the frame's layout, as Compose's `onEndApplyChanges`; one asked outside a pass asks for a frame (D1161). A node a paused composition's resume reuses is reset and detached as the resume ends, and attached again once that composition is applied or discarded (`Applier::on_paused_end`), so it shows its new content's value once that content is complete (D1162). Nodes a chain change removed are detached and released before their layout node, if the pass releases it too. Detaching cancels the node's coroutine scope (`NodeContext::coroutine_scope`, made on first use). A density change (the host's) and a layout node's layout direction change are told to its attached nodes (`on_density_change`, `on_layout_direction_change`). `on_release` is compose-rs's: a node dropped for good (its layout node released, or removed from its chain) gives back what it holds outside itself after its `on_detach`, so a node detached for reuse keeps its caches (D431's reason for keeping nodes).
- **Contexts and handles** (D1154): a callback's `NodeContext` reaches the node's tree (its density and layout direction, the text measurer) and invalidates as Compose's node functions do (`invalidate_draw`: the group it draws in, an inner layer's or its node's; `invalidate_measurement`, `invalidate_placement`, `invalidate_layer`, `invalidate_semantics`, `invalidate_parent_data`, `invalidate_subtree`, `invalidate_measurement_for_subtree`, `invalidate_draw_for_subtree`), nothing once detached. `remeasure_sync` measures its layout node now with its last constraints, as `remeasureSync`, where the tree is free (a task's `with_node`, a callback at a frame's start: once the callback returns, the node back in its chain), else in the layout that follows; `remeasurement()` gives the node's `Remeasurement` (`force_remeasure`, as Compose's: synchronous when the tree is free, between frames or from a task; from inside a pass or a handler, measured in the next layout), which `Modifier.remeasurement_modifier` hands a `RemeasurementModifier` when it's attached (D1165). A new size measures the parent in the next layout. `DrawModifierNode::on_measure_result_changed` tells a draw node that the layer it draws in was measured at a new size (D1166). `NodeContext::handle()` gives a `NodeHandle`, `Copy` and `'static`, for a task, a callback or a closure: its invalidations are queued on the tree's requests and applied at a frame's start, at the end of a composition pass and before each layout, so one asked before a frame's layout is in that frame; `is_attached` answers from a set the tree keeps of the attached nodes that made handles; `coroutine_scope` gives the node's scope where it has no context (an event handler, an element's update), made on first use, `None` once detached (D1061); `with_node` runs code with the node and its context when the tree is free (a task between frames, a side effect), through the host's composition (`Composition::applier_ref`), and answers `None` when it's busy (a pass, a callback, a handler). Each tree is in a thread-local registry under a key, as `FocusRequester`s are (D240).
- **Delegation**, as Compose's `DelegatingNode` (D1169, D1170): a node made of several owns a `Delegates`, returns it from `ModifierNode::delegates`, and delegates from anywhere its code runs (`delegate(node)` in an element's `create` or `update`, `delegate_attached(node, context)` in a callback, attached inside the call; each gives a typed `Delegate<N>`, which `get`, `get_mut` and `undelegate` take). Each delegate has its own kinds, lifecycle, context and handle, and works where its owner does; the owner has their kinds. A kind goes to the node if it implements it, else to each delegate of that kind, in delegation order, as `dispatchForKind`. The tree brings itself up to date once the node's code returns: what was delegated is attached and invalidated by its kinds, what was undelegated detached, invalidated and released, and a layout delegate come or gone makes or drops a layer. compose-rs's extras reach delegates too (`is_repaint_boundary`, `is_beyond_bounds_layout`, `hit_clip`, `bring_into_view`, `as_selectable`: D1194). An element's `update` has no context: what it leaves to do with one it asks for with `Delegates::ask_for_context`, and `on_update_with_context` runs when the pass's lifecycle does (D1193).
- **Composition locals in nodes**, as Compose's `CompositionLocalConsumerModifierNode` (D1182): a node reads a local where its layout node is composed, `NodeContext::current_value_of(&LOCAL)` in a callback (its `on_detach` too, D1189), the same on `MeasureScope` and `DrawScope`; a dynamic local's read is observed as a state's. A node saying `is_composition_local_consumer` is invalidated by its kinds when what's provided where it is changes, and not by a provider elsewhere (D1190). Each layout node takes its density, layout direction and view configuration from the locals where it's composed (D1183), so a subtree may provide its own.
- **Modifier locals**, as Compose's (D1185): a static `ModifierLocal<T>` a node provides from its `ModifierLocalMap` (`ModifierLocalModifierNode::provided_values`) to the nodes after it in its chain and below it; `NodeContext::modifier_local_current` reads the nearest, else the default. `Modifier.modifier_local_provider` and `modifier_local_consumer` are the elements, a consumer running again when what it read changes.
- **Traversal**, as Compose's `TraversableNode` (D1171, D1172): a node finds related nodes through its `NodeContext`, by a `&'static TraverseKey` (`find_nearest_ancestor_with_key`, `traverse_ancestors_with_key`, `traverse_children_with_key`, `traverse_descendants_with_key`) or by type and its own key (the same without the suffix). The walks go through chains and layout nodes, pruned by kinds, pass over what isn't attached, stop at popups, and give each node found its own context. A running node's entry is out of its chain: it's never found. Event handlers have all of this: an `EventContext` wraps a `NodeContext` (D1175); a node measuring or drawing observes reads through its handle (`NodeHandle::observe_reads`).
- **Observer nodes**, as Compose's `ObserverModifierNode` (D1167): `NodeContext::observe_reads(block)` observes what `block` reads, and once a write changes one of those, the node's `on_observed_reads_changed` (through `ModifierNode::as_observer`) is called once, where the tree applies its nodes' requests (a frame's start, each layout round), if the node is attached then; it observes again to keep observing (each observation replaces the last). A node may observe while detached (content kept for reuse): it hears a change that comes once it's attached again.
- **The built-in modifiers are methods of `Modifier`** in `compose-ui` (`padding`, `size`, `width_in`, `height_in`, `fill_max_width`, `offset`, `weight`, `align`, `z_index`, `background`, `border`, `clip`, `clip_to_bounds`, `clickable`, `toggleable`, `selectable`, `selectable_group`, `focusable`, `on_focus_changed`, `on_key_event`, `test_tag`, `semantics`), with their nodes; a few are custom elements of `compose-ui` (`aspect_ratio`, `wrap_content_width`/`height`/`size`, `default_min_size`, `layout`, `on_size_changed`, `on_globally_positioned`, `combined_clickable`, `hoverable`, `draw_behind`, …). Rust has no extension functions, so an inherent method is what lets `Modifier.padding(…)` work with nothing imported; `compose::foundation` re-exports them where Compose has them. The scope tokens (`RowScope`, `ColumnScope`, `BoxScope`) live there too, with hidden constructors for the layouts that make them.
- **No `Modifier.composed`.** Elements are plain data. State a modifier needs (pressed, hovered, focused, later ripples) lives in its `ModifierNode`, owned by the `LayoutNode`, never in composition slots, and no modifier composes or `remember`s.
- **Handlers** live inside elements as `Callback`s (`Rc<dyn Fn>`). A closure argument in a modifier chain rooted at `Modifier` (`Modifier.clickable(move || count.update(…))`) is memoized by the macro like a call-macro argument ([03](03-composable-macro.md)), so a modifier rebuilt in a pass is `same` as the previous one, and a composable receiving it still skips. An `Rc` with identity is all it takes.
- **Allocation.** Built-in elements are enum variants in an inline `SmallVec`, so typical chains of up to six elements allocate nothing. Longer chains spill once.
- **Spelling.** `Modifier` is a type and also a `const` of that type, so code writes `Modifier.padding(16.dp())` as in Kotlin, and `modifier: Modifier = Modifier` as a default.
- **Representation.** `Element` and the chain's elements are private, so built-in modifiers can change their data without a breaking change; a user-defined modifier is added with `then_custom(element)` (D260).

## Layout

```rust
#[composable]
pub fn Layout(
    #[default(Modifier)] modifier: Modifier,
    measure_policy: Rc<dyn MeasurePolicy>,
    content: impl Fn() + 'static,
);

pub trait MeasurePolicy: Any {
    fn measure(&self, scope: &mut MeasureScope, measurables: &[Measurable], constraints: Constraints) -> MeasureResult;
    // Compose's `equals`: the default, the same zero-sized type
    fn same(&self, other: &dyn Any) -> bool;
    // Compose's defaults: `measure` run in an intrinsic measurement
    fn min_intrinsic_width(&self, scope: &mut IntrinsicMeasureScope, measurables: &[IntrinsicMeasurable], height: i32) -> i32;
    fn min_intrinsic_height(&self, scope: &mut IntrinsicMeasureScope, measurables: &[IntrinsicMeasurable], width: i32) -> i32;
    fn max_intrinsic_width(&self, scope: &mut IntrinsicMeasureScope, measurables: &[IntrinsicMeasurable], height: i32) -> i32;
    fn max_intrinsic_height(&self, scope: &mut IntrinsicMeasureScope, measurables: &[IntrinsicMeasurable], width: i32) -> i32;
}

impl MeasureScope<'_> {
    fn measure(&mut self, measurable: Measurable, constraints: Constraints) -> Placeable;
    fn place(&mut self, placeable: &Placeable, x: i32, y: i32);
    fn layout(&self, width: i32, height: i32) -> MeasureResult;
    fn parent_data(&self, measurable: Measurable) -> ParentData;   // weight, alignment
    fn parent_data_any(&self, measurable: impl Into<Measurable>) -> Option<Rc<dyn Any>>;  // parent data nodes
    fn layout_id(&self, measurable: impl Into<Measurable>) -> Option<Rc<dyn Any>>;
    fn density(&self) -> Density;
    fn text_measurer(&mut self) -> &mut dyn TextMeasurer;
}
```

- **Parent data**, as Compose's (D1168): a `ParentDataModifierNode` (`ModifierNode::as_parent_data`) gives its layout node's parent data, `modify_parent_data(density, what the nodes after it gave)`, folded from the chain's tail to its head (the outermost has the last word), which the parent's policy reads with `parent_data_any` (a measurable, its placeable, or a layout modifier's content: the whole chain's, as each of Compose's coordinators). `Modifier.layout_id(id)` is one (`LayoutIdParentData`), read with `layout_id`. A parent data node updated, added or removed, or `NodeContext::invalidate_parent_data`, measures the parent again if there was or is some (Compose compares nothing). The built-in `weight` and `align` stay a fixed `ParentData` (`parent_data`), which `Row`, `Column` and `Box` read without boxing.
- **A closure is a policy**: `MeasurePolicy` is implemented for `Fn(&mut MeasureScope, &[Measurable], Constraints) -> MeasureResult`, and `measure_policy(|scope, measurables, constraints| …)` makes one for `Layout` with the argument types inferred, as Kotlin's `MeasurePolicy { measurables, constraints -> … }`: `Layout!(modifier = …, measure_policy = measure_policy(|scope, measurables, constraints| { … }), { … })`. A new closure is a new policy (measured again), as a Kotlin lambda; `remember` one that doesn't change (D176).
- **One measure-and-place pass with constraints**, as in Compose, except that a policy places its children in the same call that measures them, rather than in a placement block run afterwards. A layout modifier (`LayoutModifierNode::measure(scope, content, constraints)`) measures and places the content it wraps the same way.
- **Incremental.** Updating a node's policy (to one that isn't `same`: D1354) or modifier, or inserting, moving or removing children, marks it for measuring and its ancestors as having a dirty descendant. The next layout measures from the root, but a node with unchanged constraints and nothing dirty returns its size at once; one with only dirty descendants measures them again in place, and runs its own policy only if one of their sizes changed. So a change climbs to the first ancestor whose size holds. A frame where nothing changed measures and draws nothing.
- **Rules.** A policy may measure a child only once per measurement, as in Compose: measuring it again panics. A panic in a policy or a layout modifier node leaves the tree whole (each node's children and modifier nodes are put back as the panic unwinds) and the node marked for measuring again. Pixel rounding is Kotlin's `roundToInt` (halves up), and `Constraints::offset` adds, as Compose's.
- **Intrinsics** as Compose's (D1200–D1205). `MeasurePolicy` and `LayoutModifierNode` have the four intrinsic functions; `MeasureScope` dereferences to `IntrinsicMeasureScope`, whose `min_intrinsic_width(measurable, height)` and the three others ask a child's (or, from a layout modifier, its content's: the rest of the chain, then the policy). The defaults are Compose's: `measure` runs in an *intrinsic measurement*, where measuring a child returns a placeable sized by its intrinsic on the axis asked (and by the constraint, or 2^15 − 1 if unbounded, on the other), placing does nothing, `run_after_layout` runs nothing and `layout` takes a negative size as 0. Nothing is measured, placed or kept, and no result is cached (Compose caches none). A child whose intrinsics were asked is measured again by its parent (as Compose's `onIntrinsicsQueried`), and a change in it measures again the layout that used them: the parent, or, through intrinsics asked of intrinsics, the first ancestor up the chain whose own intrinsics weren't asked (Compose's `intrinsicsUsageByParent`); a node measured afresh whose own intrinsics weren't asked forgets what was asked below it. Foundation's layouts have Compose's formulas: `Row` and `Column` (`IntrinsicMeasureBlocks`: along the main axis, the children and the spacing, weighted ones at the largest size per weight; across, the largest child at the main-axis space it would get), `size`/`size_in`/`required_*` (`SizeNode`), `aspect_ratio`, `default_min_size`, `width`/`height`/`required_width`/`required_height(IntrinsicSize::Min|Max)`, scrolls (unbounded along), text (the paragraph's minimum and maximum intrinsic widths, its height laid out at a width, at least `min_lines` high), images (their scaled size) and text fields (from a paragraph of their own, kept for the next question at the same width, the cursor counted in the maximum width, D1206, D1208); Material 3's top app bars and text fields have Compose's overrides (D1207); `padding`, `offset`, `fill_max_*`, `wrap_content_*`, `Box` and `Modifier.layout` keep the defaults, as Compose's. Lazy lists and grids and `BoxWithConstraints`, built on `SubcomposeLayout` in Compose, panic when asked, with Compose's message (`NO_INTRINSICS_MESSAGE`).
- **Sizes** a `layout(width, height)` returns must be within 0 and 2^24 − 1 (`MAX_LAYOUT_DIMENSION`): outside, it panics, as Compose's `checkMeasuredSize` (D1202).
- **Outside the constraints.** A measured size is coerced into the constraints for the parent; the node keeps its measured size and is centered in the coerced one, as Compose does (`required_size` past the parent's bounds). A `Placeable`'s `width` and `height` are the coerced size; `measured_width()` and `measured_height()` are the measured one, as Compose's `measuredWidth` and `measuredHeight` (D1353).
- **The root** measures its children with the window's constraints loosened, and places them at the origin.
- **Layout modifiers** as Compose's: `aspect_ratio(ratio)` and `aspect_ratio_with(ratio, match_height_constraints_first)` (Compose's search: the maximum width, the maximum height, the minimums, then the same past the constraints), `wrap_content_width()` (and `wrap_content_width_with(align, unbounded)`), `wrap_content_height` and `wrap_content_size` (the content at its own size, aligned in the size imposed), `width_in`/`height_in` (`size_in` on one axis), `default_min_size` (a minimum only where the constraints set none), and `Modifier.layout(|scope, measurable, constraints| …)`, a closure measuring and placing the content (a new closure is a new modifier, as Compose's lambda; state it reads measures it again).
- **Placement blocks.** `scope.layout_with(w, h, |placement| …)` is Compose's `layout(w, h) { … }`: the block places the children after the measure pass, top down, once the node is placed; what it reads places it again and doesn't measure it, and it may measure a child (a new size places this layout again) (D1209). `scope.place` inside `measure`, with `scope.layout`, is the same with nothing to read: what built-in policies do, keeping nothing. Placing a child twice panics (D1210).
- **Layout callbacks.** `on_size_changed(|size| …)` reports the size of what follows it in the chain when first measured and when it changes; `on_globally_positioned(|coordinates| …)` reports a `LayoutCoordinates` (a snapshot: `size`, `position_in_root`, `position_in_window`, and `bounds_in_root` clipped by the clipping modifiers around it, a scroll's viewport) after each layout that changed it, and each change of a graphics layer's transform around it, with no layout (D1187) (through the graphics layers' transforms on its path, as Compose's `localToRoot`), as `GlobalPositionAwareModifierNode`s the tree registers; `on_placed(|coordinates| …)` reports them each time it's placed, depth first in placement order. `on_size_changed` is a `MeasuredSizeAwareModifierNode`, not a layout modifier, as Compose's (D1188). A node may be a `LayoutAwareModifierNode`: `on_remeasured` where its layer was measured, its reads not observed; `on_placed` after the layout, the outer ones first, with the snapshot (D1186). The lambdas run once the layout is over, outside the tree, before drawing: state they write is composed and laid out again in the same frame. A measurement reading state another wrote while laying out (a lazy list's viewport size, read by `fill_parent_max_*`) is measured again within the same layout (`UiHost::lay_out`, twice at most).
- **Drawing order.** Children are drawn, and hit, in the order their parent placed them, sorted by `z_index` first (several on one node add up), as Compose's.
- **Nested scrolling** (D188): `Modifier.nested_scroll(connection)` lets a `NestedScrollConnection` (as Compose's) take part in the scrolls of the scrollables inside it: foundation's scrollables offer each drag, wheel and fling delta to the connections around them before scrolling (the outermost first) and what's left after (the innermost first), and their flings' velocities before and after, the fling callbacks suspending as Compose's (D891); Material's top app bars collapse and its bottom sheets drag this way. A drag's and the wheel's deltas are `UserInput`, a fling's `SideEffect` (`NestedScrollSource`), dispatched as Compose's `NestedScrollDispatcher`. A scrollable finds the connections from the pointer's hit path, as `NestedScrollChain::current()` (public, for custom scrollables; there is no `dispatcher` parameter): each nested-scroll node adds its connection in the initial pass of a press or wheel event, outside in, so the connections are the ancestors that contain the pointer (Compose's are the layout parents: the same but for content drawn outside its parents). The node is a pointer observer (`ModifierNode::is_pointer_observer`): on the hit path only when something inside it is hit, so it doesn't block the siblings under it. Each scrollable is itself a nested-scroll parent of the scrollables inside it, as Compose's `ScrollingLogic`, so what an inner scrollable leaves scrolls the outer ones before the connections around them. Drags are measured in window coordinates, so content moved by a collapsing bar doesn't scroll by its own move; a drag follows its first pointer, then another still down when it lifts; a cancelled drag ends as a release without velocity (pre- and post-fling dispatched); a fling stopped by an edge post-flings with the spline's velocity there; and a parent scrollable flings with the velocity an inner one left, along its axis, unless it's flinging itself (D889).
- **Scrollable states** (D850–D855, D874, D880, D888–D890), as Compose's `foundation.gestures`: a `ScrollableState` (`ScrollState`, `LazyListState`, `LazyGridState`, or `scrollable_state(consume)`) scrolls in blocks, `state.scroll(priority, |scope| async move { scope.scroll_by(…); })` (`ScrollableStateExt`, with `scroll_by`, `animate_scroll_by` and `stop_scroll`), one at a time through its `MutatorMutex`: a block of the same or a higher `MutatePriority` interrupts the one running, which returns `Err(MutationInterrupted)` where Compose cancels its coroutine, and one of a lower priority is refused the same way; `dispatch_raw_delta` scrolls at once outside any. `is_scroll_in_progress` is true while a block runs, and `last_scrolled_forward`/`backward` say which way the last scroll in a scope went. `Modifier.scrollable(state, orientation)` (and `scrollable_with(…, enabled, reverse_direction, fling_behavior, interaction_source)`) gives a state the pointer's deltas without moving anything; `vertical_scroll_with(state, enabled, fling_behavior, reverse_scrolling)`, the lazy lists and grids drive their states the same way. A drag past the slop holds `scroll(UserInput)` in a task polled at once (`DragSession`, interrupting a fling or an animated scroll), its deltas applied in the event through the scroll's scope and the nested-scroll connections around; a release flings in a `scroll(Default)` task with the `FlingBehavior` (what it leaves, a scrollable around flings with, and a fling whose node left ends at its next delta and hands on what it had, D889) (`DefaultFlingBehavior`: Android's spline, at the density; `ScrollableDefaults::fling_behavior()`), called whatever the velocity, as Compose's; drags are told to the interaction source (`is_dragged`, counting the drags going on; `vertical_scroll` and the lazy layouts report to their state's own `interaction_source()`, `Modifier.scrollable` without one to none, D880). Padding larger than the viewport still lays out an item (the first, or the last scrolled beyond its end), and an empty list is as large as its padding (D865). `request_scroll_to_item` writes the position at once (the layout coerces it), forgets the first item's key, keeps a negative offset (before the item) and stops a scroll going on; asked while composing it writes the same, with no read of the state (D861, D885). `animate_scroll_to_item` runs Compose's search and seek (springs of at most 2,500 dp, a teleport to 100 items before a far item, then a seek to its offset; D860) on a `LazyLayoutScrollScope` that sees the last layout moved by the scrolling asked since (D858), so it follows Compose's spring frame by frame. `layout_info()` gives Compose's `LazyListLayoutInfo` (a grid's `LazyGridLayoutInfo`, with each item's line, cell and span): the items in view (from the first under the start padding to the last in view, the sticky header where it sticks), with offsets from the content's start in the list's direction, the viewport's offsets and size, the count, the orientation, the reversal, the padding and the spacing; the measurement keeps the items in a buffer of the state's and bumps a state only when they change, and the info, with its keys' and content types' hashes (D170, D432), is built when read (D859). A slot taking another item without its node moving marks the list for measuring (D857).

**Flow layouts** (D1350–D1352). `FlowRow` and `FlowColumn`, as Compose's, lay their items out in lines that wrap: `FlowRow!(horizontal_arrangement = …, vertical_arrangement = …, item_vertical_alignment = …, max_items_in_each_row = 3, max_lines = 2, |row| { … })`. A line ends after `max_items_in_each_row` items or when the next item doesn't fit along it (Compose's main-axis spacing, in whole pixels, before every item but the first); a line that wouldn't fit across, or past `max_lines`, isn't shown, nor are its items or the rest (Compose's default `FlowRowOverflow.Clip`; its `overflow` parameter, `Visible` and the expand indicators are deprecated at tip, so not ported). Each line is measured as a `Row` (a `Column`) is: `Modifier.weight(row, w)` shares what the line leaves, `align(row, …)` aligns an item across its line, and `fill_max_row_height(row)` (`fill_max_column_width`, with a fraction: `FlowLayoutModifiers`) fills a fraction of its line across. The lines are arranged across by the other arrangement. Items with neither weight nor fill are measured once, while wrapping; the others wrap by their minimum intrinsic sizes and are measured with their line. Their intrinsics are Compose's: the maximum main-axis size is the longest line of `max_items` items at their maximum intrinsics; the cross-axis size wraps the items' minimum intrinsics at the size given; the minimum main-axis size is found by bisection, between the widest item and all of them in one line, for the smallest at which the lines fit and show every item `max_lines` allows. `ContextualFlowRow` and `ContextualFlowColumn` are deprecated: not ported.

**Constraints and grids.** `BoxWithConstraints` (as Compose's) gives its content the constraints it's measured with (`BoxWithConstraintsScope`: `max_width()` and friends in `Dp`). Compose composes it while measuring; here it first composes for the constraints it'll likely get (`LOCAL_CONSTRAINTS_HINT`: the window's at the root, a lazy list's items', a grid's cells'), and the measurement writes those it got as state, composing it again within the frame if they differ.

**Lazy grids.** `LazyVerticalGrid(columns, …)` and `LazyHorizontalGrid(rows, …)` (`GridCells::Fixed(n)`, `Adaptive(min)`, `FixedSize(size)` or `Custom`, an implementation of `CrossAxisCells`, Compose's `calculateCrossAxisCellSizes`, as Compose's) lay their items out in lines: a vertical grid's rows, a horizontal one's columns. As Compose's, a grid composes item by item (D450): its items are composed by the lazy list's item composition (`LazyItems`), each in a slot of its own with its key (state kept by key, the scroll position following the first visible item's key, saveable state by key), reused by an item of its content type once it left (up to 7 per type, as a list's, D430), and prefetched between frames; the arrangement across places the cells (from the left in any direction, mirrored when placed), which stay worked out while the cells and the arrangement do, as `GridSlotCache` (D1454); `reverse_layout` works from the end, the default arrangement along then from the end too; `sticky_header`, a whole line told its index in the grid, sticks over the lines of its section as a list's, at the start across, with no line (`UNKNOWN_ROW`, `UNKNOWN_COLUMN`) (D1451); `scope.item_scope().cross_axis_cell_count()`, at least 1, estimated from the room around until measured; its measurement (`LazyGridLayout`, as Compose's `measureLazyGrid`) works in lines: the line holding the first visible item, filled to the viewport, and, by the list's cache window with lines for units, the next lines the scroll's way prefetched, a request for each of their items (`LazyGridDefaults::cache_window`, D892, D565); while a header sticks, as Compose's whose sticking item has no line, the window's first line is -1, so nothing's requested before it, and the lines from the first to the last in view are told it with a size of 0 and no key for those not in view, which refills the window as each comes back into view (D1451); with `GRID_LINES_BEYOND`, `BEYOND` (2) lines composed and placed beyond each side too, counted at the average size by the window, which starts past them (D456, D893): the measurement gives prefetching those limits in items, so a frame trims what's composed to the same, whatever the spans. Its items' sizes are kept by item (what tells a slot leaving was measured, D460) and its lines' apart (what its estimates use), each with a running sum (D456). Cells are as large as Compose's across the grid (the room less the spacing divided evenly, the remainder a pixel each to the first cells); an item is measured fixed across its cells (Compose's `Constraints.fixedWidth`, or `fixedHeight` for a horizontal grid), unbounded along, and a line is as long as its longest item, its items at its start. The `LazyGridScope` has the list's forms (`item`, `items`, `items_keyed`, `items_list`, `items_indexed`, keyed or not), each with a `_with` form taking Compose's `contentType` after the key, as a list's (`items_keyed_with(count, key, content_type, content)`), and a `_with_span` form taking Compose's `span` and `contentType` (`items_keyed_with_span(count, key, span, content_type, content)`, D454): a span (`GridItemSpan(cells)`) is worked out from the `LazyGridItemSpanScope` (`max_line_span`, `max_current_line_span`, the cells left in the line) and the item, kept within 1 and the line's cells; an item that doesn't fit the cells left starts the next line, its span asked again for a whole line, as Compose's `LazyGridSpanLayoutProvider`. Which items a line holds is arithmetic without spans; with spans, the items are walked from the first only as far as a measurement asks (kept while the items and the cells are the same: a caller recomposing with the grid's content lambda unchanged skips the grid; a content that changed walks them again, as Compose's, D454), the line count estimated from the items not walked. `LazyGridState` counts in items (`first_visible_item_index` is the first item of the first visible line; `scroll_to_item` scrolls to the item's line), so a new cell count keeps the first item in view. Right to left, a vertical grid's first column is at the right, and a horizontal grid's first column too, as a `LazyRow`'s first item. A grid needs a bounded size along and across its axis. The items of a not yet measured grid compose for a cell's constraints in the space around (`LOCAL_CONSTRAINTS_HINT`), then for those of a one-cell item. No `reverse_layout`, `user_scroll_enabled`, sticky headers, `GridCells.FixedSize`, or staggered grids.

**Snapping** (D1462). `snap_fling_behavior` lands a fling where a `SnapLayoutInfoProvider` says; `remember_list_snap_fling_behavior` and `remember_grid_snap_fling_behavior` land on an item or line at a `SnapPosition`, passed as a list's `fling_behavior`.

**Gestures.** `Modifier.draggable_with` and `draggable_2d` are Compose's `DragGestureNode`: a slop, a gesture left to pick up if something took it and let it go, an angle deciding between a vertical and a horizontal drag nested, scrollables among them (D1458, D1459). Page Up and Page Down scroll a scrollable by the size at its place in the modifier chain (D1460), and move the cursor of a text field, which takes them first. `Modifier.pointer_input(key, |scope| async move { … })` (as `pointerInput(key) { … }`) runs a coroutine over the pointer events reaching its node: `scope.await_pointer_event(pass)` gives each one as a `PointerInputChange` it can `consume()`. The coroutine is an executor task polled at once as each event reaches the node (`platform::poll_now`, as Compose resumes it undispatched), so what it consumes the handlers after it see consumed; its timeouts are executor timers. It starts at the first event and starts over when its key changes, its gesture is cancelled or its node leaves; a block that returns stays done. Each change carries its pointer's id and time (`uptime_millis`), and Compose's `previous_position` and `position_change()`: the previous event's position in the node as laid out now, so a node that moves between events (a sheet dragged by its own `draggable`) sees the finger's move, not the finger's move less its own (D189); and `Enter`/`Exit` go through the three passes as other events. Compose's detectors are there, with their rules: `await_first_down`, `wait_for_up_or_cancellation` (up once no pointer is down; cancelled when a move is consumed, in the main pass or by a parent by the final pass, or leaves the node), `await_touch_slop_or_cancellation`, `with_timeout`, `detect_tap_gestures(TapGestures)` (tap, double tap within 300 ms but not sooner than 40 ms, long press after 400 ms, press; a cancelled or held second press still reports the first tap) and `detect_drag_gestures(DragGestures)` (past the 8 dp touch slop, following the pointer that crossed it, its first amount what's past the slop; a parent that takes the moves first keeps the gesture); their callbacks run once the event's dispatch is over. `PointerInputDriver` runs a block for custom pointer nodes. Foundation's `Modifier.draggable(state, orientation, …)` (its `on_drag_stopped` given the release's velocity, from the last 100 ms of moves as Compose's `VelocityTracker`) with `remember_draggable_state(on_delta)` reports drags along an axis as deltas, as Compose's: a node of its own that calls its newest callbacks, and calls `on_drag_stopped` when the drag is cancelled too.

**More clicks.** `combined_clickable(on_long_click, on_double_click, on_click)` (and `combined_clickable_with(options, …)`), as Compose's `combinedClickable` and its node (`clickable.rs`, D1052): with `on_double_click`, a click waits out the 300 ms double-click timeout (a second press sooner than 40 ms after the first release is ignored); with `on_long_click`, holding 400 ms long-clicks (with `LongPress` haptics unless `haptic_feedback_enabled` is off), and everything is consumed until the release; holding Enter, Space or the D-pad's center long-clicks too, and pressing one twice double-clicks; its focus, hover and semantics are `clickable`'s, plus a long-click action (`SemanticsActions::ON_LONG_CLICK`, labelled `on_long_click_label`) with `on_long_click`. `selectable(selected, on_click)` is a clickable whose semantics say `selected`, and `selectable_group()` marks the group; `tri_state_toggleable(state, on_click)` a clickable whose semantics say its `ToggleableState`, as Compose's. `hoverable(interaction_source, enabled)` emits a mouse over the node into the source (disabled, it's no modifier), and `focusable_with(enabled, interaction_source)` its focus.

**Hover.** A mouse's hit path is tracked: when it changes, what the mouse left hears `PointerEventType::Exit` and what it came over `Enter`, as Compose's (not while a button is held: a drag stays with what it pressed); leaving the window (`UiHost::send_pointer_left`, from winit's `CursorLeft`) is an exit, and content moving under a resting mouse moves the hover (a hit test after each layout, as Compose Desktop's synthetic move). Clickables emit `HoverInteraction`s, which their indication shows. `Modifier.pointer_hover_icon(icon)` (as `pointerHoverIcon`) sets the mouse pointer's look over a node (`PointerIcon::Text`, `Hand`, `Crosshair`; the innermost on the hovered path wins); text fields show an I-beam, and the desktop window sets its cursor from `UiHost::pointer_icon`.

**Tooltips.** `TooltipArea(tooltip, …, content)` (as Compose Desktop's) shows `tooltip` in a popup at the mouse pointer, 16 dp below it (`TooltipPlacement`), or above it where there's no room below, once it has rested over the content for 500 ms (moving starts the wait again), and hides it when the pointer leaves the area (resting on the tooltip inside the area keeps it) or presses; Material's `PlainTooltip` is its look (the small body text on the inverse surface).

**Scrollbars.** `VerticalScrollbar` and `HorizontalScrollbar` (as Compose Desktop's) show a thumb for a `ScrollbarAdapter` (`remember_scrollbar_adapter(scroll_state)`, exact; `remember_lazy_list_scrollbar_adapter(list_state)`, from the average item size): its length the viewport's share of the content (at least 16 dp), dragged to scroll, a press on the track paging toward it, hidden while everything fits; `ScrollbarStyle` and `LOCAL_SCROLLBAR_STYLE` as Compose's defaults (8 dp, black at 12 %, 50 % while dragged). The thumb darkens while hovered or dragged.

**Layout direction.** Each layout node takes `LOCAL_LAYOUT_DIRECTION` (as `LocalLayoutDirection`) where it's composed; the host provides the window's (`UiHost::set_layout_direction`, `WindowOptions::layout_direction` on desktop), and `CompositionLocalProvider` changes it for a subtree. `MeasureScope::layout_direction`, `DrawScope::layout_direction` and `EventContext::layout_direction` read it. In right-to-left, as Compose: `place_relative` mirrors a child in the width its layout reports (once that's known); the root, `padding`, `offset`, the size modifiers, scrolling containers, lazy lists and Material's layouts place relatively; a `Row`'s arrangement and `Box`'s and `Column`'s alignments run from the right (a `Column`'s arrangement still runs from the top); a horizontal scroll or lazy row starts at the right and a drag, a wheel or a focused child's bring-into-view goes the other way; a text field lays its text out again when the direction changes; popups align with their anchor's start and offset toward its end, and menus try the anchor's right first; a slider and a switch are drawn mirrored (and the slider's pointer and arrow keys follow); text with no strong character runs in the layout's direction.

## Text

- **`TextMeasurer`** is the interface layout uses: it lays out a paragraph and returns a handle with its metrics. Each platform implements it with the text stack Compose uses there ([07](07-platforms.md)):
  - **desktop:** Skia's paragraph module (HarfBuzz shaping, ICU line breaking and bidi), as Compose Desktop;
  - **Android:** Android's own `StaticLayout`, as Android Compose.

  Kerning, ligatures, complex scripts, fallback fonts and emoji come from the platform stack.
- **Tests** use a fixed-advance measurer by default, so measurements are identical on every machine and don't depend on fonts; the Skia measurer (the system's fonts, no bundled ones: D94) can be given to a test host. The fixed measurer (`FixedTextMeasurer`, D1105) gives every character the same advance and line metrics (`FixedFontMetrics`: half an em wide and 1.25 em lines by default; `FixedFontMetrics::SAMPLE_FONT` is Compose's test font, one em wide and one em high with the baseline at 0.8 em, for Compose's paragraph tests) and lays text out as Android does: lines broken greedily at spaces (spaces hang past the width, a longer word is split), each paragraph in the style's direction or its first strong character's with the Unicode bidi algorithm reordering mixed runs, aligned (justified lines spread their spaces), indented, with each span's size, letter spacing and horizontal scale, the line height style's alignment and trims, an ellipsized last line holding the rest of the text, and the width Compose's `finalMaxWidth` chooses.
- `BasicText`/`Text` keep the paragraph handle on the node, so a recomposition with the same text measures nothing. New constraints lay it out again as Compose's `ParagraphLayoutCache` decides (`newLayoutWillBeDifferent`, D550; [15](15-android-stress-benchmark.md), "Compose's defaults" (g)): always for a new minimum or maximum width, for a new height only when the paragraph is taller than it or cut at its maximum lines; a new text, density, direction, or style attribute that lays text out (`TextStyle::has_same_layout_affecting_attributes`, as Compose's) lays it out anew. A new color or decoration only keeps the layout and draws it in the new paint (`TextMeasurer::restyle`, D555), as Compose's `updateDraw`; where the measurer can't (the desktop's), the text is laid out anew. A layout for new constraints goes through `TextMeasurer::relayout` where the measurer keeps what it measured of the text, as Compose's `ParagraphIntrinsics`: Android's (`TextMeasurer.kt` keeps the spans, paint, boring metrics and own width, so a new width doesn't measure the text's own width again; its `StaticLayout` still measures what it breaks); the desktop's lays the text out anew. A text's intrinsics are Compose's (D1205): its minimum and maximum intrinsic widths are its paragraph's (`TextMeasurer::min_intrinsic_width`, the widest segment between line break opportunities: SkParagraph's, Kotlin's from a line `BreakIterator` as Compose's `LayoutIntrinsics`, measured when first asked; and `max_intrinsic_width`), rounded up, from the measured paragraph or one laid out unbounded; its intrinsic heights are its height laid out at the width asked, at least `min_lines` high. A height whose constraints would lay the text out differently than the measured paragraph reads a paragraph of its own, kept for the next one, and leaves the measured one and its constraints alone (D554), as Compose's intrinsics have caches of their own; on Android it's laid out from the measured paragraph's kept intrinsics and never recorded ahead (`TextMeasurer::layout_probe`, Kotlin's `probeLayout`). Intrinsics set no overflow and call no `on_text_layout`; the review tests are in `review_d550.rs`.
  - **A compose-rs-only optimization, off by default** (D551): with the host's `Optimization::REUSE_PARAGRAPH_AT_SAME_LAYOUT_WIDTH` (D520), a new width bound keeps the paragraph when the width it's laid out at (Compose's `finalMaxWidth`: the text's own width within the bounds, or the maximum when the minimum equals it) is the same, and the paragraph fit: its own width within the line width limit, so no line broke to fit, and no line past its maximum. A measurer lays a text out from that width alone, so the layout is the one a new layout would make: a short label in a container whose width changes keeps its paragraph; a text across the whole width (`fill_max_width`), wrapped, ellipsized, or held wider by a minimum width that changes is laid out again. Measurers report the text's own width (`TextMeasurer::max_intrinsic_width`); without it, Compose's rule applies.
- **Styles** (D1102, D1103). `TextStyle`, `SpanStyle` and `ParagraphStyle` have Compose's fields: the paint (`color`, or a `brush` with an `alpha`: `foreground()` resolves them as Compose's `TextForegroundStyle`, a brush winning and a solid brush being its color), size, weight, style (italic), synthesis, family (sans-serif, serif, monospace, cursive, or a system family by name, falling back to the default), font feature settings, letter spacing, baseline shift, geometric transform (scale, skew), locales, background, decoration (underline, line-through, combinable), shadow, draw style (fill or stroke); alignment, direction (`TextDirection`, resolved against the layout's), line height and its `LineHeightStyle` (alignment, trim, mode), indent, line break (`LineBreak`'s strategy, strictness and word break, with Compose's presets), hyphens, motion, and the platform part (`PlatformTextStyle`: font padding, emoji matching). A `TextStyle` is a span style's fields and a paragraph style's (`to_span_style`, `to_paragraph_style`, `TextStyle::from_styles`). What isn't set (`None`, `TextUnit::UNSPECIFIED`, `Color::UNSPECIFIED`) comes from the style it's merged over (`merge`, `+`, `merge_span_style`, `merge_paragraph_style`), as Compose's rules: a brush wins over a color, a brush without an alpha keeps the previous alpha, platform parts merge. `lerp` interpolates as Compose's (colors in Oklab, units of the same type, weights rounded, a missing shadow from its transparent self, discrete fields switching half way), and `TextStyle::resolve_defaults` gives every unset field Compose's default. Sizes, letter spacing, line heights and indents are `TextUnit`s in `sp` or `em` (D1102); the measurers resolve an `em` against the font size (a span's `em` font size against its text's). The styles are `Clone`, not `Copy` (a brush, the font features and the locales are shared, D1103): a closure that uses a style twice clones it. They save through `remember_saveable` (`Saveable`, as Compose's savers: a span style's family, brush, draw style and platform part aren't saved, as in Compose). The measurers draw the paint (a gradient as its average color, D1103), size, weight, style, family, letter spacing, decoration, background, line height and alignment; the other attributes are the model's until the measurers take them (docs/11). Material's `Text` takes each as a parameter over `LOCAL_TEXT_STYLE`, as Compose's, and its typography is shared (D1106: `MaterialTheme::typography()` is an `Rc<Typography>`, so reading it copies no style; a composable takes one with `.clone()`). `overflow` (as `TextOverflow`) clips by default, ends the last line with "…" (`Ellipsis`; one line without soft wrap, as Compose's), or draws past the bounds (`Visible`). **Styled text** comes from `AnnotatedString` (D1104, as Compose's): text with annotations over byte ranges (`AnnotatedRange`, with a tag): span styles, paragraph styles (nested or covering the same range, never partly overlapping: the string panics, as Compose's throws), string and text-to-speech annotations, links (`LinkAnnotation::Url`/`Clickable` with `TextLinkStyles` and a `LinkInteractionListener`) and bullets, built with `AnnotatedString::build(|builder| { builder.append(…); builder.with_style(…, |builder| …); })` and Compose's other builder calls (`push_*` returning an index, `pop`, `pop_to`, `with_*` returning the block's value, `add_*`, bullet lists). `sub_sequence`, `+`, the annotation queries, `normalized_paragraph_styles` (the paragraphs a multi-paragraph layout splits the text into) and the saver are Compose's. `BasicAnnotatedText` and Material's `AnnotatedText` show one, each run of span styles laid out in its style (SkParagraph's styled runs); paragraph styles inside the text, links, text-to-speech annotations and bullets are the model only for now (docs/11).
- **Line heights** (D571). A style's `line_height_style` is Compose's `LineHeightStyle` (an alignment, as its top ratio with `PROPORTIONAL` -1, and a trim), and a style without one is `LineHeightStyle::DEFAULT`, as Compose's `createCharSequence` (ui-text 1.12.1, `AndroidParagraphHelper`) applies `LineHeightStyle.Default` (proportional, both ends trimmed); Compose's plain `LineHeightSpan` goes only with `includeFontPadding`, which compose-rs never has. Material's text styles carry its `DefaultLineHeightStyle` (centered, nothing trimmed, `TypographyTokens.kt`), and `LOCAL_TEXT_STYLE` defaults to its `DefaultTextStyle` (`DEFAULT_TEXT_STYLE`). On Android the span is ported from Compose's `LineHeightStyleSpan`, in its `Fixed` mode: every line the line height, ceiled; the difference from the first line's font height split by the top ratio (`ceil(diff × (1 − ratio))` below when growing, `ceil(diff × ratio)` when shrinking, multiplied in floats as Compose's); the first line's top and the last's bottom back to the font's when trimmed, and a single line trimmed at both ends left as it is. So at density 1, a 16 sp Roboto "Hello" on 40 sp lines is 19 px high, two lines 59 px. An empty last line (an empty text's, or after a last new line) is as high as a line of text, as Compose's `TextLayout.getLastLineMetrics`: a zero-width space laid out alone with a copy of the span gives its metrics (`lastLineExtra`), so an empty Material text field's cursor is the line height (24 sp: 54 px on the Pixel 8 Pro, as Compose's `getCursorRect`). An empty text with a line height is never a `BoringLayout`, and a boring line takes the same span's metrics. On the desktop, a centered style sets Skia's half leading and the trims its text height behavior (`DisableFirstAscent`, `DisableLastDescent`); Skia's other alignments stay proportional. Not there: the `Tight` and `Minimum` modes, `includeFontPadding`, and the padding Compose's `TextLayout` adds when trimming a line shorter than its font.
- **Offsets** are UTF-8 byte offsets at character boundaries in every text API (D1100), where Compose's are UTF-16 indices; the measurers convert where their platform needs UTF-16 (SkParagraph's and Android's queries).
- **Editing** (D1101) has Compose's `ui.text.input` model: `TextRange`, `TextFieldValue` (text, selection, the input method's composition, kept in the text when made), the edit commands (`CommitTextCommand`, `SetComposingTextCommand`, `SetComposingRegionCommand`, `SetSelectionCommand`, `DeleteSurroundingTextCommand` and its code-point form, `FinishComposingTextCommand`, `BackspaceCommand`, `MoveCursorCommand`, `DeleteAllCommand`), the `EditingBuffer` they edit (its operations crate-private, as Compose's are internal) and the `EditProcessor` applying them to a value. A command's position inside a character moves to a boundary (a range widens over it, a cursor goes to its start); backspace and cursor moves step by grapheme clusters, as Compose's character break iterator. `BasicTextField` applies typed text and deletions through an `EditProcessor`, as Compose's text field applies its key input's commands.
- **Line bounds and layout results.** `min_lines` makes a text at least that many lines high (as `heightInLines`; `0 < min_lines <= max_lines`, else it panics, as Compose's `validateMinMaxLines`), and `on_text_layout` hears each new layout (the paragraph laid out again for a new text, style or width, or a new size; not a measurement that changed nothing, and a new listener only swaps the old one) as a `TextLayoutResult` (as Compose's: `layout_input`, `multi_paragraph`, `size`, `line_count`, the baselines, `did_overflow_width`, `did_overflow_height` with the lines cut by `max_lines`, `has_visual_overflow()`, and the queries below), called after the layout as `on_size_changed` is (`MeasureScope::run_after_layout`), so what it writes is laid out within the frame; intrinsics aren't reported. Whether lines were cut comes from `TextMeasurer::did_exceed_max_lines` (Skia's `didExceedMaxLines`, `StaticLayout`'s line count and ellipsis on Android; a measurer that can't tell says no) (D233, D250).
- **Paragraph queries** (D1105). A laid-out text is a `Paragraph` (Compose's interface, byte offsets): its width, height, intrinsic widths, baselines, line count and whether lines were cut; per line its start and end (`get_line_end(line, visible_end)`), top, bottom, baseline, left, right, width and ellipsis; `get_line_for_offset`, `get_line_for_vertical_position`, `get_offset_for_position`, `get_horizontal_position` (primary or secondary, as Android's), `get_paragraph_direction`, `get_bidi_run_direction`, `get_bounding_box` (and for a range), `get_cursor_rect`, `get_word_boundary` (Compose's `WordIterator` over Unicode's word breaks, D1108, a run of Thai, Lao, Myanmar or Khmer one word until there's a dictionary, D1114) and `get_path_for_range` (Android's selection path). A line's visible end leaves out Compose's `isLineEndSpace` characters on every measurer (D1109), an ellipsized line's stops at its ellipsis (D1110), and an offset for a position is a grapheme cluster boundary (D1111). `TextMeasurer::paragraph(handle)` gives it as an `Rc<dyn Paragraph>` that outlives the handle, and `TextLayoutResult` answers the same queries through it. The answers are a `ParagraphLayout`'s, which follows Android's `Layout` and Compose's code over it: the fixed measurer builds it as it lays out; the desktop reads SkParagraph's line metrics and each character's rectangles when asked; Android reads the `StaticLayout`'s lines and every offset's horizontal positions in one JNI crossing when asked (`TextMeasurer.kt`'s `paragraphLayout`). `BasicText` asks only when it has an `on_text_layout` to call. Not there yet: a `MultiParagraph` of paragraphs (the measurers lay a text out as one paragraph; it comes with paragraph styles inside text), `getRangeForRect`, `fillBoundingBoxes`, placeholders, `paint`, the `Paragraph(…)` constructors (a measurer lays the text out).

## Drawing

A draw pass records a **display list**: a subset of the `Canvas` API (clips to rectangles, rounded rectangles and paths, transforms, rectangles, rounded rectangles, arcs, lines, paths, images, shadows, paragraphs drawn by handle, paints with gradient shaders; no blend modes yet). Draw modifier nodes record into it in chain order: `DrawModifierNode::draw` before the content (the rest of the chain and the children), `draw_after` after it, in reverse order, which is Compose's `drawContent()` split in two (`background` draws before, `border` after; `clip` is a graphics layer, below). A node draws at the size of the layer its draw node is in, so `padding(8).background(…)` fills inside the padding. A platform `Renderer` replays the list: Skia on desktop, Android's `Canvas` on Android ([07](07-platforms.md)). Tests dump it as text or render it to PNG through Skia's CPU raster backend. The list is assembled whenever anything changed, into a buffer kept from frame to frame (so a warm frame allocates nothing): what's outside every repaint boundary is drawn again, and each boundary's group refers to what it kept, drawn again only if something it drew from changed (below, "Repaint boundaries").

**Paths and vector images.** `Path` is Compose's mutable path (D530): built with `move_to`, `line_to`, `quadratic_to`, `cubic_to`, `arc_to`, their `relative_` forms, `add_rect`, `add_oval`, `add_round_rect` (a `RoundRect`), `add_arc`, `add_path` and `close` (shapes counterclockwise unless given a `PathDirection`, as Compose's), moved with `translate` and `transform` (a `Matrix`), combined with `op` (a `PathOperation`: computed by Skia when it's called on desktop, kept as steps that Android's replayer computes with `android.graphics.Path.op`, D535: compose-skia installs Skia's path ops per thread with `platform::set_path_operator`, the result flat contents with conics approximated by two quadratic curves each, an operation Skia can't do leaving the path as it was and returning `false`, as Android's; elsewhere the path keeps `PathStep`s (push an operand's contents, combine the top two, add contours, set the fill type), a flat list `Replayer.kt` runs with pooled scratch paths, and `op` returns `true`; a path combined with itself appends two steps in place, so a union of 100,000 shapes is 200,001 steps, built in linear time and dropped iteratively, its definition carrying all its operands each time it's redefined, where Compose's result stays flat; the result's fill type is even-odd, as Skia's; `get_bounds` and `is_empty` bound steps by their operands', exact on desktop; where the result isn't computed, its last point isn't known, so a relative command after it starts at the origin and an `arc_to` moves rather than draws a line), emptied with `reset` (keeping its fill type) or `rewind`, with `fill_type`/`set_fill_type`, `get_bounds`, `is_empty` and `is_convex`; or parsed from SVG path data (`Path::from_svg`, arcs converted to curves). Arcs follow Skia (`arc_to_rad` and `add_arc_rad` take radians): a whole turn from a quarter's angle is the closed oval, nothing is added for no sweep, and otherwise Skia's `arcTo` is forced to move, so a whole turn from another angle is a lone point, as is `arc_to` of a whole number of turns, and a larger sweep its remainder. `add_path(path, offset)` appends another path, `Path::combine` makes one from an operation. `reset` keeps the fill type, as Android's, and `rewind` sets it back to non-zero, as Skia's, both keeping the commands' storage; `is_convex` is true for an empty path or a line, as Skia's. A contour drawn without a move gets an explicit one, as Skia's `injectMoveToIfNeeded` makes it (to the origin first, to the closed contour's start after a close), so `add_path`, `translate` and `is_convex` see what Skia does; after an operation kept as steps it's left to the platform. The contents (`PathData`: steps, commands, fill type; `Send` and `Sync`; not `Clone`, as a copy would carry its original's identity and generation) are changed in place while nothing else holds them, else copied, so contents once shared never change; the identity is a process-wide counter (D530). It is a shared reference, as Kotlin's (an `Rc<RefCell<Arc<PathData>>>`; a clone is the same path, `!Send`; `ComposeArg` by identity), so code remembers one (`remember(Path::new)`) and resets it in a drawing block each frame, as Compose code does. Drawing it (`DrawScope::draw_path`, `clip_path`) records its contents as they are then: a `PathData` in an `Arc` (shared, never changed: a change after drawing makes new contents), with the path's identity and a generation each change bumps, in a `DrawPath` op with a scale and offset (an `ImageVector`'s viewport fitted to its size; an `ImageVector` holds `Arc<PathData>`s). A recording keeps the contents it drew: changing a path draws nothing again, as in Compose, and a drawing run again for its own reasons (state it read) draws the path as it is (D531), so a group's key and version name one drawing (D157). On Android a path changed in place is defined again under the id of its old contents once nothing holds them, and the replayer refills the same `android.graphics.Path` (D532). Material's `Icon` draws an `ImageVector`; `icons::filled::add()` and friends are material-icons-core's filled icons.

**Interactions** (D1050). As Compose's `androidx.compose.foundation.interaction`: a component emits what happens to it into a `MutableInteractionSource` (`try_emit`, or `emit` from a coroutine), as `Interaction`s: `PressInteraction::Press(press)` (where it went down) and its `Release` or `Cancel` naming that press, `FocusInteraction::Focus` and `Unfocus`, `HoverInteraction::Enter` and `Exit`, `DragInteraction::Start`, `Stop` and `Cancel`, or the app's own (`Interaction::custom`); each start is compared by identity, as Compose's classes. `source.interactions()` collects them from then on (`collect(|interaction| …).await` in a coroutine, or `next().await`), each collector with a queue of its own of the latest 16, as Compose's `MutableSharedFlow(extraBufferCapacity = 16, DROP_OLDEST)`; a collector is a `futures_core::Stream`, as the runtime's flows will be. `collect_is_pressed_as_state()`, `collect_is_focused_as_state()`, `collect_is_hovered_as_state()` and `collect_is_dragged_as_state()` are Compose's (a state collected from the composition on, in a `LaunchedEffect`); `is_pressed()`, `is_focused()`, `is_hovered()` and `is_dragged()` are compose-rs's own state reads of everything the source saw since it was made (Material's elevations read them). The clickable family, `focusable_with` and `hoverable` emit into the source they're given, or (the clickables) into one of their own, made when first needed. Presses, releases, cancels and focus changes are emitted from a task on the node's coroutine scope, as Compose's launched emissions, in order: hovers, and the ends of interactions a node forgets (it left, was reused, its source changed), go at once, after what the node queued, so a release then an exit stay in that order; a node detached drops what it queued but its fallbacks (press releases and cancellations and focus changes, sent at once: D1065), its scope then cancelled with its tasks and timers (D1053, D1057, D1061). compose-rs's own indications listen to the source (called back from the emission, no task) and draw again through their host's handle, as Compose's call `invalidateDraw` (D1060). An indication's node takes its collector (`interactions()`) when it's made, and is attached and detached with the clickable hosting it, as Compose's delegate (D1056: one made in an event or replaced by an update, where the clickable has no `NodeContext`, from a task through the clickable's `NodeHandle`, until MN-5's delegates).

**Indication** (D1051). As Compose's: an `Indication` is a factory (`IndicationNodeFactory`: `create(interaction_source)` makes a node collecting the source and drawing what it says, `same` is its `equals`), `Indication::NONE` (Compose's `null`) or `Indication::LOCAL`: `LOCAL_INDICATION`'s value where the clickable's node is (D1056: set as the layout node takes its modifier, so a modifier made outside the provider shows the provider's; for `Modifier.indication`, where it's made; foundation's default is Compose's debug indication, black at 30 % pressed and 10 % hovered or focused). `Modifier.indication(source, indication)` draws one; the clickable family draws `ClickableOptions::indication` (`LOCAL` by default, as Compose's overloads without one), delegating to its node (D1193): made at once with a source given, else with the clickable's own source at its first interaction (a pointer event, a key, the focus), reset if it's attached and the clickable reused, detached and released when it leaves or is reused (D1064); a new source, or a factory not the same, makes it again. The node is a delegate, with its own context and `coroutine_scope`, cancelled when it's replaced (D1193). A built-in node delegating to an indication observes its state reads as a custom one (`ModifierNode::observes_reads`). `Indication::bounded(color)` (and a `Color`'s `into()`) and `Indication::unbounded(color, radius)` are compose-rs's state layer, Material's ripple at rest (10 % pressed or focused, 8 % hovered; an unbounded one a circle of `radius`), which Material's components use until its ripple moves onto `Indication`. A press inside something waiting for a gesture past it (a scrollable, a draggable, for a touch: `PointerInputModifierNode::waits_for_gesture`, as Compose's `hasWaitingParent`) is emitted after `TAP_INDICATION_DELAY` (100 ms, Android's tap timeout), at once with its release if released sooner, never if cancelled sooner (a scroll took it).

**Custom drawing.** `Modifier.draw_behind(|scope| …)` draws under the content and `Modifier.draw_with_content(|scope| { …; scope.draw_content(); … })` around it, drawing the rest of the node and its children where `draw_content` is called (or not at all), as Compose's; foundation's `Canvas(modifier, |scope| …)` is a node to draw in (`Canvas_with(modifier, content_description, …)` described to accessibility, as Compose's overload). Their lambdas are observed: state they read draws again, without recomposing or measuring. `Modifier.draw_with_cache(|cache| cache.on_draw_behind(…))` (or `on_draw_with_content`), as Compose's `drawWithCache`, builds what it draws with (paths, brushes) from the `CacheDrawScope`'s size, and keeps it until the size, density or direction changes or state the build read does: the build runs under an observer of its own (whose write bumps a state the drawing reads, so the node draws again), and what the drawing lambda reads only draws again.

**`DrawScope`.** Besides rectangles, rounded rectangles, lines, paths and images: `draw_circle(center, radius, paint)`, `draw_oval(oval, paint)` (a whole turn of an arc, so no new operation) and `draw_arc_with(…, use_center, paint)` (a pie slice); `center()`; a paint that draws nothing (a transparent color without a shader, as Material's transparent containers) records nothing, as Skia drops it (D251); and the scoped transforms and clips of Compose's `DrawScope` extensions, each restoring after its block: `rotate(degrees, pivot, |scope| …)` and `scale(scale_x, scale_y, pivot, |scope| …)` (a save and a `Transform`), `translate(left, top, |scope| …)` and `inset(left, top, right, bottom, |scope| …)` (moving the scope's origin, and shrinking its size: no operation), `clip_rect(rect, |scope| …)` and `clip_path(&path, |scope| …)` (a `ClipPath` operation). Geometry comes before the paint, as the scope's other calls (Compose's put the color or brush first). `draw_path` takes a `&Path` (its contents now, shared) or a `&Arc<PathData>` (contents that never change). `Paint::with_alpha` multiplies a paint's opacity, as the draw calls' `alpha`.

**Brushes.** `Brush` is Compose's: `Brush::Solid`, `linear_gradient`, `horizontal_gradient`, `vertical_gradient`, `radial_gradient`, `sweep_gradient`, each taking colors or `(stop, color)` pairs (`ColorStops`), the short forms with Compose's defaults and the `_with` forms with the positions and a `TileMode`; positions are in the drawing's coordinates, `Offset::INFINITE`, `Offset::UNSPECIFIED` and an infinite radius standing for its size, center and half its smaller side, as Compose's. `DrawScope::brush_paint(&brush, alpha, style)` resolves it for the scope into a `Shader` the display list keeps (`DisplayList::shaders`) and returns a `Paint` naming it (`Paint::shader()`, an index hosts read; `Paint` stays `Copy`), usable with any draw call; `Modifier.background(brush)` and `background_with(brush, shape)` are Compose's `background(color, shape)` and `background(brush, shape, alpha)` (a color converts to a brush; the alpha is `brush.with_alpha(alpha)`). Each recording (the frame's own, each repaint boundary's kept one) has its own shaders, its paints naming its table's, so a frame refers to a kept recording without re-indexing anything (D270); `flatten` appends them, shifting the indices. Skia paints the gradients (interpolated premultiplied, as Android's HWUI and Skiko's: D210). A brush paint's `color` is the gradient's average, what a renderer without the shader would paint; Android's replayer builds the gradient (D210).

**Arcs and caps.** `DrawScope::draw_arc` (as `drawArc`) draws part of an oval; a stroke's `cap` (`StrokeCap::Butt`, the default as Compose's `Stroke`, `Round` or `Square`) shapes open ends. Material's progress indicators draw with them, their caps `Round` by default as Material 3 1.4's (D320): `CircularProgressIndicator(progress)` and `LinearProgressIndicator(progress)` (40 dp and 240 × 4 dp, as Compose's; `progress` a lambda read while drawing and when the semantics are read, as Compose's non-deprecated overloads, D1003), and `IndeterminateCircularProgressIndicator` and `IndeterminateLinearProgressIndicator` (Compose's no-progress overloads, named apart since Rust has no overloads), whose keyframed animations (Material 3 1.3's: the circular arc growing from a tenth to 87 % as the whole turns, the linear lines accelerating over 1.75 s) are computed from one infinite clock read while drawing, so each frame only draws again (each is a repaint boundary of its own, so what's around it isn't drawn again: D323).

**Snackbars.** `SnackbarHostState::show_snackbar(message)` (or `SnackbarVisuals`; `show_snackbar_with(message, action_label, with_dismiss_action, duration)` with Compose's optional parameters) is a coroutine, as Compose's: snackbars asked for show one at a time, in order; it returns `ActionPerformed` or `Dismissed` (after 4 or 10 seconds, or never for `Indefinite`), and cancelling it takes its snackbar away. `SnackbarHost` shows the current one, faded and scaled in; `Scaffold`'s `snackbar_host` slot places it above the bottom bar and the FAB, centered. The color scheme has Material 3's inverse, container, scrim and bright/dim roles.

**Shapes and borders** (D1054). A `Shape` is Compose's: `Shape::Rectangle` (`RECTANGLE_SHAPE`), the corner-based shapes as values (`RoundedCornerShape`, `CutCornerShape`, `AbsoluteRoundedCornerShape`, `AbsoluteCutCornerShape` in `foundation::shape`, taking one corner size or four: a `Dp`, pixels as an `f32`, a percent as an `i32`, or a `CornerSize`; `CIRCLE_SHAPE`, `ZERO_CORNER_SIZE`; `copy` and `corners` as `CornerBasedShape`'s), or `Shape::Custom` for any other (`GenericShape(|path, size, direction| …)`, or an app's `CustomShape`). Its outline is Compose's `Outline`: a rectangle, a rounded rectangle, or a path (`Outline::Generic`, a cut corner's or a generic shape's). Corner sizes resolve as Compose's `CornerBasedShape`: the two start corners scale down together when they're more than the shorter side, and the two end corners (so a 40 px top start with no bottom start stays 40 px on a 50 px box), a negative one panics, and the relative shapes mirror right to left. Backgrounds, borders, clips, graphics layers and shadows take any shape: a path outline is drawn as a path and clipped to as one (`DrawPath`, `ClipPath`; a layer clipping to a path clips its content with `ClipPath`, hit testing follows the path), its shadow is the path's on desktop; on Android the path is the layer's render node's outline (`Outline.setPath`, D1055; the layer keeps a built-in shape's while its shape, size, direction and density stay, D1059, and makes a custom shape's on each update, as it may read state, D1063), clipped to by the node where it can (API 33 on), by the node's recording otherwise, as Compose's, and casting its shadow. `Modifier.border(width, color)`, `border_with(width, brush, shape)` and `border_stroke(BorderStroke, shape)` (`BorderStroke(width, brush)`) draw as Compose's `BorderRenderer` (public, `draw_border(scope, width, brush, outline)`): inside the outline's bounds, `Dp::HAIRLINE` one pixel, an unspecified or negative width nothing, a fractional width rounded up, the shape filled when the stroke is more than half the shorter side; a rounded outline with corners that differ, or smaller than half the stroke, is the outline less the one inside the stroke (a path difference), a path outline a stroke twice as wide clipped to the path.

**Shadows.** `Modifier.shadow(elevation)` and `shadow_with(elevation, shape, clip, ambient_color, spot_color)` are a graphics layer with that elevation, shape and clip, as Compose's (none without an elevation or a clip; `clip` defaults to an elevation above 0). The layer casts its outline's shadow under its content, even with nothing in it: on Android a render node's elevation, outline and shadow colors, drawn by HWUI in the reordering section (`enableZ`) its parent's recording puts around it, lit by the window's light, as Compose's (D524); on desktop a `DrawShadow` op in the layer's operations, Skia's `ShadowUtils` with Compose Desktop's light (300 dp above the window's top, 600 dp up, 800 dp wide) and alphas (3.9 % ambient, 19 % spot, faded with the layer). Material's `Surface` is Compose's `Modifier.surface`, in its order: a layer casting its `shadow_elevation`'s shadow (not clipping), its border, its color (`tonal_elevation` tints the surface color with the surface tint, summed through nested surfaces, as `surfaceColorAtElevation` and `LocalAbsoluteTonalElevation`), then `clip(shape)` around its content (D526). A card is one clipping layer, an elevated card adds its 1 dp shadow's; the FAB has its 6 dp shadow and menus their 3 dp one; a button's or card's elevation follows its press, hover and focus, animated and read in composition as Compose's (`shadowElevation(enabled, interactionSource)`; no draw node of its own), as material3 1.4's `animateElevation` with its `ElevationDefaults`: to a new interaction's elevation in 120 ms with `FastOutSlowInEasing`, back from a hover in 120 ms and from a press, a drag or a focus in 150 ms, both `CubicBezierEasing(0.4, 0, 0.6, 1)`, the spec picked by the interaction entered or left, and at once with neither (D526). On Android the shadow's node is drawn between `enableZ` and `disableZ`, as Compose's `AndroidGraphicsLayer.draw`, its parent's recording drawn again when it starts or stops casting one (`Group.drawnBy`); `DRAW_SHADOW`'s operands are skipped by the replayer, as no record holds one (D524).

**Images.** `ImageBitmap` holds premultiplied RGBA pixels in an `Arc`, made from raw pixels or decoded by the backend (`compose_skia::decode_image`, PNG, JPEG, WebP, …, as the desktop's `decodeToImageBitmap`). `DrawScope::draw_image` records a `DrawImage` op (a source and destination rect and an alpha); Skia makes its image once per bitmap and forgets it the frame after the bitmap is dropped; a source rect is sampled strictly (nothing from outside it bleeds in), and a header claiming more than 2^28 pixels isn't decoded. Foundation's `Image(bitmap, content_description, modifier, alignment, content_scale, alpha)` is its pixels' size within the constraints scaled by its `ContentScale` (as Compose's painter node), draws scaled by a `ContentScale` (`Fit`, `Crop`, `FillBounds`, `FillWidth`, `FillHeight`, `Inside`, `None`) and aligned, clipped to its node, and reads as `Role::Image` with its description.

**Graphics layers.** `Modifier.graphics_layer(|layer| …)` applies `GraphicsLayerScope`'s properties to what follows it in the chain and the children, as `graphicsLayer`: alpha, scale, rotation, translation, a shadow (`shadow_elevation` in pixels, `ambient_shadow_color`, `spot_shadow_color`), a `shape` and whether it `clip`s to it, and a `compositing_strategy` (Compose's names and defaults; the block reads the layer's `size` and `density`). Its block runs while drawing, so the state it reads (an animation's value) changes the drawing without recomposing or measuring. `alpha`, `scale`, `rotate`, `clip`, `clip_to_bounds` and `shadow` are layers, as in Compose (`clip(shape)` is `graphicsLayer(shape = shape, clip = true)`, `alpha(a)` one clipping to its bounds, none at 1; `rotate(0)` and `scale(1)` none, D523). Each layer is a group of the display list (below), as each of Compose's is a layer: when it is its node's first drawing modifier (nothing drawn before it in the chain), its properties are its node's repaint boundary's, as a `RenderNode`'s: its block's reads are observed apart, and a write to them computes the properties again without drawing the layer's content again (no version changes). A layer after a drawing (`background(…).clip(shape)`, a surface's) is an inner layer: a group of its own inside its node's drawing, holding what follows it in the chain and the children, drawn by reference where it is (its key flagged, `render::INNER_LAYER_KEY`); what draws its node draws the drawings before it, and a change inside it (its block's reads, a child's drawing or move, its node's measurement for a state it read) draws it again, not them, and a state read before it draws them again, not it (D522). Its key is `render::INNER_LAYER_KEY` (bit 63) with a counter, owned by its node (`UiTree::inner_layer_owners`) and kept by chain index across modifier updates; what its block or its content read is observed apart (`Observation::InnerLayers`), and a frame listing it records it again in place if dirty (`list_inner_layer`); what's before it draws again without it (`invalidate_draw_before_inner_layers`), and a child's move, coming or going, a z-order change or its node's measurement draws it alone (`invalidate_children_draw_of`, `invalidate_layout_of`), unless a layer's size changed. A group that starts or stops drawing anything (a shadow given to an empty layer, or taken) gets a new version, so the record naming it names it, or no longer. A node is a boundary only when its first drawing modifier is a layer or it has `repaint_boundary`, so `background(…).clip(…)` adds no node, as Compose draws the background in the parent's layer. `CompositingStrategy::Auto` draws an alpha below 1 offscreen (Android: `setHasOverlappingRendering(true)`, HWUI's save layer; desktop: `SaveLayerAlpha`), `Offscreen` always (a compositing layer), `ModulateAlpha` never (each drawing's alpha multiplied: Android's `setHasOverlappingRendering(false)`, desktop's walk fading paints, text and shadows in layers of their own). A clip clips hit testing too, as Compose's layer's `isInLayer` (`GraphicsLayerNode::hit_clip`; hit testing runs a layer's block for its real size and density, `ModifierNode::hit_clip_at`, D523). `LayerProperties` carries the layer in its group's coordinates (`outline`, `casts_shadow`, `offscreen`, `modulated_alpha`). Desktop matches Compose Desktop's `SkikoGraphicsLayer`: `Auto` saves a layer for an alpha below 1, `Offscreen` always, `ModulateAlpha` never, and an offscreen layer inside a modulated one is composited as one at the modulated alpha, its content at full alpha, as HWUI and Skiko fade a child node's layer (D528). There are no `rotation_x`/`rotation_y`, camera distance, render effects, blend modes or color filters (nothing renders them yet). On Android, a clip to an outline whose corners differ (a path) clips the node's recording to the path on API 29 to 32, where an outline path can't clip, as Compose's `usePathForClip` (D525). The block isn't memoized by the macro (its closure takes a `&mut` scope, which a `Callback` can't hold): remember the modifier for a callee to skip. Hit testing doesn't follow the transform yet. Clips inside a drawing (`DrawScope`'s `clip_rect`, `clip_path`) stay operations of it, as Compose's canvas clips.

**compose-rs's optimizations.** What compose-rs does beyond Compose's rendering is a flag of `Optimizations` (`compose_ui::platform`, one table: `Optimization::ALL`). The default is the `recommended` set (D610; it was none, Compose's rendering, D581); `none` is Compose's rendering, which a benchmark against Compose sets so it measures the same work. A host sets them (`UiHost::set_optimizations`; Android's `ComposeRsView.optimizations`, desktop's `WindowOptions::optimizations`, `set_optimizations` or `COMPOSE_OPTIMIZATIONS`), and renderers read them. `single_drawing_fade` (off) fades an `Auto` layer holding one drawing with a paint by that paint instead of offscreen, the same pixels (D153, D157, D521); `performance_hint` (off) is Android's hint session (D390, D500); `reuse_paragraph_at_same_layout_width` (off) keeps a text's paragraph at the same layout width (D551). D520 records the mechanism.

**Repaint boundaries.** A node whose first drawing modifier is a graphics layer is a repaint boundary, as Compose's layer (a `RenderNode` on Android); so is one with `Modifier.repaint_boundary()`, a layer without properties, and every lazy item; an inner layer is a group of its own too (above). What a boundary draws, its children included, is a group of the display list (`DisplayList::groups`), in its own coordinates: a renderer can keep the group's recording while its operations stay the same, so a scrolled item, or one beside an animation, isn't recorded again (Android's replayer does, D154, D157).

Each boundary keeps what it drew, as Compose's layers keep their recordings (D155; a change marks the nearest boundary at or above it, an overlay stopping the walk, as it's drawn at the root; a layer with nothing to draw records no operations): a draw records what's outside every boundary, the boundaries in it by reference (`DisplayList::boundaries`: where each is drawn), then lists each boundary's group, nested boundaries included, without running its draw code. A group holds its boundary's recording by reference (`DrawGroup::content`, an `Arc` shared with the boundary, which records into it in place once the frames sharing it are gone), not a copy of its operations (D270): the frame is a tree, the groups listed depth first (`descendants`), which renderers walk. Skia draws a group's content where its boundary is, in a save of its own (an unbalanced clip stays in it, as in a render node); Android's serializer copies a kept group's record without reading its operations. `DisplayList::flatten` copies it all into one list (`FlatDisplayList`, each group a range of its operations), for tests and dumps (`UiHost::display_list` and `dump` give it). A boundary is drawn again only when something it drew from changed: a state read while drawing a node in it (up to the boundaries inside it) is written; a node in it is measured, or moves inside it, or its modifier changes; a child is added or removed; a handler asks (`EventContext::invalidate_draw`: a press, a focus, a selection); the density changes; or `UiTree::invalidate_draw` asks for everything. Moving the boundary itself (a scroll) is its parent's operations and keeps it. State written while laying out (a lazy list's or a scroll's measured state, a hover the layout moved) is applied just before drawing, so it's drawn in the frame that wrote it; a measurement it invalidates waits for the next frame. Data passed from one node's measure to another node's drawing without state (an `Rc<Cell>`) is stale when the writer and the reader are in different boundaries: measuring the writer draws its own boundary again, not the reader's. Material's `TextField` (its label's width and start, for the outline's cut) keeps the writer and the reader in one node; the tab rows write their tabs' positions in their measure for the indicator's `tab_indicator_offset`, which reads them in its own measure, later in the same pass. Its group's `version`, from a counter of the tree, changes when it's drawn again or a boundary inside it changed version, so a renderer keeps a recording by key and version without comparing operations. A graphics layer's properties are its group's `layer`, outside its content: Skia applies them as operations around it (`LayerProperties::operations`: `Save`, `Transform`, `ClipRect`, `SaveLayerAlpha`, each if needed, then their restores; a flattened group has them at `layer_start..start` and `end..layer_end`); Android sets them on the group's render node, so a layer-only animation records nothing again (D157). A boundary a frame drew that is composed and no longer placed (a lazy list's item kept beside the wanted ones, D375; any unplaced child left composed) has its group and its nested ones listed apart in each frame while it stays so and none of them changed (`DisplayList::kept`, outer before inner; the 8 most recent, `KEPT_CAPACITY`, noted from the last frame's groups), for a platform that asks (`UiHost::set_keep_unplaced_groups`: Android): no boundary draws it, nothing in it runs, and Android keeps its render nodes recorded, so the frame placing it again draws them by reference (D380). One that changed (it or a nested one), or went, is no longer listed: the frame placing it draws it.
Each boundary keeps what it drew, as Compose's layers keep their recordings (D155; a change marks the nearest boundary at or above it, an overlay stopping the walk, as it's drawn at the root; a layer with nothing to draw records no operations): a draw records what's outside every boundary, the boundaries in it by reference (`DisplayList::boundaries`: where each is drawn), then lists each boundary's group, nested boundaries included, without running its draw code. A group holds its boundary's recording by reference (`DrawGroup::content`, an `Arc` shared with the boundary, which records into it in place once the frames sharing it are gone), not a copy of its operations (D270): the frame is a tree, the groups listed depth first (`descendants`), which renderers walk. Skia draws a group's content where its boundary is, in a save of its own (an unbalanced clip stays in it, as in a render node); Android's serializer copies a kept group's record without reading its operations. `DisplayList::flatten` copies it all into one list (`FlatDisplayList`, each group a range of its operations), for tests and dumps (`UiHost::display_list` and `dump` give it). A boundary is drawn again only when something it drew from changed: a state read while drawing a node in it (up to the boundaries inside it) is written; a node in it is measured, or moves inside it, or its modifier changes; a child is added or removed; a handler asks (`EventContext::invalidate_draw`: a press, a focus, a selection); the density changes; or `UiTree::invalidate_draw` asks for everything. Two differences from Compose follow, kept (D1164): a node measured again draws its boundary again even at the same size and place (Compose's draws again only what resized or moved, the nodes that draw what their measurement changed invalidating their drawing themselves), and the root isn't a boundary (Compose's root has a layer), so what's outside every boundary is recorded on every draw. Moving the boundary itself (a scroll) is its parent's operations and keeps it. State written while laying out (a lazy list's or a scroll's measured state, a hover the layout moved) is applied just before drawing, so it's drawn in the frame that wrote it; a measurement it invalidates waits for the next frame. Data passed from one node's measure to another node's drawing without state (an `Rc<Cell>`) is stale when the writer and the reader are in different boundaries: measuring the writer draws its own boundary again, not the reader's. Material's `TextField` (its label's width and start, for the outline's cut) and `TabRow` (its tabs' positions, for the indicator) keep the writer and the reader in one node. Its group's `version`, from a counter of the tree, changes when it's drawn again or a boundary inside it changed version, so a renderer keeps a recording by key and version without comparing operations. A graphics layer's properties are its group's `layer`, outside its content: Skia applies them as operations around it (`LayerProperties::operations`: `Save`, `Transform`, `ClipRect`, `SaveLayerAlpha`, each if needed, then their restores; a flattened group has them at `layer_start..start` and `end..layer_end`); Android sets them on the group's render node, so a layer-only animation records nothing again (D157). A boundary a frame drew that is composed and no longer placed (a lazy list's item kept beside the wanted ones, D375; any unplaced child left composed) has its group and its nested ones listed apart in each frame while it stays so and none of them changed (`DisplayList::kept`, outer before inner; the 8 most recent, `KEPT_CAPACITY`, noted from the last frame's groups), for a platform that asks (`UiHost::set_keep_unplaced_groups`: Android): no boundary draws it, nothing in it runs, and Android keeps its render nodes recorded, so the frame placing it again draws them by reference (D380). One that changed (it or a nested one), or went, is no longer listed: the frame placing it draws it.

## Animation

`compose::animation` is Compose's `animation` and `animation.core`. An `Animatable` holds its value in state and animates it with tasks ([04](04-runtime.md)): `animate_to(target, spec).await` takes a step each frame (`with_frame_nanos`) along a spec, `tween` (duration, delay, easing: Compose's curves, cubic Béziers solved as its `CubicBezierEasing`, to the bit, their vertical range computed when made, D808, D815), `spring` (Compose's damped-spring equations, keeping the velocity across interruptions, and ending at the duration Compose's estimation gives for it to stay within its visibility threshold, per component: 0.01 unless the spec has one, `spring().visibility_threshold(Dp(0.4))`), `snap`, `keyframes(|frames| { frames.duration_millis = 400; frames.at(time, value).using(easing); })` (as Compose's `keyframes { durationMillis = 400; value at time using easing }`, with `at_fraction`; two specs built alike equal, D816), `repeatable` or `infinite_repeatable` (of a tween, keyframes or snap, with a `StartOffset` in their `_with` forms), `InterruptionAwareAnimationSpec::new(spec, interruption_spec)` (the second when it interrupts a running animation, D809), and specs and easings of an app's own (`AnimationSpec::custom`, `DurationBasedSpec::custom`, `Easing::custom`; specs are `Clone` values holding `Rc`s, D816), per component of the value's `AnimationVector` (one to four floats: `f32`, `i32`, `Dp`, `DpOffset`, `Offset`, `IntOffset`, `Size`, `IntSize`, `Rect`, and `Color` in Oklab, as Compose's converters). Every spec is a `VectorizedAnimationSpec`, evaluated at a play time as Compose's `Vectorized*Spec`s are, to the bit (D800), and `TargetBasedAnimation` binds one to its start, target and initial velocity (Compose's `Animation`): an `Animatable` plays one, at its target with the spec's end velocity once its duration is over. `animate_decay(velocity, &exponential_decay(…))` throws the value at a velocity until it slows under a threshold (a `DecayAnimation`, D807; `spline_based_decay(density)` and `remember_spline_based_decay()` decay as Android's flings, D820; foundation's flings decay along it, D826), and `update_bounds` keeps the value within bounds, an animation reaching one ending with `AnimationEndReason::BoundReached`; `animate_to_with` and `animate_decay_with` call a block each frame. Without an `Animatable`, `animate(…)`, `animate_value(…)` and `animate_decay(…)` call a block each frame, and an `AnimationState` keeps a value its `animate_to` and `animate_decay` move (D819). A new animation interrupts the running one, which ends with `AnimationEndReason::Interrupted` where Compose throws a cancellation; the new one starts at the frame the old one last set the value at, as Compose's (`lastFrameTimeNanos`), so it's one frame further along at the next frame. The default springs of `animate_dp_as_state` and its siblings carry the type's threshold (`Dp::VISIBILITY_THRESHOLD`, 0.4 dp; a pixel for offsets, sizes and rects; 1 for integers), as Compose's. `animate_float_as_state(target)` and its siblings follow a target, `remember_infinite_transition()` animates forever (one task per transition sets all its values each frame, as Compose's `InfiniteTransition`; a value starts at the first frame after it enters the composition, and again when its initial or target value changes, not its spec alone, as Compose's (D420, D822); its values register with a `DisposableEffect` and change with a `SideEffect`, as Compose's `updateValues`; a value's start is a frame time, not the transition's play time, so a value moved to another transition goes on where it was, where Compose's runs on the transition's clock; values are computed without velocities, by the spec's `value_from_nanos` (Compose's `getValueFromNanos`); checked frame by frame against a verbatim copy of the task-per-value version, `crates/compose-animation/tests/suite/infinite.rs`), and `AnimatedVisibility(visible, enter = fade_in() + expand_vertically(), …)` animates content in and out, keeping it composed while it leaves, as Compose's (D804): the visibility drives a transition and the content a child transition of `EnterExitState`s whose deferred animations animate the real alpha and scale (in a graphics layer), size and slide offset (in pixels, the content measured at its full size) along each part's spec; `visible` is a `bool`, a `MutableTransitionState<bool>`, or either with the `ColumnScope` or `RowScope` it's in, `(column, visible)`, whose defaults expand and shrink along it; the content gets an `AnimatedVisibilityScope`; `unveil_in()` and `veil_out()` animate a scrim over the content (D814); `transition.AnimatedVisibility(|state| …, …)` shows content for some of a transition's states, on its clock (D812); `Crossfade(target_state, …)` fades one state's content into the next's; `AnimatedContent(target_state, …)` has the new state's content enter as the old one's exits (`transition_spec(scope)` gives an `enter.together_with(exit)` `ContentTransform`, the scope an `AnimatedContentTransitionScope` with the change, the alignment and `slide_into_container`/`slide_out_of_container`, D817; Compose's default fading and scaling in after 90 ms while the old fades out, the container's size animating, or as large as the largest content without a size transform; contents are measured with the container's constraints; each content keeps the enter and exit of the change that brought it in or took it out, and shows while its state is the transition's current or target state, as Compose's, D805), the container's size animating on the transition along its `SizeTransform`; the content gets an `AnimatedContentScope` and its state, `content_key` tells contents apart, a new target of the same key taking a content over without animating, `ExitTransition::KEEP_UNTIL_TRANSITIONS_FINISHED` holds a content until the transition ends, and `scope.animate_enter_exit(enter, exit, label)` animates a child with its content (D817); `transition.AnimatedContent(…)` shows a transition's states' contents (D812); `update_transition(target_state, label)` (or `remember_transition(&MutableTransitionState, label)`) animates several values together on one state's change (`transition.animate_dp(|segment| spec, |state| …)` and friends, the spec chosen by the `Segment`, `segment.is_transitioning_to(&a, &b)`), as Compose's `Transition`: one task per transition sets its play time and every value still animating each frame, each value a `TargetBasedAnimation` delayed by the play time it was given at, so a value first composed mid-way starts then from its value for the state the transition was at (D803); its `current_state` reaches the target once they all end (on an interruption, the state the change was heading for, which is where the next change's segment starts), `is_running` a state read, a value interrupted mid-way goes on along a spring of its type's threshold (unless its spec is a spring), as Compose's `interruptionSpec`, and `create_child_transition(label, |state| …)` makes a transition of a derived state playing on its parent's clock, and `animations()` and `transitions()` list its values and children for tools, with their labels (`animate_*_with(…, label, …)`, D813, D818); a transition remembered with a `SeekableTransitionState` follows a gesture instead: `seek_to_with(fraction, target).await` sets its values at that fraction of its total duration, `animate_to(target)` animates the fraction on to 1 and `snap_to(target)` jumps, one call at a time (a new one cancels the task of the one running, as Compose's `CancellationException`), a change of target mid-way taking the values on from where they are, the content seeked from staying while they go on (D821, D823, D824); the transition writes its target, segment and current state as it composes, as Compose's, with plain `set`s (D802, D712); `Modifier.animate_content_size()` animates a node's size to its content's, placing the content by an alignment and telling a listener when an animation finishes in `animate_content_size_with(spec, alignment, finished_listener)` (D811); `DeferredTargetAnimation` animates to the targets it's given from a task, the first taken at once (D810). `Animate::same_value` lets a type compare its values itself: `Color` compares its packed value, as `Color.equals`, where the default compares the vectors (for a color, an Oklab conversion of both: 6 `powf`s and 6 `cbrt`s) (D422). Animated values are read where they are used: in a graphics layer's block (a redraw) or a layout (a re-measure), not in composition, so a frame recomposes nothing.

## Material 3 components

What the components in `compose::material3` do beyond their Compose counterparts' parameters (the modules table below lists them).

- **Standard sheets** (D1028). `BottomSheetScaffold` places a top bar, a body (given the peek height as padding), a sheet at the state's offset and snackbars above the sheet while it peeks; `BottomSheet` is the sheet alone, in place. Their `SheetState` is `ModalBottomSheet`'s; a scaffold's by default can't hide.
- **Ripples** (D1025, D1030). `MaterialTheme` provides `ripple()` as `LOCAL_INDICATION`; its node (`ripple.rs`) draws a press's circle over the content, growing from where it went down to the center, with the state layers of hovers, focuses and drags, or an inset ring for a focus where `LOCAL_RIPPLE_THEME_CONFIGURATION` says, all following the `MotionDurationScale`. At rest it draws nothing. It's Compose's common node, on Android too, where Compose's is a `RippleDrawable` with another look. `RippleOptions` has `ripple`'s parameters; `LOCAL_RIPPLE_CONFIGURATION` a subtree's color, ring colors, or `None` to turn them off.
- **Theme values.** `MaterialTheme` takes a `ColorScheme`, a `Typography` and `Shapes` (or, what a nested theme keeps of the enclosing one, their shared `Rc`s: `ThemeValue`, D1024) and compares them by value, and `LOCAL_COLOR_SCHEME`, `LOCAL_TYPOGRAPHY` and `LOCAL_SHAPES` share one `Rc` each with their readers, comparing values when a new one is provided (`SharedValueEqualityPolicy`), so a read copies nothing and an equal value made anew recomposes no reader (D1021, D1106, D1107).
- **Type scale and colors** (D570, D572, D573). The typography is built from Material 3 1.4.0's `TypeScaleTokens` (constants of `TypeScaleToken`: size, line height, tracking, weight), over `DefaultLineHeightStyle`; 1.4's tracking is body large 0.5 sp, body medium 0.2, body small 0.4, title medium 0.2, title small 0.1, label large 0.1, label medium and small 0.5, display large -0.2, none for the display, headline and title-large styles. Components take 1.4.0's color tokens: `OutlinedButton`'s label is on-surface-variant (`OutlinedButtonTokens.LabelTextColor`) and its outline the outline-variant color, at 10 % disabled (`OutlineColor`, `DisabledContainerOpacity`); the flat chips' outline is the outline-variant color (`AssistChipTokens.FlatOutlineColor`, `SuggestionChipTokens`, `FilterChipTokens.FlatUnselectedOutlineColor`); a linear indicator's track is the secondary container (`ProgressIndicatorTokens.TrackColor`); disabled filled and elevated buttons are on-surface at 10 % under on-surface-variant at 38 %, tonal ones on-surface 12 % and 38 %, text ones on-surface-variant 38 %. The indicators draw the tip's tracks (D1003): `LinearProgressIndicator` draws its track after the progress, past `gap_size` (`LINEAR_INDICATOR_TRACK_GAP_SIZE`, 4 dp by default) grown by the stroke for capped lines (`adjustedGapSize`), only when it starts before the end, then the stop dot (`ProgressIndicatorDefaults::draw_stop_indicator`; `draw_stop_indicator = Some(DrawStopIndicator::none())` leaves it out, as Kotlin's `drawStopIndicator = {}`); the indeterminate linear one draws its tracks around its lines past the gaps; the circular ones draw their track (the secondary container determinate, none indeterminate) past `gap_size` too. A chip draws its outline outside its clip, as Compose's `Surface` modifier orders them. Components the bench screens don't use (selection controls, segmented buttons, text fields, navigation) weren't audited against 1.4's tokens.
- **Drag handles** (D1032). `VerticalDragHandle` is a capsule growing when pressed or dragged, its values for each state in `DragHandleColors`, `DragHandleShapes` and `DragHandleSizes`. It shows a drag from its `interaction_source`, which `Modifier.draggable_with` takes; the drag itself is the app's `Modifier.draggable`.
- **Vertical and range sliders** (D1035). `VerticalSlider`'s `SliderState` knows its direction, `top_to_bottom`; `RangeSlider` and `RangeSliderState` have two thumbs, each with its own keys and accessibility node, a gesture taking the nearer one; `SliderDefaults::centered_track` and `range_track` draw them.
- **Chips and shapes by state** (D1039, D1040). Every chip kind on `Surface` as Compose's, `ChipColors`, `SelectableChipColors`, `ChipElevation`, the `*ChipDefaults`; a `shapes` parameter (`ChipShapes`, `ButtonShapes`, `IconButtonShapes`, `IconToggleButtonShapes`) moves corners with the press or selection through `remember_animated_shape`; `ButtonDefaults` and `IconButtonDefaults` have the expressive sizes.
- **FABs** (D1042). `MediumFloatingActionButton`, the sized extended FABs, each with a `…Content` for content of its own, and `Modifier::animate_floating_action_button` to show and hide one.
- **Drawers that aren't modal** (D1043). `DismissibleNavigationDrawer` pushes the content aside, `PermanentNavigationDrawer` is always there, each with its sheet. A `ModalDrawerSheet` or `DismissibleDrawerSheet` given its `drawer_state` stretches with the back gesture (D1049).
- **Exposed dropdown menus** (D1044). `ExposedDropdownMenuBox` around a text field with `Modifier::menu_anchor(&scope, type)` and an `ExposedDropdownMenu`, as wide as the field and between the margins beside it; it takes the focus unless the field's typed in. `Modifier::on_preview_key_event` hears a key before what has the focus, from the root down.
- **Motion** (D1031). `MaterialTheme` carries a `MotionScheme`, six `AnimationSpec`s (`standard()`, `expressive()` or an app's own), read as `MaterialTheme::motion_scheme()`; a component's animations take its specs where it composes, its nodes through their elements. An inset ring takes the scheme; a state layer's tweens are constants, as in Compose. Selections animate on it too (D1034): a navigation item's indicator and colors, a list item's colors and corners (`remember_animated_shape`; made when they first change, D1036), a text field's label, border, placeholder and affixes, read in layout, draw and the label's scope, a segmented button's check.
- **The rest of the theme** (D1008). `ColorScheme` has the 12 fixed roles (the palettes' tones 90, 80, 10 and 30, the same light and dark) and `expressive_light_color_scheme()`; `content_color_for` matches in Compose's order, the fixed roles and `surface_bright`/`surface_dim` included, and the free `content_color_for(background)` falls back to `LOCAL_CONTENT_COLOR`. `Typography` has the 15 emphasized styles and its styles name the tokens' sans serif family (as Compose's `TypeScaleTokens` fonts; the measurers draw it as no family); `Typography::from_font_family` is `Typography(fontFamily)`, `with_default_font_family` fills the styles given without one. `Shapes` has `large_increased`, `extra_large_increased` and `extra_extra_large`, from `ShapeDefaults`. `LOCAL_TONAL_ELEVATION_ENABLED` turns surfaces' tint off below it; `ProvideTextStyle` merges into the current text style (`MaterialTheme` provides the body style through it); `MaterialExpressiveTheme` defaults to the expressive light scheme outside another expressive theme, and to the expressive motion scheme. `MaterialTheme::values()` reads the three as `MaterialThemeValues`, Compose's `LocalMaterialTheme.current`.
- **Styling parameters** (D180). Buttons, cards and FABs take Compose's styling parameters in Compose's order: `shape`, `colors`, `elevation` (`ButtonElevation`, `CardElevation`, `FloatingActionButtonElevation`), `border`, `content_padding`, `interaction_source`. Colors change with struct update syntax (`ButtonColors { container_color, ..ButtonDefaults::button_colors() }`) where Compose names arguments of `buttonColors(…)`, so the `…Defaults` constructors take none. A default that reads another parameter (the outlined button's, card's and icon button's border reading `enabled`; a segmented button's border and check icon reading `colors` and `selected`) is an `Option` whose `None` is Compose's default, since a `#[default]` can't name another parameter.
- **Clickable surfaces** (D181). Buttons, FABs, filled and outlined icon buttons, clickable cards and segmented buttons share the body of `ClickableSurface`, `SelectableSurface` or `ToggleableSurface` (D1010: the filled and outlined icon toggle buttons), so each has at least the 48 dp touch target, as Compose's clickable surfaces. `IconButton` and `IconToggleButton` take a `shape`; the icon buttons' disabled containers are on-surface at 10 % and the outlined ones' disabled outline at 38 %, the tip's tokens.
- **Icons and items** (D187). The icons are material-icons-core's 49 filled icons (Apache-2.0 path data), in one table of labels and path data, each parsed once per thread when first asked for, an icon's function a call with its index; `icons::default` stands for `Icons.Default`, and `icons::filled::all()` lists them. `NavigationRailItemColors` is `NavigationBarItemColors` (the same roles). A segmented button row lays its buttons out itself (each as wide as the widest, or sharing the row's minimum width, extra pixels to the first), without Compose's z-index raising the pressed one (their outlines are the same color).
- **Prefixes and suffixes** (D235). `TextField` and `OutlinedTextField` take `prefix` and `suffix` (after the icons, Compose's order) and `max_lines`, `min_lines` (after `single_line`): the prefix before the text and the suffix at its end, 2 dp from it, in the text's style and `TextFieldColors::prefix_color` and `suffix_color` (and the disabled ones), their alpha the label's float progress (always shown without a label), placed on the text's line. `BasicText` takes `on_text_layout` after `style` and `min_lines` after `max_lines`, as Compose's; Material's `Text` takes `min_lines` and `on_text_layout` before `style`.
- **Anchored drags** (D185). `ModalBottomSheet` and `SwipeToDismissBox` share an `Anchored` offset, as Compose's `AnchoredDraggableState`: anchors from the last layout, a drag clamped between them, a release settling by Compose's `computeTarget` (past 56 dp from the current anchor, or faster than 125 dp/s), and `confirm_value_change` able to refuse; the offset at rest follows its anchor as the layout moves it. The sheet is a focusable popup over the window (the scrim and Escape hide it, then call `on_dismiss_request`), shown by a `LaunchedEffect` once laid out. Its drags are its own `draggable`, and its content's scrolls drag it through a nested-scroll connection (up first, down with what the content leaves, flings settling it), as Compose's `ConsumeSwipeWithinBottomSheetBoundsNestedScrollConnection`. The scrim asks `confirm_value_change(Hidden)` first, and back on an expanded sheet that can rest half way takes it there. The sheet follows the tip's API (D1017): `SheetState::new(enabled_values, positional_threshold, velocity_threshold, initial_value, confirm_value_change)` and `remember_bottom_sheet_state(initial_value, enabled_values, confirm_value_change)` (the default) rest partially expanded at half the sheet's height, at most half the window's, whatever its height (Compose's `isBottomSheetPartiallyExpandedDeterministicEnabled`, on by default; compose-rs has no flag). Compose's deprecated legacy states (`SheetState(skipPartiallyExpanded, …)`, `rememberModalBottomSheetState`: half the window, only for a sheet taller than that) aren't here (D1019): a sheet that shouldn't rest half way takes `&[SheetValue::Hidden, SheetValue::Expanded]`. `show`, `expand`, `hide` and `partial_expand` ask `confirm_value_change` and animate with the motion scheme's springs (default spatial to show, fast effects to hide; drags settle on the default spatial one, a fling down slowing within 125 dp of the hidden anchor), `hide` and `partial_expand` panicking on a state without that value, as Compose's; new anchors take a state to its target at once unless it's animating (an empty sheet shown is expanded without moving, then reconciles with its content). `ModalBottomSheet` takes `sheet_gestures_enabled` (its drags and nested scrolls) and `properties` (`ModalBottomSheetProperties`: back and the scrim's click dismissing); a click on its drag handle expands it, dismisses it once expanded; the scrim fades on the default effects spring. `remember_bottom_sheet_state` and `remember_swipe_to_dismiss_box_state(initial_value, positional_threshold)` are saveable, as Compose's (their lambdas the first composition's: `remember_saveable` takes no inputs), and the sheet shows on entering only if it's hidden (a restored expanded sheet stays expanded). As Compose's `AnchoredDraggableState`, the offset has a settled value (where it last settled: the sheet's `current_value`, the box's `settled_value`) and a current value that follows a drag once it's half way to the next anchor (the box's `current_value`, the sheet's `is_visible`). `SwipeToDismissBox` follows the tip's API (D1001): no `confirm_value_change` (deprecated in Compose), `on_dismiss` hearing the direction once settled away, swipes only while settled in place, and a state resting at a disabled direction comes back in place.
- **List items** (D1004). `ListItem` is the tip's: the content (the headline) trailing, `ClickableListItem`, `SelectableListItem` and `ToggleableListItem` for Compose's interactive overloads (`on_long_click` on the three), each with `enabled`, `vertical_alignment` (`None`: Compose's default, centered under 60 dp of content height, else at the top), `shapes`, `colors`, `elevation`, `content_padding` (16 dp at the sides, 10 dp above and below); one merged semantics node. Its colors and shape follow its state (selected, pressed, focused, hovered, disabled) on the motion scheme (D1034); there's no dragged state (no drag interactions). A supporting text is taken for two lines from its height (over 30 sp), Compose's intrinsic heuristic, since compose-rs has no baselines to compare.
- **Tab rows** (D1005). `PrimaryTabRow`, `SecondaryTabRow`, `PrimaryScrollableTabRow` and `SecondaryScrollableTabRow` are the tip's: an `indicator` slot taking a `TabIndicatorScope` (`None`: Compose's default, a 3 dp pill as wide as the selected tab's content for the primary rows, a 3 dp line as wide as the tab for the secondary ones), a `divider` slot, `scroll_state` and `min_tab_width` for the scrollable ones. `Modifier.tab_indicator_offset(&scope, index, match_content_size)` (from `TabIndicatorModifiers`) places the indicator under a tab, moving and resizing to a new one with the theme's default spatial spec, as Compose's node; `tab_indicator_layout` measures it with the positions. The indicators are `TabRowDefaults::primary_indicator` and `secondary_indicator` (methods taking every argument: Rust has no default arguments outside the call macros). A scrollable row scrolls the selected tab to the middle a frame after its layout (its scroll's maximum is known then), with the same spring. A tab's color follows its selection with the default-effects spring (the fast one when deselected). A tab with a text and an icon centers them, where Compose places the text by its baseline (no alignment lines here). Compose's deprecated `TabRow` and `ScrollableTabRow` are gone.
- **Sliders** (D1006). `Slider(state, on_value_change, …)` is the tip's: a `SliderState` (`SliderState::new(value, steps, track_range)`, `remember_slider_state`, saveable; the value's setter coerces and snaps, the first value is kept as given) drawn as a 4 by 44 dp handle (half as wide while pressed or focused) on a 16 dp track split 6 dp around it, a stop dot at its end and the steps' ticks. `thumb` and `track` are slots taking the state (`None`: `SliderDefaults::thumb` and `SliderDefaults::track`); `SliderDefaults::track_with` takes the rest of Compose's `Track` parameters (`draw_stop_indicator`, `draw_tick` as `DrawSliderStopIndicator` and `DrawSliderTick` values, the gap, the inside corners, and `track_corner_size` for the overload whose corners shrink). A drag past the touch slop follows the pointer less the slop; left and right, page up and down, home and end move it; `SetProgress` snaps to the last of two nearest stops, as Compose's. A new value measures the slider again (compose-ui has no placement-only relayout), where Compose's places its thumb again only. No `RangeSlider`, `VerticalSlider` or `CenteredTrack` yet.
- **Semantics bounds** (D1007). A slider's semantics node is 10 dp wider than its layout on each side and a linear progress indicator's 10 dp taller, as Compose's `IncreaseHorizontalSemanticsBounds` and `IncreaseVerticalSemanticsBounds` (a "negative padding" layout, a merging semantics node, and the padding back): screen readers' boxes reach their minimum size, the layout stays.
- **Checkboxes** (D1009). `Checkbox` and `TriStateCheckbox` are the tip's: `interaction_source`, Compose's stroke overload as `checkmark_stroke` and `outline_stroke` (`Stroke`, `None` for 2 dp), every `CheckboxColors` field (`CheckboxDefaults::colors_with` for the six-color overload). The box's and the check mark's colors animate (the theme's motion scheme's effects specs, the fast one going out), the check mark draws in along its length (the default spatial spring), stays 100 ms after an unchecking, and gravitates to a line for the indeterminate state, as Compose's transition; disabled, the colors snap. The check mark is its two lines (their square ends meet at its right angle as the path's miter join would), the toggle around the touch target so all of it takes presses (Compose's, inside it, extends its hit test; compose-ui doesn't yet), so the node's semantics bounds are the 48 dp target where Compose's are the box. As Compose's with its `isCheckboxStylingFixEnabled` flag off, the default: 2 dp of padding, and the check mark's color the same disabled.
- **Alert dialogs** (D1011). `AlertDialog` is a `BasicAlertDialog` (a dialog of any content, 280 to 560 dp wide, its minimum passed on) of a surface with Compose's styling parameters (`shape`, `container_color`, the icon's, title's and text's content colors, `tonal_elevation`; `AlertDialogDefaults`), the buttons in the primary color and the label large style, laid out as Compose's `AlertDialogFlowRow`: a flow row in the other layout direction, so the confirm button ends the row, or tops the column when they stack.
- **Switches** (D1012). `Switch` is the tip's: the track a box with its border and background (their colors by the state, not animated), the thumb a child whose layout node (`ThumbNode`) animates its size and offset with the theme's fast spatial spec: 16 dp unchecked, 24 dp checked or with `thumb_content` (shown in it in the icon color), 28 dp while `interaction_source` is pressed (snapping); its state layer a 40 dp circle around it while pressed, focused or hovered, in the content color. Reused, it shows its value without animating. The toggle stays around the touch target, as the checkbox's (D1009).
- **Segmented buttons** (D1013). `MultiChoiceSegmentedButtonRow` lays out `CheckableSegmentedButton`s (Compose's checkable `SegmentedButton` overload, a toggleable surface) as the single-choice row does its `SegmentedButton`s; both take `content_padding` (`SegmentedButtonDefaults::CONTENT_PADDING`). A button rises over its neighbours by its interactions (pressed, focused, hovered) and 5 more while active, as Compose's `interactionZIndex`, so its border shows over theirs. Its content keeps the icon's room (`ICON_SIZE` and 8 dp) and, without an icon, moves the label back by half of it (animated with the fast spatial spring), as `SegmentedButtonContentMeasurePolicy`. The default check shows at once (Compose fades and scales it in).
- **Scrims** (D1018). `Scrim(content_description, modifier, on_click, alpha, color)` is Compose's: filling its container in `ScrimDefaults::color()` (the scrim color at 32 %) at `alpha()` (read while drawing), nothing without a color; with `on_click` (by default one doing nothing) it takes the pointer, a tap or the click action calling it, and has its description; without, neither. The drawer's and the sheet's scrims are the same node.
- **Menus** (D1016). `DropdownMenu` takes Compose's `properties`, `shape`, `container_color`, `tonal_elevation`, `shadow_elevation` and `border` (`MenuDefaults`: the extra-small shape, the surface container, 3 dp of shadow); it grows in from 0.8 of its size and fades in, and out again before it leaves, on Compose's transition (fast spatial and fast effects springs) from the side of its anchor (`calculateTransformOrigin`, recorded by the position provider). `DropdownMenuItem` takes `colors` (`MenuItemColors`, `MenuDefaults::item_colors()`: the icons in the on-surface variant), `content_padding` and `interaction_source`; its icons sit at the start of slots at least 24 dp wide, and its width when the menu asks is 112 to 280 dp (`size_in`); the menu's column is Compose's `Column` with `width(IntrinsicSize::Max)`, its children keeping their own widths. The segmented buttons' content layout answers intrinsics without its label's animation (D1013), which compose-ui's intrinsic measurement would otherwise move back and forth.
- **Dividers** (D1015). `HorizontalDivider` and `VerticalDivider` are Compose's: a `Canvas` as wide (or tall) as allowed and `thickness` thick, drawing a line of that width through its middle in `DividerDefaults::color()` (the outline variant); `DividerDefaults::THICKNESS` is 1 dp, and `Dp::HAIRLINE` gives no size and a stroke of no width, the renderers' one-pixel line.
- **Snackbars** (D1014). `ContentSnackbar` is Compose's content overload (`action`, `dismiss_action`, `action_on_new_line`, the action and dismiss content colors, `SnackbarDefaults`); `Snackbar(data, …)` builds one from its data, 12 dp in, with `action_on_new_line` and the colors too. One row is Compose's legacy `OneRowSnackbar` without baselines (compose-rs has no alignment lines: the text centered, 48 or 68 dp high); the action on a new line is Compose's `NewLineButtonSnackbar` (its flagged layout: the text 14 dp above and below, the buttons at the end 4 dp above the bottom), where its default legacy one places the text by its baselines. `SnackbarData::with_callbacks` makes data without a host, as implementing Compose's interface. The dismiss button has no tooltip yet.
- **Drawers** (D1002). `ModalNavigationDrawer` composes and measures its sheet even while closed, as Compose's (its width gives `DrawerState::current_offset`, minus the width closed), placing it only while shown; opened, the sheet's first focusable takes the focus. `DrawerState::new(initial_value, confirm_state_change)` and `remember_drawer_state(initial_value, confirm_state_change)` (saveable) can refuse a value: a drag let go settles back, the scrim doesn't close, and `open`, `close` and `snap_to` move the sheet but leave the value, as Compose's `anchoredDrag`. `is_animation_running` and `target_value` (the nearer value while dragged) are state reads. Compose's deprecated `animateTo(value, spec)` isn't public. `ModalDrawerSheet` takes `window_insets` (padding, zero by default).
- **Top app bars** (D186). One `TopAppBarLayout` measure policy lays out the single-row bars and both rows of the medium and large ones; its height, the titles' alphas and the container's color are read from `TopAppBarState` while measuring and drawing, so collapsing measures and draws again only. With no alignment lines, a bottom-arranged title's baseline is taken at 80 % of its height (the text measurer's, for a line). `TopAppBarDefaults::pinned_scroll_behavior()` and its siblings take no arguments (state and scope remembered at the call); `TopAppBarScrollBehavior::pinned(state, scope)` and its siblings take a given state. There is no `can_scroll`, no fling decay before the settle (a spring to the nearer end), and the bar itself isn't draggable.

## Popups and dialogs

`Popup` and `Dialog` (`compose::ui`, as Compose's `ui.window`) show content over the rest of the window. Compose gives them windows or layers of their own; here they are **overlays**: nodes composed where they are called (so composition locals, state and remembered values follow) whose modifier (`Modifier.overlay(provider, …)`) makes the tree place them in the root after layout, with a position provider (`PopupPositionProvider`: `AlignmentOffsetPositionProvider` for `Popup(alignment, offset)`, a menu's below-or-above provider), from their anchor's bounds and the window's size. The anchor is the layout around the popup inside its modifiers (as `parentLayoutCoordinates`), and popups are measured with the window's size, again when it changes. They are drawn after everything else and hit before it (a point in an overlay is its, handled or not); in semantics they are roots of their own, never merged into what's around their anchor. A popup with `on_dismiss_request` gets an outside catcher under it, dismissing it on a press outside: a focusable popup takes that press (what's beneath gets nothing while it shows), a non-focusable one lets it through, as Android's non-focusable popup windows. A focusable popup is modal for input whatever its dismiss settings, takes the focus, and back (Escape on desktop) dismisses it (`dismiss_on_back_press`), as on Android a popup window that takes focus gets the back key; a non-focusable one doesn't take back. A dialog is modal: its content centered (24 dp from the window's edges) over a scrim that takes every event (a click on it dismisses), taking the focus. While a dialog or focusable popup shows, Tab cycles through its focusables only (the overlay itself isn't a stop), keys stay in it (they never reach the handlers around its host), and with nothing focused they go to it, as a window of its own; back goes to it before what's beneath (D220); opening it scrolls nothing around its host, and once it's gone, what had the focus before gets it back. Non-focusable popups take no focus. `LOCAL_DENSITY` (as `LocalDensity`) gives composition the window's density. Material's `AlertDialog`, `DropdownMenu` and `DropdownMenuItem` are built on them; a menu is as wide as its widest item (112 to 280 dp, asked with `MeasureScope::max_intrinsic_width`), scrolls when taller than the window, and is placed as Compose's `DropdownMenuPositionProvider` (at the anchor's start, else its end, else the window's; below, else above, keeping 48 dp from the window's top and bottom, and always within the window); its `scroll_state` is remembered where it's called, so a reopened menu keeps its scroll.

## Back, saved state and the platform's values

- **Back.** `BackHandler(enabled, on_back)` (`compose::ui`, as AndroidX's `BackHandler`) registers with the host's `NavigationEventDispatcher` (`LOCAL_NAVIGATION_EVENT_DISPATCHER_OWNER`, `compose::navigation_event`, D845) while it's in the composition, enabled while its lifecycle is started, and `PredictiveBackHandler(enabled, on_back)` takes the gesture with its progress, its task collecting a `BackProgress`; `LOCAL_ON_BACK_PRESSED_DISPATCHER` is how back reaches them; a back press goes to the innermost enabled one: those in dialogs and focusable popups first (the deepest first, as their own windows get back before the window beneath), then the one registered last (composed last), as AndroidX's dispatcher (D220). The platform calls `UiHost::on_back_pressed()` (Android's back gesture or button), and Escape that no focused node consumes goes back too (`send_key`), which is how desktop dialogs close on Escape. An entry leaving a `NavDisplay` disables its own through its lifecycle. `has_enabled_back_handlers()` tells the platform whether to intercept back at all: Android lets the activity finish when no handler is enabled. A `Dialog` and a focusable `Popup` take back while they show (their own always-enabled handler), dismissing only if `dismiss_on_back_press`: back never goes past them. Material's components go through it, so Android's back works as Escape does (D241): an open or opening `ModalNavigationDrawer` closes (enabled while its target is open, as Compose's; its handler is composed after the content's and before the sheet's content, so it goes before the content's handlers and after those in the drawer, as Compose's `DrawerPredictiveBackHandler`); a `ModalBottomSheet` (a focusable popup) goes from expanded to half way, then hides and is dismissed; a `DropdownMenu` (a focusable popup) is dismissed before what's beneath it.
- **Saved state.** `remember_saveable(|| mutable_state_of(0))` (`compose::runtime`, as Compose's `rememberSaveable`) remembers as `remember` does, and registers the value (a remembered `OwnedState`'s value) with the host's `SaveableStateRegistry` (`LOCAL_SAVEABLE_STATE_REGISTRY`) while it's in the composition. `UiHost::save_state()` collects every registered value as a `SavedState` (`to_bytes` encodes it: booleans, integers, floats, strings and lists, what an Android `Bundle` holds); a new host given it (`restore_state`, before its first frame) hands each value back to the `remember_saveable` at the same place, found by `current_composite_key_hash()` (the keys of the groups from the root, as Compose's `currentCompositeKeyHash`: a composable's key, a `key(…)`'s value, a branch's region), values at the same place told apart by their order (D223). Each group's ordinal among its earlier siblings of the same key is part of the hash: group keys are per composable, not per call site, so two calls of one composable are told apart by their order, and values registering out of order (one call's branch opening first) don't swap. `perform_save` starts from the values restored and not yet taken back, as Compose's `performSave`. The saved tree's text variant is `Text`: a variant named `String` makes rustc print `std::string::String` in diagnostics. Values convert with a `Saver` (`saver(save, restore)` with `remember_saveable_with(saver, init)`); the `Saveable` types (integers, floats, `bool`, `char`, `String`, `Option`, `Vec`, tuples) need none (`AutoSaver`, Compose's `autoSaver`). A value that can't be restored (saved by another version of the app) is computed again. `remember_lazy_list_state`, `remember_lazy_grid_state` and `remember_scroll_state` are saveable, as Compose's; text fields hold no state of their own to save (their value is the app's, which `remember_saveable` keeps, as in Compose).
- **Saveable state holders.** `remember_saveable_state_holder()` (`compose::runtime`, as Compose's `rememberSaveableStateHolder`) keeps the saveable state of content that leaves the composition, by key: `holder.SaveableStateProvider(key, || …)` composes content with a `SaveableStateRegistry` of its own, provided to it; when the content leaves, the holder keeps what that registry saves, and gives it to the content next composed with the key; `holder.remove_state(key)` forgets it (content in the composition then leaves nothing behind). The holder saves what it keeps, and what its content in the composition holds, across the host's recreation. Keys are any `Hash` value, kept as their stable FNV hash. A provider is a movable group (the key's hash as its data key) holding its registry; a remember observer in a group after the content's registers it with the holder and, when forgotten, saves the registry into the holder (a removed subtree's observers are forgotten in the reverse of its pre-order, so this runs before the content's values unregister). Values in a provider are found by their composite key hash *within* it (the walk stops at the provider's group, unlike Compose's), so content that leaves and comes back under another parent (an animated container's next slot) finds them; content moved within one pass doesn't, as in Compose. Each lazy list item's content is in a provider of its key (Compose's `LazySaveableStateHolder`), so items scrolled away and back keep their `remember_saveable` values, saved with the list across recreation; as in Compose, they're kept for the list's life, so thousands of items with saveable state grow the saved state (an Android `Bundle` holds about 1 MB). A key composed at two places at once panics in debug builds, as Compose throws (D290). A provider is a `ReusableContent(key)`, as Compose's (D430): matched by its place, not its key, so content with another key composed in its place reuses its groups and nodes (its values computed anew); providers in a loop need a `key(…)` each to move with their keys, as in Compose.
- **Navigation.** `compose::navigation` (the `compose-navigation` crate, as Navigation 3, D1400, D1405): a `NavBackStack<T>` (`remember_nav_back_stack`, saved; a `Copy` handle to a `SnapshotStateList` of the app's keys, `Saveable`) is the state; an entry provider, any `Fn(T) -> NavEntry<T>`, makes a `NavEntry` of each key, its `content_key` by default what the key prints; `NavEntryDecorator`s wrap what entries show, keeping one content for a place so entries stay equal (D1402); and `NavDisplay!(back_stack, entry_provider = …)` shows them as `Scene`s, made by `SceneStrategy`s or else a single pane, in a deferred `AnimatedContent`: a predictive back gesture moves them by its progress, a pop animates what's popped with its entry still composed, each scene has a lifecycle owner, resumed once settled, and `OverlayScene`s (`DialogSceneStrategy`) show above it. It's restartable, reading a state list itself, and a change of the stack shows again only what's new (D1408); `ViewModelStoreNavEntryDecorator` gives each entry its view models (D1409). `ResultEventBus` passes results back, and `UriDeepLinkMatcher` makes keys and back stacks of URIs (D1414).
- **The configuration.** `LOCAL_CONFIGURATION` (`Configuration`: the screen's width and height in dp, its orientation, the font scale, the density, and night mode: the parts of Android's `Configuration` apps read) is the host's (`UiHost::set_configuration`); foundation's `is_system_in_dark_theme()` reads its night mode, so `MaterialTheme!(color_scheme = if is_system_in_dark_theme() { dark_color_scheme() } else { light_color_scheme() }, …)` follows the system, as the gallery and feed examples do (D225).
- **Window insets.** The host's insets (`PlatformWindowInsets`, a state; `UiHost::set_window_insets`: each of Android's types, those ignoring visibility, the keyboard animation's source and target, which types are hidden, in pixels; zero on desktop; `set_window_cutout_path`, the cutout's outline) are what foundation's `WindowInsets` read (`system_bars()`, `status_bars()`, `navigation_bars()`, `caption_bar()`, `ime()`, `display_cutout()`, `system_gestures()`, `mandatory_system_gestures()`, `tappable_element()`, `waterfall()`, `safe_drawing()`, `safe_gestures()`, `safe_content()`, the `*_ignoring_visibility()`, `ime_animation_source()` and `ime_animation_target()`; `WindowInsets::new(…)` in pixels or `Dp`; `union`, `exclude`, `add`, `only(WindowInsetsSides::…)`; `MutableWindowInsets`; `is_ime_visible()` and friends, `cutout_path()`; D1356). A value keeps its host's insets and reads them where it's used, a state per type, made when first read (D1363). `Modifier.window_insets_padding(insets)` and its shorthands (from `WindowInsetsModifiers`), `window_insets_top_height` and the other sizes read them while measuring (a change measures them again; nothing recomposes); `insets.as_padding_values()` reads them in composition. The paddings consume what they pad, as Compose's, with `consume_window_insets`, `on_consumed_window_insets_changed` and `recalculate_window_insets` (D1355, D1357): nested paddings of the same insets pad once. Material's components and `Scaffold` default to Compose's insets (D1359, D1360). `imeNestedScroll` isn't there (D1361).
- **Images.** `decode_image_bytes(bytes)` decodes an encoded image with the platform's `ImageDecoder` (Skia's codecs on desktop, `BitmapFactory` on Android; the host sets it with `set_image_decoder`), and `remember_image_resource(include_bytes!("icon.png"))` decodes a bundled one once where it's composed, as `ImageBitmap.imageResource` (named `remember_…` so the composable transform sees the slots it takes, D224).
- **Properties and events.** An app embedded in a platform UI reads the properties the platform passes (`LOCAL_HOST_PROPS`: `props.string("tab")`, `number`, `boolean`; read in composition, a change recomposes the reader) and sends it events (`LOCAL_HOST_EVENTS.current().send(name, payload)`); the host's side is `UiHost::props().set(…)` and `set_event_listener` (D226). `HostProps` is a map of states created on first read, so a read before the platform sets a property recomposes when it does; the values are text, numbers or booleans, and the events a name and a text payload to one listener.
- **Platform services.** As Compose's, content reaches the platform's services through composition locals (`compose::ui`): `LOCAL_URI_HANDLER.current().open_uri("https://…")` (`UriHandler`: Android starts an `ACTION_VIEW` intent, desktop asks the OS: `open`, `xdg-open`, Windows' URL handler; headless, it logs the link; the platform's is a `PlatformUriHandler`, which opens only well-formed URIs of `http`, `https`, `mailto` and `tel`, see below), `LOCAL_CLIPBOARD_MANAGER.current()` (`ClipboardManager`: `get_text`, `set_text`, `has_text`, plain text; the same clipboard text fields and `SelectionContainer` use) and `LOCAL_HAPTIC_FEEDBACK.current().perform_haptic_feedback(HapticFeedbackType::LongPress)` (`HapticFeedback`: Android's `View.performHapticFeedback`, nothing on desktop). The values are `Rc<dyn …>`; the host sets the platform's on its tree before composing (`UiTree::set_uri_handler`, `set_clipboard`, `set_haptic_feedback`), and the locals' defaults read the composing tree's (as `LOCAL_FOCUS_MANAGER`), so a test or a subtree provides a fake with `CompositionLocalProvider(LOCAL_URI_HANDLER.provides(Rc::new(Fake)), …)`. **Links are checked** (D283): `PlatformUriHandler` refuses, with a warning naming only the scheme and host, a URI whose scheme isn't allowed (`DEFAULT_URI_SCHEMES`; `file:`, `search-ms:` and the like could launch programs through the OS's opener), a scheme of one letter (a Windows drive path), and whitespace, control characters, quotes or backslashes. A subtree widens it with `PlatformUriHandler::current().with_schemes(&["https", "myapp"])`, provided as `LOCAL_URI_HANDLER`; `compose::ui::check_uri` is the check. A URI from an untrusted source (a server, a message) should still be validated by the app: an allowed scheme can lead anywhere. `combined_clickable`'s long click performs `LongPress` feedback, as Compose's (`hapticFeedbackEnabled`'s default; the feedback is the local's where the modifier is made in composition). There are no touch selection handles yet, so nothing performs `TextHandleMove` (D281).
- **Calling the app's own Kotlin.** There is no `LOCAL_CONTEXT`: an app embedded in an Android UI calls its own Kotlin (share a text, start an activity, ask for a permission) through host events, and hears back through properties (D226, D282). The content sends `LOCAL_HOST_EVENTS.current().send("share", &text)` from a callback; Kotlin's listener runs it with the activity at hand, posted after the call into Rust returns, and answers with `view.setProp("permission", true)`, which recomposes whoever reads `LOCAL_HOST_PROPS.current().boolean("permission")`:

  ```kotlin
  view.setOnEventListener { name, payload ->
      when (name) {
          "share" -> startActivity(Intent.createChooser(
              Intent(Intent.ACTION_SEND).setType("text/plain").putExtra(Intent.EXTRA_TEXT, payload), null))
          "ask_camera" -> cameraPermission.launch(Manifest.permission.CAMERA) // its result: view.setProp(…)
      }
  }
  ```

  On desktop the same events reach `UiHost::set_event_listener`, so the app's Rust can do the platform's part there.
- **Logging.** compose-rs logs through the `log` crate (re-exported as `compose::log`), and apps may too: `compose::log::info!("loaded {} items", items.len())`, `warn!`, `debug!`. Android's host installs a logcat logger (`__android_log_write`, tagged with the logging crate's name: `adb logcat -s my_app compose_runtime`), desktop's (`application`, `run_app`) and the test rule a stderr one (`compose::ui::platform::install_stderr_logger`), each at `debug` in debug builds and `info` in release ones, unless the app set a logger of its own first (`env_logger`, say, before `run_app`). On desktop and in tests `COMPOSE_LOG` filters, as `RUST_LOG` does: `COMPOSE_LOG=warn,my_app=debug,compose_runtime::state=off` (`LogFilter`; an invalid value is warned about once and ignored). On Android the logger is installed by `JNI_OnLoad`, before any of the app's code; `export_apps! { logger = false; "main" => App }` leaves it to the app (`android_logger`, in a `JNI_OnLoad` of its own calling `compose_android::on_load_with`). The runtime's debug warnings (a stale handle's, D240) go through it (D280).

## Input, focus and semantics

- **Pointer input.** A pointer event hit-tests through the node tree as Compose does: each pointer-input node is hit inside its own layer's bounds, a node's bounds don't limit what's hit inside it (an `offset`'s content, children placed outside), a `clip` does (to its outline), and at each level the topmost child with a hit wins. It collects the pointer-input modifier nodes under it, outermost first. It is dispatched in Compose's three passes: `Initial` down the path, `Main` up from the target, `Final` down again, and a handler consuming it hides it from those after. A press captures the path: the pointer's moves and release go to the same nodes. `clickable` follows Compose's tap detection: it clicks on a release inside, and moving out, a release outside or another handler consuming the events cancels. `toggleable` builds on it.
- **The view configuration.** The gesture detectors' timeouts and distances are compose-ui's `ViewConfiguration`, as Compose's (D907): `long_press_timeout_millis`, `double_tap_timeout_millis`, `double_tap_min_time_millis`, `touch_slop`, `handwriting_slop`, `minimum_touch_target_size`, `maximum_fling_velocity`, `minimum_fling_velocity` and `handwriting_gesture_line_margin`, in pixels; `ViewConfiguration::at(density)` gives Android's (400 ms, 300 ms, 40 ms, 8 dp, 2 dp, 48 dp, 8,000 dp/s, 50 dp/s, 16 dp). The host's (`UiHost::set_view_configuration`, Android's at its density when unset) is what `PointerInputScope::view_configuration`, the tap and drag detectors, the clickable family's timeouts and touch target (D1062), scrolling's touch slop and fling bounds and compose-test's injection read, and content reads it as `LOCAL_VIEW_CONFIGURATION`. It is the host's, not a subtree's (Compose's `WithViewConfiguration` needs modifier nodes reading composition locals), and a running `pointer_input` block doesn't restart when it changes.
- **Handlers run after dispatch.** Application callbacks a node triggers (`on_click`, `on_value_change`) are queued as actions and run once the tree is free, so they can do anything a callback may. `on_key_event` handlers run during dispatch, since their result decides where the event goes: they may write state but not reach the tree.
- **Focus** (`focus.rs`, `focus_search.rs`, `focus_properties.rs`, `focus_requester.rs`; design: `parity/design/focus-and-semantics.md`, D1267-D1286). As Compose's: one active target, every other state derived from it (`FocusState`: `Active`, `ActiveParent`, `Captured`, `Inactive`), the targets' tree found by walking chains by kind. Targets are `Modifier.focus_target()`, `focus_group()` (a target that can't take the focus, its children searched together), `focusable`, `clickable` (`Focusability::SYSTEM_DEFINED`: not in touch mode, `InputMode`, D1272), the text fields, and `FocusTargetNode` to delegate to. `Modifier.focus_properties(|properties| …)` says whether a target can focus, where each direction goes (`FocusRequester::DEFAULT`, `CANCEL`, a requester), `set_on_enter` and `set_on_exit` (a block that may cancel or redirect), and its `focus_rect`, the outermost winning. A transaction tells targets (`FocusTargetModifierNode::on_focus_changed(previous, current, context)`) and the event nodes up to the next target (`FocusEventModifierNode::on_focus_event`; `on_focus_event` and `on_focus_changed(|state: FocusState| …)`) in Compose's order, a callback moving the focus stopping the rest. Application callbacks run after the transaction, those after one that moved the focus not at all (D1271). `FocusRequester` (`remember(FocusRequester::new)`, attached with `Modifier.focus_requester`; a `Copy` id, D240) and `LOCAL_FOCUS_MANAGER.current()` act at once and give real results where the tree is free (an `on_enter` or `on_exit` block's included, D1270), and are queued where it's busy (in composition, in a node's code, D1268: from a node's code, `NodeContext::request_focus` is what asks, done as the node's code returns): `request_focus()` and `request_focus_with(direction)` (several nodes: each in turn, the last keeps it), `capture_focus`, `free_focus`, `save_focused_child`, `restore_focused_child`, `FocusRequester::create_refs()`; `clear_focus(force)` and `move_focus(direction)`. `Modifier.focus_restorer(fallback)` restores the child that had the focus. A node has these on its `NodeContext` and `NodeHandle`, with `focus_state`, `focused_rect` and `request_focus_for_child_in_root_bounds`. On Android, navigation keys nothing takes move the focus (elsewhere Tab alone, D1283), the view's focus follows the content's, the input mode is the view system's, and what's focusable pins a lazy item around it (`LOCAL_PINNABLE_CONTAINER`). Searches are Compose's over the targets' tree: `Next` and `Previous` by placement order, parents before children going forward, wrapping around (clearing and taking the focus anew); `Up`, `Down`, `Left`, `Right` among the focused target's siblings first, then out; `Enter`, `Exit`; a lazy list lays out more for one that finds nothing inside it (D477). A dialog or a focusable popup is a window of its own (D1269, D1284): each window has its focus, what's behind keeps it, searches stay in their window, keys go to the top one, `LOCAL_FOCUS_MANAGER` acts in the window composing, and `LOCAL_WINDOW_INFO.current().is_window_focused()` says whether that one is the top one; a field commits what's being composed as another opens over it (D1286). Tab and Shift-Tab move the focus, consumed if it moved (D1275); Enter or Space clicks a focused clickable. Key events go from the active target's last key node before the next target up.
- **Keyboard and text.** Key events go to the focused node's key input nodes, from its focus target outward, then to its ancestors', until one consumes them; committed text follows the same path. `BasicTextField` is value-based, as Compose's `BasicTextField(value, onValueChange)` (D96): it consumes the keys that type text (down and up, so an ancestor's single-key shortcuts and a clickable row's Space don't take them), edits by grapheme clusters, and follows Compose Desktop's key mappings: arrows (visually in right-to-left text), Up and Down by visual line keeping the horizontal position, words with Option (macOS) or Ctrl, line ends with Cmd on macOS and Home/End, the text's ends with Cmd+Up/Down or Ctrl+Home/End, word and line deletion, select all, copy, cut and paste through the platform's clipboard, and undo and redo (Cmd/Ctrl+Z, Shift+Cmd/Ctrl+Z, Ctrl+Y; typing within 5 s is one step). A plain Tab types a tab in a multi-line field; Shift+Tab moves focus. On macOS, Ctrl moves and deletes as Cocoa's Emacs-style bindings (Ctrl+A, E, B, F, P, N, D, H, K). The pointer places the cursor and drags a selection; a double-click selects a word and a triple-click a line, and a drag after them extends by words or lines (there is no Shift+click yet: pointer events carry no modifiers). An input method's composition shows in place of the selection, underlined, until committed; keys are the input method's meanwhile (but Tab), and a click or a focus change commits it, asking the platform to reset its input method so it isn't committed twice. Losing focus collapses the selection to its end. A single-line field scrolls horizontally, a multi-line one vertically, to keep the cursor in view, and text that overflows is clipped, as Compose's. `SelectionContainer(content)` makes the texts in it selectable, as Compose's: a press and drag selects from where it went down to the pointer across the texts in order (placement order below the container), a double-click a word, a triple-click a text (a drag after them extending by words or texts); Cmd+A (Ctrl+A) selects all and Cmd+C (Ctrl+C) copies, joined by new lines; a click elsewhere in it or its losing focus clears the selection; `DisableSelection` leaves texts out. The texts are `Selectable` modifier nodes the tree finds below the container when a gesture asks, as it finds focus targets (D151); the selection's ends name their texts, so it stays on them as others come and go, and is dropped when a text it ends in changes or leaves. A press in a nested container is that container's. `keyboard_options` (`KeyboardOptions { capitalization, auto_correct_enabled, keyboard_type, ime_action }`, with `KeyboardCapitalization`, `KeyboardType` and `ImeAction` in `compose_ui::text_input`, as Compose's `ui.text.input`) and `keyboard_actions` (`KeyboardActions::new().on_done(…)`) are Compose's. The focused field gives its options to the host as `ImeOptions` (`KeyboardOptions::to_ime_options(single_line)`), for an on-screen keyboard. Enter in a single-line field, or the input method's action key (`UiHost::perform_ime_action`, any action the keyboard showed, a single line's `Default` being `Done` as on Android), performs the field's action for it; without one, as Compose's default actions, `Next` and `Previous` move the focus and `Done` hides the on-screen keyboard; `Default` on desktop does nothing. `LOCAL_SOFTWARE_KEYBOARD_CONTROLLER.current()` (as `LocalSoftwareKeyboardController`, `None` only outside a `UiTree`'s composition) shows or hides the on-screen keyboard (`show()`, `hide()`; `EventContext::show_software_keyboard` and `hide_software_keyboard` from a handler). A tap on a focused, editable field (on its text or its decoration) asks to show it again, as Compose's `tapToFocus`, so a keyboard `Done` hid comes back; desktop ignores the request. A multi-line field is between `min_lines` and `max_lines` lines high (as `heightInLines`: the heights of one and two lines of "H" in its style give the first line's and each next one's), its text scrolling within; a single line is one line high. `visual_transformation` (`impl Into<VisualTransformation>`, so a `PasswordVisualTransformation` needs no `.into()`, D232) changes how the text shows without changing it, as Compose's `VisualTransformation` with an `OffsetMapping` (byte offsets here): `PasswordVisualTransformation` masks each character with •, its semantics say `password` with the masked text, and it can't be copied or cut. Its `decoration_box` lays out what surrounds the text (Material's container, label and placeholder) and calls `inner_text_field` where the text goes; the field's modifier, semantics node and taps are the decoration's, as `CoreTextField`'s (D102).
- **Semantics.** Semantics modifier nodes build a semantics tree, merged or unmerged as in Compose: a node merging its descendants (`clickable` does) takes their properties, placed or not, and hides them, unless they merge themselves or are deactivated (D1037). Tests find nodes through it (`on_node_with_text`, as Compose testing does), and it feeds the accessibility bridges (AccessKit on desktop, `Accessibility.kt` on Android). Properties are Compose's typed keys (D1250): `SemanticsPropertyKey<T>` statics, compared by address, in Compose's sets `SemanticsProperties` (`TEXT`, `CONTENT_DESCRIPTION`, `ROLE`, `FOCUSED`, `PANE_TITLE`, `COLLECTION_INFO`, `TRAVERSAL_INDEX`…) and `SemanticsActions` (`ON_CLICK`, `SCROLL_BY`, `SET_PROGRESS`, `REQUEST_FOCUS`, `CUSTOM_ACTIONS`…), each with Compose's merge policy (texts and content descriptions concatenate; a role, a test tag, a traversal index never merge up; a pane title, a dialog or a popup in a merging node is an error; an action's label and function merge apart); an application declares its own keys and action signatures the same way. A configuration (`SemanticsConfiguration`) holds the values inline for Compose's types, an application's through one `Rc`; it reads with `get(&KEY)`/`contains(&KEY)` and is written with Compose's receiver setters (`config.set_text(…)`, `config.heading()`, `config.on_click(label, action)`, `config.set(&KEY, value)`). A node's own modifiers apply from the innermost to the outermost, so an outer one's values win, key by key (an action keeps the inner one's label or function where the outer has none, as Compose's `set`). A dialog's content sits in a node of its own, as large as it, `IS_DIALOG`. `Modifier.clear_and_set_semantics` (as `clearAndSetSemantics`) hides what's inside a node (an icon next to its label). Actions are closures that screen readers and `perform_semantics_action` call instead of sending input, outside the tree: `clickable` and `toggleable` click (whether enabled or not, as Compose's: the platform bridges refuse a disabled node's actions, D1255), a focusable node takes the focus (`RequestFocus`, bound by the tree to the node's focus target, D1251), a scrolling container scrolls, a slider (its own merged node, with its `ProgressBarRangeInfo`) moves to a value snapped to its steps, a text field takes a new text (`SET_TEXT`). A node's own configuration is kept per layout node, computed when a tree or an action first asks, as Compose's `LayoutNode.semanticsConfiguration` (D1257): it's computed again after `invalidate_semantics`, a chain update of a semantics node (as Compose's auto-invalidation), a state read in a custom node's `apply_semantics` written, the node's measurement or a focus change of its focus target; a clickable builds its click once per update (D1258); performing an action reads the node's own configuration and its parts', no tree (`UiTree::unmerged_semantics_config`). A node's semantics id (`SemanticsNode::semantics_id`, Compose's `SemanticsNode.id`) is another when it's reused, and it's what the accessibility bridges name it by (D1262). `SemanticsModifierNode` has Compose's `should_merge_descendant_semantics`, `should_clear_descendant_semantics` and `is_important_for_bounds` (D1260). Known differences: `Modifier.semantics` runs its block at composition (a state it reads recomposes the caller), the texts are plain strings, and an invalidated configuration is computed when next asked, not at the invalidation. `Modifier.progress_semantics()` (indeterminate, `ProgressBarRangeInfo::INDETERMINATE`) and `progress_semantics_with(value, value_range, steps)` say a progress, merging their descendants, as Compose's `progressSemantics`; `on_click_label` and `on_long_click_label` are the click actions' labels (`on_click(label, …)`).

## The host

`UiHost` (in `compose::ui::platform`, D260) is a composition of a `UiTree` in a root of a given size and density, with its text measurer: the core every platform host wraps, and what tests drive headless. `frame()` recomposes invalid scopes, then measures and draws what changed (a write the pass made to state read while measuring or drawing is this frame's: it asks for no other frame, D806); `send_pointer`, `send_key` and `send_text` dispatch events and run their actions; `needs_frame()` says whether a frame would do anything, and a waker tells the platform when state changes. It owns what the platform gives content: the back dispatcher, the saveable state registry, the configuration, the window insets, the properties and the event listener (above). Between frames, `has_prefetch_work()` says whether lazy lists wait for idle time, and `prefetch(deadline)` gives them the time until `deadline` (the next frame's start; `prefetch_with(deadline, true)` gives the first request no deadline, Compose's idle frame); it does nothing while a frame has work (`has_pending_work`: state changed, a scroll), asks for no frame itself (what it composes isn't placed, what it disposes wasn't), unless measuring wrote state for others, and returns whether work is left. After it, with `DRAW_PREFETCHED_AHEAD`, `has_draw_ahead_work()` and `draw_ahead()` draw the items it measured, one at a time, and `cancel_draw_ahead()` gives them up (above). `compose-test` builds Compose's test rule on it ([09](09-testing.md)).

What a platform with an on-screen keyboard reads from it (D234): `text_input_area()` is `Some` while a focused node takes text (its cursor, where a candidate window goes); `text_input_options()` gives that field's `ImeOptions` (keyboard type, action key, capitalization, auto-correction, single line; from `KeyInputModifierNode::ime_options`, its `auto_correct_enabled` true by default, Compose's resolved default for its nullable `autoCorrectEnabled`), read when the field takes the focus to configure the keyboard (Android's `EditorInfo` in `onCreateInputConnection`: input type and IME options); `perform_ime_action(action)` is the keyboard's action key (to `KeyInputModifierNode::on_ime_action`) (Android's `performEditorAction`); `take_software_keyboard_request()` returns what the content last asked (`Some(true)` to show the keyboard for the focused field, `Some(false)` to hide it), taken after each frame and event, the asking having woken the host; `take_input_method_reset()` says a field committed its composition itself. Desktop reads the area and the reset; Android reads them all (its `EditorInfo`, `performEditorAction`, `showSoftInput`/`hideSoftInputFromWindow`, D250).

**What apps use, what hosts use (D260).** Each module's top level is the app-facing surface. The plumbing hosts and the toolkit's crates use sits in a `platform` module beside it, outside semver: `compose::runtime::platform` (the `Composer` and `current`, `Applier`, `NodeRef` and `NodeTree`, the executor's driving functions (`run_ready`, `poll_now`, `fire_timers`, `dispatch_frame`, `set_wake_handler`, the manual clock), `ReadObserver`, `flush_derived_states`, and the counting hooks `bodies_run`, `track_recompositions`, `recomposition_counts`, `live_state_count`) and `compose::ui::platform` (`UiHost`, `UiTree`, `LayoutNode`, `NodeId`, `DisplayList`, `DrawOp`, `Renderer`, `TextMeasurer` and its paragraph types, `FixedTextMeasurer`, `ImageDecoder`, `SemanticsNode`, `PointerInputDriver`, the platform's window insets, `trace`, and since D265 `Action`, `Shader`, `ShaderIndex`, `Gradient`, `LayerProperties`, `NestedScrollChain`, `StackMeasurePolicy` and `round_to_int`; hosts read a paint's shader with `Paint::shader()` and set one with `with_shader`). Apps' tests reach the counting hooks through `compose::test` (the facade's `test` feature). The built-in modifier representation (`Element`, `Modifier::elements`, `then_element`) and foundation's text nodes are private; `then_custom` stays, and `platform::shared_custom_modifier` lets a toolkit share one element. compose-ui's modules are private: everything public is re-exported at the root or in `platform`, `unreachable_pub` warns on strays, and every library crate denies `unnameable_types`, so a public signature can't use a type from a private module (D265).

**Types that grow.** Enums Compose keeps extending are `#[non_exhaustive]`: `Role`, `Key`, `ImeAction`, `KeyboardType`, `KeyboardCapitalization`, `PointerType`, `PointerEventType`, `PointerIcon`, `TextAlign`, `TextOverflow`, `AnimationSpec`; a match on them needs a `_` arm (`DrawOp`, a platform type outside semver, isn't, so the hosts match it exhaustively). `Paint` is `#[non_exhaustive]` too (built with `Paint::fill` and `Paint::stroke`). Structs that stand for a Compose constructor with all-optional parameters keep public fields and are built with struct update from their default, which is the supported way: `TextStyle { font_size: 20.sp(), ..TextStyle::DEFAULT }`, `KeyboardOptions { ime_action: ImeAction::Done, ..KeyboardOptions::DEFAULT }`, `ButtonColors { container_color: Color::RED, ..ButtonDefaults::button_colors() }`; a field added later is a minor change for code written so (a literal naming every field, or a pattern without `..`, is not supported).

Parameter names, order and defaults follow Compose, in snake_case. Deviations Rust forces, documented per composable:
- text parameters take `impl Into<SharedString>` (a `#[format]` one, as `Text`'s, converts whatever it is given): a `&'static str` (kept as is), a `String` or `&String` (copied into an `Rc<str>`), an `Rc<str>`, `&Rc<str>` or `&SharedString` (shared). A borrowed `&str` converts through `to_string()`: `From<&'a str>` would conflict with the literals' conversion, which allocates nothing;
- scopes are explicit tokens;
- there are no overloads (D263): overloads that differ by an argument's type are one function taking `impl Into<T>` where a type fits (`padding(impl Into<PaddingValues>)` takes `8.dp()`, `(16.dp(), 8.dp())`, `(start, top, end, bottom)` or `PaddingValues { start: 8.dp(), ..PaddingValues::ZERO }`; `size` and `required_size` take a `Dp` or `(width, height)` as a `DpSize`; `background` a `Color` or a `Brush`; the gradients `&[Color]` or `&[(f32, Color)]` as `ColorStops`), or else a trait their argument implements (`Arrangement::spaced_by`, `Arrangement::aligned`, `RoundedCornerShape`: the `SpacedBy`, `AlignedBy` and `RoundedCorners` traits; `PaddingValues` converts from `Dp`, `(Dp, Dp)` or `(Dp, Dp, Dp, Dp)`), a tuple standing for several arguments. Overloads that only add Compose's optional parameters keep the Compose name for the short form (Compose's required parameters), and `<name>_with` takes the rest, the one variant suffix (`fill_max_width_with(fraction)`, `weight_with(scope, weight, fill)`, `background_with(brush, shape)`, `border_with(width, color, shape)`, `shadow_with`, `semantics_with(merge_descendants, properties)`, `focusable_with(enabled)`, `hoverable_with`, `aspect_ratio_with`, `wrap_content_*_with`, `fill_parent_max_*_with`, the gradients' `_with`, `Paint::stroke_with`, `spring_with`, `fade_in_with`, `mutable_state_of_with`, `remember_saveable_with`): positionally in Compose's order, or, for the clickable family (`clickable_with`, `toggleable_with`, `selectable_with`, `combined_clickable_with`), a `ClickableOptions` built by struct update from `ClickableOptions::DEFAULT`. `_keyed` marks the overloads taking Compose's `key`s (`remember_keyed`, `items_keyed`). A function whose parameters are all optional in Compose takes them all, with no `_with` (`offset(x, y)`, `default_min_size(min_width, min_height)`).
