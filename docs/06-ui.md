# 6. UI (`compose-ui`, `compose-foundation`, `compose-material3`)

This follows Compose UI's structure: layout nodes with chains of `Modifier.Node`s, a public `Layout` primitive that `Column` and `Row` are written on, measure and place with constraints, and a draw pass. Text is measured and drawn by each platform's own stack, as in Compose.

## Nodes

- **`LayoutNode`**: one per UI element, owned by the `UiTree` arena behind `Copy` generational `NodeId`s. A node holds:
  - its `MeasurePolicy` (an `Rc<dyn MeasurePolicy>`, compared by pointer);
  - its modifier, and the chain of modifier nodes built from it;
  - its children;
  - its measurement: one *layer* per layout modifier, outermost first, then its own content, each with a size and an offset in the layer outside it (Compose's node coordinators).
- **`UiTree`** is the composition's applier (the `UiApplier` of earlier drafts): it implements the runtime's `Applier` for `LayoutNode`s (insert, move, remove, and release at the end of the pass, rule R1), and runs measurement, drawing, input, focus and semantics. Composables update their node's policy and modifier through `with_applier`. It never runs application code while the runtime holds its state.

## Modifiers: `Modifier.Node`, no `composed`

A `Modifier` is an **ordered chain of elements**. Call order matters, exactly as in Compose: `Modifier.padding(8.dp()).background(Color::RED)` differs from the reverse.

```rust
pub struct Modifier { elements: SmallVec<[Element; 4]> }     // Clone; ComposeArg (element-wise)

pub enum Element {                                           // the built-ins: no allocation
    Padding(PaddingValues), Size(SizeSpec), FillMax(Axis, f32), Background(Color, Shape),
    Border(Dp, Color, Shape), Clickable(ClickableSpec), Toggleable(ToggleableSpec),
    Weight(f32, bool), Align(Alignment), Semantics(SemanticsSpec), …,
    Custom(Rc<dyn ModifierNodeElement>),                     // user-defined modifiers
}

pub trait ModifierNodeElement: Any {
    fn create(&self) -> Box<dyn ModifierNode>;
    fn update(&self, node: &mut dyn ModifierNode);           // in place: node state survives
    fn same(&self, other: &dyn ModifierNodeElement) -> bool; // through a downcast
}

pub trait ModifierNode: Any {   // optional capabilities, as Compose's Modifier.Node delegates
    fn as_layout(&mut self) -> Option<&mut dyn LayoutModifierNode> { None }
    fn as_draw(&mut self) -> Option<&mut dyn DrawModifierNode> { None }
    fn as_pointer_input(&mut self) -> Option<&mut dyn PointerInputModifierNode> { None }
    fn as_semantics(&mut self) -> Option<&mut dyn SemanticsModifierNode> { None }
    fn as_focus_target(&mut self) -> Option<&mut dyn FocusTargetModifierNode> { None }
    fn as_key_input(&mut self) -> Option<&mut dyn KeyInputModifierNode> { None }
    fn on_detach(&mut self, context: &mut DetachContext) {}  // release resources (paragraphs)
}
```

- **Diffing** happens on recomposition. When the kinds are the same, in the same order (the usual case: a value changed), each element updates its node in place, allocating nothing. Otherwise old and new elements are matched by kind in order (a longest common subsequence, as Compose's chain diff): matched ones update their node in place, so `clickable`'s pressed state and a text field's focus survive elements added or removed around them; the others' nodes are created or detached. A pointer gesture in progress follows its node to its new place in the chain.
- **The built-in modifiers are methods of `Modifier`** in `compose-ui` (`padding`, `size`, `fill_max_width`, `offset`, `weight`, `align`, `background`, `border`, `clip`, `clickable`, `toggleable`, `focusable`, `on_focus_changed`, `on_key_event`, `test_tag`, `semantics`), with their nodes. Rust has no extension functions, so an inherent method is what lets `Modifier.padding(…)` work with nothing imported; `compose::foundation` re-exports them where Compose has them. The scope tokens (`RowScope`, `ColumnScope`, `BoxScope`) live there too, with hidden constructors for the layouts that make them.
- **No `Modifier.composed`.** Elements are plain data. State a modifier needs (pressed, hovered, focused, later ripples) lives in its `ModifierNode`, owned by the `LayoutNode`, never in composition slots, and no modifier composes or `remember`s.
- **Handlers** live inside elements as `Callback`s (`Rc<dyn Fn>`). A closure argument in a modifier chain rooted at `Modifier` (`Modifier.clickable(move || count.update(…))`) is memoized by the macro like a call-macro argument ([03](03-composable-macro.md)), so a modifier rebuilt in a pass is `same` as the previous one, and a composable receiving it still skips. An `Rc` with identity is all it takes.
- **Allocation.** Built-in elements are enum variants in an inline `SmallVec`, so typical chains of up to four elements allocate nothing. Longer chains spill once.
- **Spelling.** `Modifier` is a type and also a `const` of that type, so code writes `Modifier.padding(16.dp())` as in Kotlin, and `modifier: Modifier = Modifier` as a default.

## Layout

```rust
#[composable]
pub fn Layout(
    #[default(Modifier)] modifier: Modifier,
    measure_policy: Rc<dyn MeasurePolicy>,
    content: impl Fn() + 'static,
);

pub trait MeasurePolicy: 'static {
    fn measure(&self, scope: &mut MeasureScope, measurables: &[Measurable], constraints: Constraints) -> MeasureResult;
    // intrinsic sizes later, with default implementations
}

impl MeasureScope<'_> {
    fn measure(&mut self, measurable: Measurable, constraints: Constraints) -> Placeable;
    fn place(&mut self, placeable: &Placeable, x: i32, y: i32);
    fn layout(&self, width: i32, height: i32) -> MeasureResult;
    fn parent_data(&self, measurable: Measurable) -> ParentData;   // weight, alignment
    fn density(&self) -> Density;
    fn text_measurer(&mut self) -> &mut dyn TextMeasurer;
}
```

- **One measure-and-place pass with constraints**, as in Compose, except that a policy places its children in the same call that measures them, rather than in a placement block run afterwards. A layout modifier (`LayoutModifierNode::measure(scope, content, constraints)`) measures and places the content it wraps the same way.
- **Incremental.** Updating a node's policy or modifier, or inserting, moving or removing children, marks it for measuring and its ancestors as having a dirty descendant. The next layout measures from the root, but a node with unchanged constraints and nothing dirty returns its size at once; one with only dirty descendants measures them again in place, and runs its own policy only if one of their sizes changed. So a change climbs to the first ancestor whose size holds. A frame where nothing changed measures and draws nothing.
- **Rules.** A policy may measure a child only once per measurement, as in Compose: measuring it again panics. A panic in a policy or a layout modifier node leaves the tree whole (each node's children and modifier nodes are put back as the panic unwinds) and the node marked for measuring again. Pixel rounding is Kotlin's `roundToInt` (halves up), and `Constraints::offset` adds, as Compose's.
- **Outside the constraints.** A measured size is coerced into the constraints for the parent; the node keeps its measured size and is centered in the coerced one, as Compose does (`required_size` past the parent's bounds).
- **The root** measures its children with the window's constraints loosened, and places them at the origin.
- **State read in measurement and drawing is observed**, as Compose's `SnapshotStateObserver` does: a node's policy and its custom layout modifiers measure, and its custom draw nodes draw, under an observation keyed by the node, so a write to what they read measures or draws that node again at the next frame without recomposing (built-in nodes read no state and aren't observed). `vertical_scroll` keeps its offset in state this way.
- **`Box`, `Column`, `Row` and `Spacer` are ordinary composables** in `compose::foundation::layout`, each a `Layout` with its own `MeasurePolicy`. That's Compose's split: layout is library code on a public primitive, not built into the node kinds.
- **Scoped modifiers.** `weight` and `align` exist only inside `Row`/`Column`/`Box` content, as in Compose. Rust has no context receivers, so a content lambda receives its scope as a `Copy` zero-sized token, and those modifiers take it:
  ```rust
  Row!(modifier = Modifier.fill_max_width(), |row| {
      Text!("Title", modifier = Modifier.weight(row, 1.0));
      Text!("Done");
  });
  ```
  A `RowScope` value can only come from `Row`, so misuse is a compile error at zero runtime cost. Compose's `Modifier.weight(1f)` reads slightly cleaner; this is the closest checked equivalent. `Box` the composable lives in the value namespace and `std::boxed::Box` in the type namespace, so they don't clash.

**Lazy lists.** `LazyColumn` and `LazyRow` compose only the items in view and two beyond each side, as Compose's: `LazyColumn!(state = list_state, |scope: LazyListScope| { scope.items_keyed(todos.len(), |index| todos[index].id, |index| TodoRow(…)); })`, with `item`, `items` and `items_keyed` (an item keeps its state when items before it come and go), content padding and arrangement. Compose composes items while measuring; here composition can't run inside layout (the tree is borrowed), so the list composes a range of items, and its measurement, which fills the viewport from the `LazyListState` (the first visible item and its offset), writes the range it needs when the composed one falls short. `UiHost::frame` then recomposes and measures again within the frame, up to three times, so a scroll never shows an empty frame. The items compose in a restartable scope of their own, each item a restartable composable: a scroll recomposes neither the list's caller nor the items that stay. Items outside the range leave the composition (their state goes, as in Compose without `rememberSaveable`), but the focused one, pinned by key, which stays composed and placed (Compose's pinning). A viewport's worth of items is composed beyond each side (at least two), so focus can reach the next focusable item. The composed items beyond the viewport are placed too, out of view, so focus moves to them, and a focused node is brought into view by its scrolling ancestors (`ModifierNode::bring_into_view`, as `BringIntoViewResponder`; `vertical_scroll` does it too). The scroll position follows the first visible item by key when items come and go before it, keeps fractions of a pixel, and steps over items only once they are composed (their sizes known), but for jumps of hundreds of items, which it estimates from the average size (Compose composes every item in between). Keys are looked for within a window around their last index; items are found by binary search over the intervals. An empty first layout (data still loading) keeps the initial position; an emptied list starts again at its top. Content shorter than the viewport is placed by the arrangement. The wheel and drags scroll it: the innermost scrollable takes a drag past the slop (8 dp from the press; scrolling what moved beyond it), and a wheel delta a list can't use goes on to the scrollables around it; `scroll_to_item` jumps; at the end, the last item ends the viewport.

## Text

- **`TextMeasurer`** is the interface layout uses: it lays out a paragraph and returns a handle with its metrics. Each platform implements it with the text stack Compose uses there ([07](07-platforms.md)):
  - **desktop:** Skia's paragraph module (HarfBuzz shaping, ICU line breaking and bidi), as Compose Desktop;
  - **Android:** Android's own `StaticLayout`, as Android Compose.

  Kerning, ligatures, complex scripts, fallback fonts and emoji come from the platform stack.
- **Tests** use the desktop implementation with bundled fonts, so measurements are identical on every machine. A fixed-advance measurer stays available for layout golden tests that should not depend on fonts at all.
- `BasicText`/`Text` keep the paragraph handle on the node, keyed on text, style and width constraint, so a recomposition with the same text measures nothing.

## Drawing

A draw pass records a **display list**: a subset of the `Canvas` API (clips, transforms, rectangles, rounded rectangles, paths, images, paragraphs drawn by handle, paints with shaders and blend modes). Draw modifier nodes record into it in chain order: `DrawModifierNode::draw` before the content (the rest of the chain and the children), `draw_after` after it, in reverse order, which is Compose's `drawContent()` split in two (`background` draws before, `border` after, `clip` saves and clips before and restores after). A node draws at the size of the layer its draw node is in, so `padding(8).background(…)` fills inside the padding. A platform `Renderer` replays the list: Skia on desktop, Android's `Canvas` on Android ([07](07-platforms.md)). Tests dump it as text or render it to PNG through Skia's CPU raster backend. The list is recorded whole whenever anything changed, into a buffer kept from frame to frame (so a warm frame allocates nothing); caching per-node lists comes when profiling asks for it.

**Paths and vector images.** `Path` holds lines, curves and closes, built in code or parsed from SVG path data (`Path::from_svg`, arcs converted to curves), and draws with `DrawScope::draw_path` (a `DrawPath` op holding it in an `Arc`, with a scale and offset: an `ImageVector`'s viewport fitted to its size, nothing copied per frame). Material's `Icon` draws an `ImageVector`; `icons::filled::add()` and friends are a subset of Material's icons.

**Images.** `ImageBitmap` holds premultiplied RGBA pixels in an `Arc`, made from raw pixels or decoded by the backend (`compose_skia::decode_image`, PNG, JPEG, WebP, …, as the desktop's `decodeToImageBitmap`). `DrawScope::draw_image` records a `DrawImage` op (a source and destination rect and an alpha); Skia makes its image once per bitmap and forgets it the frame after the bitmap is dropped. Foundation's `Image(bitmap, content_description, modifier, alignment, content_scale, alpha)` is as large as its pixels within the constraints (shrunk, its aspect ratio kept), draws scaled by a `ContentScale` (`Fit`, `Crop`, `FillBounds`, `FillWidth`, `FillHeight`, `Inside`, `None`) and aligned, clipped to its node, and reads as `Role::Image` with its description.

**Graphics layers.** `Modifier.graphics_layer(|layer| …)` applies alpha, scale, rotation and translation to a node's drawing, as `graphicsLayer`: the display list saves, transforms around the layer's pivot and draws into an alpha layer (`Transform`, `SaveLayerAlpha`). Its block runs while drawing, so the state it reads (an animation's value) redraws the node without recomposing or measuring it. `alpha`, `scale` and `rotate` are fixed layers. The block isn't memoized by the macro (its closure takes a `&mut` scope, which a `Callback` can't hold): remember the modifier for a callee to skip. Hit testing doesn't follow the transform yet.

## Animation

`compose::animation` is Compose's `animation` and `animation.core`. An `Animatable` holds its value in state and animates it with tasks ([04](04-runtime.md)): `animate_to(target, spec).await` takes a step each frame (`with_frame_nanos`) along a spec, `tween` (duration, delay, easing), `spring` (Compose's damped-spring equations, keeping the velocity across interruptions), `snap`, `repeatable` or `infinite_repeatable`, per component of the value's vector (`f32`, `i32`, `Dp`, `Offset`, `IntOffset`, `Size`, and `Color` in Oklab, as Compose's converters). A new animation interrupts the running one, which ends with `AnimationEndReason::Interrupted` where Compose throws a cancellation. `animate_float_as_state(target)` and its siblings follow a target, `remember_infinite_transition()` animates forever, and `AnimatedVisibility(visible, enter = fade_in() + expand_vertically(), …)` animates content in and out, keeping it composed while it leaves; `Crossfade(target_state, …)` fades one state's content into the next's; `Modifier.animate_content_size()` animates a node's size to its content's. Animated values are read where they are used: in a graphics layer's block (a redraw) or a layout (a re-measure), not in composition, so a frame recomposes nothing.

## Popups and dialogs

`Popup` and `Dialog` (`compose::ui`, as Compose's `ui.window`) show content over the rest of the window. Compose gives them windows or layers of their own; here they are **overlays**: nodes composed where they are called (so composition locals, state and remembered values follow) whose modifier (`Modifier.overlay(provider, …)`) makes the tree place them in the root after layout, with a position provider (`PopupPositionProvider`: `AlignmentOffsetPositionProvider` for `Popup(alignment, offset)`, a menu's below-or-above provider), from their anchor's bounds and the window's size. They are drawn after everything else and hit before it (a point in an overlay is its, handled or not); in semantics they are roots of their own, never merged into what's around their anchor. A popup with `on_dismiss_request` gets an outside-click catcher; a focusable one takes the focus and Escape dismisses it. A dialog is modal: its content centered (24 dp from the window's edges) over a scrim that takes every event, taking the focus. Material's `AlertDialog`, `DropdownMenu` and `DropdownMenuItem` are built on them.

## Input, focus and semantics

- **Pointer input.** A pointer event hit-tests through the node tree as Compose does: each pointer-input node is hit inside its own layer's bounds, a node's bounds don't limit what's hit inside it (an `offset`'s content, children placed outside), a `clip` does (to its outline), and at each level the topmost child with a hit wins. It collects the pointer-input modifier nodes under it, outermost first. It is dispatched in Compose's three passes: `Initial` down the path, `Main` up from the target, `Final` down again, and a handler consuming it hides it from those after. A press captures the path: the pointer's moves and release go to the same nodes. `clickable` follows Compose's tap detection: it clicks on a release inside, and moving out, a release outside or another handler consuming the events cancels. `toggleable` builds on it.
- **Handlers run after dispatch.** Application callbacks a node triggers (`on_click`, `on_value_change`) are queued as actions and run once the tree is free, so they can do anything a callback may. `on_key_event` handlers run during dispatch, since their result decides where the event goes: they may write state but not reach the tree.
- **Focus.** One node has focus. A focus target is a modifier node (`focusable`, and `clickable`, which is focusable when enabled, as on desktop Compose). Tab and Shift-Tab move through the focus targets in tree order, wrapping around (Compose's one-dimensional focus search), and Enter or Space clicks a focused clickable. `on_focus_changed` reports whether the focus target after it in the chain, or a node below, has focus (Compose's `FocusState.hasFocus`), once when it attaches and then on every change. A focus target that is removed or can no longer take focus (disabled) loses it, and is told. Key events go to every key input node of the focused node, those after its focus target included, as Compose's `lastLocalKeyInputNode`.
- **Keyboard and text.** Key events go to the focused node's key input nodes, from its focus target outward, then to its ancestors', until one consumes them; committed text follows the same path. `BasicTextField` is value-based, as Compose's `BasicTextField(value, onValueChange)` (D96): it consumes the keys that type text (down and up, so an ancestor's single-key shortcuts and a clickable row's Space don't take them), edits by grapheme clusters, and follows Compose Desktop's key mappings: arrows (visually in right-to-left text), Up and Down by visual line keeping the horizontal position, words with Option (macOS) or Ctrl, line ends with Cmd on macOS and Home/End, the text's ends with Cmd+Up/Down or Ctrl+Home/End, word and line deletion, select all, copy, cut and paste through the platform's clipboard, and undo and redo (Cmd/Ctrl+Z, Shift+Cmd/Ctrl+Z, Ctrl+Y; typing within 5 s is one step). A plain Tab types a tab in a multi-line field; Shift+Tab moves focus. On macOS, Ctrl moves and deletes as Cocoa's Emacs-style bindings (Ctrl+A, E, B, F, P, N, D, H, K). The pointer places the cursor and drags a selection; a double-click selects a word and a triple-click a line, and a drag after them extends by words or lines (there is no Shift+click yet: pointer events carry no modifiers). An input method's composition shows in place of the selection, underlined, until committed; keys are the input method's meanwhile (but Tab), and a click or a focus change commits it, asking the platform to reset its input method so it isn't committed twice. Losing focus collapses the selection to its end. A single-line field scrolls horizontally, a multi-line one vertically, to keep the cursor in view, and text that overflows is clipped, as Compose's. Its `decoration_box` lays out what surrounds the text (Material's container, label and placeholder) and calls `inner_text_field` where the text goes; the field's modifier, semantics node and taps are the decoration's, as `CoreTextField`'s (D102).
- **Semantics.** Semantics modifier nodes build a semantics tree, merged or unmerged as in Compose: a node merging its descendants (`clickable` does) takes their text and state and hides them, unless they merge themselves. Tests find nodes through it (`on_node_with_text`, as Compose testing does), and it feeds AccessKit later, for screen readers.

## The host

`UiHost` is a composition of a `UiTree` in a root of a given size and density, with its text measurer: the core every platform host wraps, and what tests drive headless. `frame()` recomposes invalid scopes, then measures and draws what changed; `send_pointer`, `send_key` and `send_text` dispatch events and run their actions; `needs_frame()` says whether a frame would do anything, and a waker tells the platform when state changes. `compose-test` builds Compose's test rule on it ([09](09-testing.md)).

Parameter names, order and defaults follow Compose, in snake_case. Deviations Rust forces, documented per composable:
- text parameters take `impl Into<SharedString>`;
- scopes are explicit tokens;
- there are no overloads, so variants get distinct names or merged defaults;
- there are no composition locals at first (`MaterialTheme` is a value).

`CompositionLocal` is planned ([10](10-roadmap.md)); Rust can implement it in the runtime with no language support.
