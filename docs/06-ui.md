# 6. UI (`compose-ui`, `compose-foundation`, `compose-material3`)

This follows Compose UI's structure: layout nodes with chains of `Modifier.Node`s, a public `Layout` primitive that `Column` and `Row` are written on, measure and place with constraints, and a draw pass. Text is measured and drawn by each platform's own stack, as in Compose.

## Nodes

- **`LayoutNode`**: one per UI element, owned by the `UiTree` arena behind `Copy` generational `NodeId`s. A node holds:
  - its `MeasurePolicy` (an `Rc<dyn MeasurePolicy>`, compared by pointer);
  - its modifier, and the chain of modifier nodes built from it;
  - its children;
  - its measurement: one *layer* per layout modifier, outermost first, then its own content, each with a size and an offset in the layer outside it (Compose's node coordinators).
- **`UiTree`** is the composition's applier (the `UiApplier` of earlier drafts): it implements the runtime's `Applier` for `LayoutNode`s (insert, move, remove, and release at the end of the pass, rule R1), and runs measurement, drawing, input, focus and semantics. Composables update their node's policy and modifier through `with_applier`. It never runs application code while the runtime holds its state.

## Modifiers: `Modifier.Node`, no `composed`

A `Modifier` is an **ordered chain of elements**. Call order matters, exactly as in Compose: `Modifier.padding(8.dp()).background(Color::RED)` differs from the reverse.

```rust
pub struct Modifier { elements: SmallVec<[Element; 6]> }     // Clone; ComposeArg (element-wise)

pub enum Element {                                           // the built-ins: no allocation
    Padding(PaddingValues), Size(SizeSpec), FillMax(Axis, f32), Background(Color, Shape),
    Border(Dp, Color, Shape), Clickable(ClickableSpec), Toggleable(ToggleableSpec),
    Weight(f32, bool), Align(Alignment), Semantics(SemanticsSpec), …,
    Custom(Rc<dyn ModifierNodeElement>),                     // user-defined modifiers
}

pub trait ModifierNodeElement: Any {
    fn create(&self) -> Box<dyn ModifierNode>;
    fn update(&self, node: &mut dyn ModifierNode);           // in place: node state survives
    fn same(&self, other: &dyn ModifierNodeElement) -> bool; // through a downcast
}

pub trait ModifierNode: Any {   // optional capabilities, as Compose's Modifier.Node delegates
    fn as_layout(&mut self) -> Option<&mut dyn LayoutModifierNode> { None }
    fn as_draw(&mut self) -> Option<&mut dyn DrawModifierNode> { None }
    fn as_pointer_input(&mut self) -> Option<&mut dyn PointerInputModifierNode> { None }
    fn as_semantics(&mut self) -> Option<&mut dyn SemanticsModifierNode> { None }
    fn as_focus_target(&mut self) -> Option<&mut dyn FocusTargetModifierNode> { None }
    fn as_key_input(&mut self) -> Option<&mut dyn KeyInputModifierNode> { None }
    fn on_detach(&mut self, context: &mut DetachContext) {}  // release resources (paragraphs)
}
```

- **Diffing** happens on recomposition. When the kinds are the same, in the same order (the usual case: a value changed), each element updates its node in place, allocating nothing. Otherwise old and new elements are matched by kind in order (a longest common subsequence, as Compose's chain diff): matched ones update their node in place, so `clickable`'s pressed state and a text field's focus survive elements added or removed around them; the others' nodes are created or detached. A pointer gesture in progress follows its node to its new place in the chain.
- **The built-in modifiers are methods of `Modifier`** in `compose-ui` (`padding`, `size`, `width_in`, `height_in`, `fill_max_width`, `offset`, `weight`, `align`, `z_index`, `background`, `border`, `clip`, `clip_to_bounds`, `clickable`, `toggleable`, `selectable`, `selectable_group`, `focusable`, `on_focus_changed`, `on_key_event`, `test_tag`, `semantics`), with their nodes; a few are custom elements of `compose-ui` (`aspect_ratio`, `wrap_content_width`/`height`/`size`, `default_min_size`, `layout`, `on_size_changed`, `on_globally_positioned`, `combined_clickable`, `hoverable`, `draw_behind`, …). Rust has no extension functions, so an inherent method is what lets `Modifier.padding(…)` work with nothing imported; `compose::foundation` re-exports them where Compose has them. The scope tokens (`RowScope`, `ColumnScope`, `BoxScope`) live there too, with hidden constructors for the layouts that make them.
- **No `Modifier.composed`.** Elements are plain data. State a modifier needs (pressed, hovered, focused, later ripples) lives in its `ModifierNode`, owned by the `LayoutNode`, never in composition slots, and no modifier composes or `remember`s.
- **Handlers** live inside elements as `Callback`s (`Rc<dyn Fn>`). A closure argument in a modifier chain rooted at `Modifier` (`Modifier.clickable(move || count.update(…))`) is memoized by the macro like a call-macro argument ([03](03-composable-macro.md)), so a modifier rebuilt in a pass is `same` as the previous one, and a composable receiving it still skips. An `Rc` with identity is all it takes.
- **Allocation.** Built-in elements are enum variants in an inline `SmallVec`, so typical chains of up to six elements allocate nothing. Longer chains spill once.
- **Spelling.** `Modifier` is a type and also a `const` of that type, so code writes `Modifier.padding(16.dp())` as in Kotlin, and `modifier: Modifier = Modifier` as a default.

## Layout

```rust
#[composable]
pub fn Layout(
    #[default(Modifier)] modifier: Modifier,
    measure_policy: Rc<dyn MeasurePolicy>,
    content: impl Fn() + 'static,
);

pub trait MeasurePolicy: 'static {
    fn measure(&self, scope: &mut MeasureScope, measurables: &[Measurable], constraints: Constraints) -> MeasureResult;
    // intrinsic sizes later, with default implementations
}

impl MeasureScope<'_> {
    fn measure(&mut self, measurable: Measurable, constraints: Constraints) -> Placeable;
    fn place(&mut self, placeable: &Placeable, x: i32, y: i32);
    fn layout(&self, width: i32, height: i32) -> MeasureResult;
    fn parent_data(&self, measurable: Measurable) -> ParentData;   // weight, alignment
    fn density(&self) -> Density;
    fn text_measurer(&mut self) -> &mut dyn TextMeasurer;
}
```

- **A closure is a policy**: `MeasurePolicy` is implemented for `Fn(&mut MeasureScope, &[Measurable], Constraints) -> MeasureResult`, and `measure_policy(|scope, measurables, constraints| …)` makes one for `Layout` with the argument types inferred, as Kotlin's `MeasurePolicy { measurables, constraints -> … }`: `Layout!(modifier = …, measure_policy = measure_policy(|scope, measurables, constraints| { … }), { … })`. A new closure is a new policy (measured again), as a Kotlin lambda; `remember` one that doesn't change (D176).
- **One measure-and-place pass with constraints**, as in Compose, except that a policy places its children in the same call that measures them, rather than in a placement block run afterwards. A layout modifier (`LayoutModifierNode::measure(scope, content, constraints)`) measures and places the content it wraps the same way.
- **Incremental.** Updating a node's policy or modifier, or inserting, moving or removing children, marks it for measuring and its ancestors as having a dirty descendant. The next layout measures from the root, but a node with unchanged constraints and nothing dirty returns its size at once; one with only dirty descendants measures them again in place, and runs its own policy only if one of their sizes changed. So a change climbs to the first ancestor whose size holds. A frame where nothing changed measures and draws nothing.
- **Rules.** A policy may measure a child only once per measurement, as in Compose: measuring it again panics. A panic in a policy or a layout modifier node leaves the tree whole (each node's children and modifier nodes are put back as the panic unwinds) and the node marked for measuring again. Pixel rounding is Kotlin's `roundToInt` (halves up), and `Constraints::offset` adds, as Compose's.
- **Outside the constraints.** A measured size is coerced into the constraints for the parent; the node keeps its measured size and is centered in the coerced one, as Compose does (`required_size` past the parent's bounds).
- **The root** measures its children with the window's constraints loosened, and places them at the origin.
- **Layout modifiers** as Compose's: `aspect_ratio(ratio, match_height_constraints_first)` (Compose's search: the maximum width, the maximum height, the minimums, then the same past the constraints), `wrap_content_width(align, unbounded)`, `wrap_content_height` and `wrap_content_size` (the content at its own size, aligned in the size imposed), `width_in`/`height_in` (`size_in` on one axis), `default_min_size` (a minimum only where the constraints set none), and `Modifier.layout(|scope, measurable, constraints| …)`, a closure measuring and placing the content (a new closure is a new modifier, as Compose's lambda; state it reads measures it again).
- **Layout callbacks.** `on_size_changed(|size| …)` reports the size of what follows it in the chain when first measured and when it changes; `on_globally_positioned(|coordinates| …)` reports a `LayoutCoordinates` (a snapshot: `size`, `position_in_root`, `position_in_window`, and `bounds_in_root` clipped by the clipping modifiers around it, a scroll's viewport) after each layout that changed it (through the graphics layers' transforms on its path, as Compose's `localToRoot`; a layer-only change doesn't report), as `GlobalPositionAwareModifierNode`s the tree registers; an intrinsic probe doesn't call `on_size_changed`. Both run once the layout is over, outside the tree, before drawing: state they write is composed and laid out again in the same frame. A measurement reading state another wrote while laying out (a lazy list's viewport size, read by `fill_parent_max_*`) is measured again within the same layout (`UiHost::lay_out`, twice at most).
- **Drawing order.** Children are drawn, and hit, in the order their parent placed them, sorted by `z_index` first (several on one node add up), as Compose's.
- **Nested scrolling** (D188): `Modifier.nested_scroll(connection)` lets a `NestedScrollConnection` (as Compose's) take part in the scrolls of the scrollables inside it: foundation's scrollables offer each drag, wheel and fling delta to the connections around them before scrolling (the outermost first) and what's left after (the innermost first), and their flings' velocities before and after; Material's top app bars collapse and its bottom sheets drag this way.
- **State read in measurement and drawing is observed**, as Compose's `SnapshotStateObserver` does: a node's policy and its custom layout modifiers measure, and its custom draw nodes draw, under an observation keyed by the node, so a write to what they read measures or draws that node again at the next frame without recomposing (built-in nodes read no state and aren't observed). `vertical_scroll` keeps its offset in state this way.
- **`Box`, `Column`, `Row` and `Spacer` are ordinary composables** in `compose::foundation::layout`, each a `Layout` with its own `MeasurePolicy`. That's Compose's split: layout is library code on a public primitive, not built into the node kinds.
- **Scoped modifiers.** `weight` and `align` exist only inside `Row`/`Column`/`Box` content, as in Compose. Rust has no context receivers, so a content lambda receives its scope as a `Copy` zero-sized token, and those modifiers take it:
  ```rust
  Row!(modifier = Modifier.fill_max_width(), |row| {
      Text!("Title", modifier = Modifier.weight(row, 1.0));
      Text!("Done");
  });
  ```
  A `RowScope` value can only come from `Row`, so misuse is a compile error at zero runtime cost. Compose's `Modifier.weight(1f)` reads slightly cleaner; this is the closest checked equivalent. `Box` the composable lives in the value namespace and `std::boxed::Box` in the type namespace, so they don't clash.

**Lazy lists.** `LazyColumn` and `LazyRow` compose only the items in view and two beyond each side, as Compose's: `LazyColumn!(state = list_state, |scope: LazyListScope| { scope.items_keyed(todos.len(), move |index| ids[index], |index| TodoRow(…)); })`, with `item`, `items` and `items_keyed` (an item keeps its state when items before it come and go), and over a list (an `ImmutableList`, shared, or a `Vec`, an array or a slice, copied into one) `items_list`, `items_list_keyed`, `items_indexed` and `items_indexed_keyed` (Compose's `items(list)` and `itemsIndexed`, named apart: Rust has no overloads), whose content receives the `LazyItemScope` (the others get it from `scope.item_scope()`) for `Modifier.fill_parent_max_width(&scope)`, `fill_parent_max_height`, `fill_parent_max_size` and their `_fraction` forms (the viewport less the content padding, as Compose's); content padding, arrangement, and the cross-axis alignment (a column's `HorizontalAlignment`, a row's `VerticalAlignment`, as `Column`'s and `Row`'s). `reverse_layout` lays the items out from the end (the first item at the bottom, or the right of a row in left to right) and reverses drags, the wheel and bring-into-view; the arrangement stays physical, as Compose's (`Arrangement::TOP` places a short reversed list's last item at the top), but its default stays `TOP` where Compose's becomes `Bottom` (D171). `user_scroll_enabled = false` keeps drags and the wheel from scrolling (the state and bring-into-view still do). `sticky_header(|scope| …)` (and `sticky_header_keyed`) adds a header that sticks at the list's start over the items after it, pushed out by the next one, as Compose's `stickyHeader`: the measurement writes which header is over the first visible item, which the items' composition keeps composed (wherever it is), and places it last, so it's drawn over the items and hit first. Keys are hashed to 64 bits; debug builds check the composed items' keys and panic on a duplicate (as Compose throws) or on a hash collision of different keys (which would share their state), comparing the full keys (D170). Compose composes items while measuring; here composition can't run inside layout (the tree is borrowed), so the list composes a range of items, and its measurement, which fills the viewport from the `LazyListState` (the first visible item and its offset), writes the range it needs when the composed one falls short. `UiHost::frame` then recomposes and measures again within the frame, up to three times, so a scroll never shows an empty frame. To keep that work out of frames, a list that scrolled asks for the next items in the scroll direction to be **prefetched** between frames, as Compose's `LazyListPrefetchStrategy` (D156): its measurement schedules a `PrefetchRequest` with the host's `PrefetchScheduler` (`LOCAL_PREFETCH_SCHEDULER`) when there is something to do, and when the platform is idle, `UiHost::prefetch(deadline)` runs it: it widens the composed range by one item ahead (disposing those behind that the layout no longer wants, as a frame composing the item would), recomposes (outside the frame; state writes in composition still panic), and measures the item with the items' constraints (`PrefetchRequestScope::premeasure`, as Compose's), composing and measuring again what that measurement wrote (a nested list's items, a `BoxWithConstraints`' content); one item at a time, up to two beyond those the layout wants, each only while the time left exceeds what an item took on average (lowered each time it doesn't fit, so one slow item doesn't stop prefetching). Items composed beyond the wanted range aren't placed, as Compose's prefetched items: nothing draws them, `first_visible_item_index` and the rest don't move, and the frame that scrolls them into the wanted range finds them composed and measured; each is a repaint boundary, so that frame draws it for the first time and the items that stay keep what they drew (D155). Prefetch goes the way the list was last scrolled. A prefetched item that takes the focus (an autofocused field) is placed with the others and, as any node focused before its first placement, scrolled into view once laid out. Short of time, a request gives up until the next scroll. Items outside the range leave the composition (their state goes, as in Compose without `rememberSaveable`), but the focused one, pinned by key, which stays composed and placed (Compose's pinning). A viewport's worth of items is composed beyond each side (at least two), so focus can reach the next focusable item. The composed items beyond the viewport are placed too, out of view, so focus moves to them, and a focused node is brought into view by its scrolling ancestors (`ModifierNode::bring_into_view`, as `BringIntoViewResponder`; `vertical_scroll` does it too). The scroll position follows the first visible item by key when items come and go before it, keeps fractions of a pixel, and steps over items only once they are composed (their sizes known), but for jumps of hundreds of items, which it estimates from the average size (Compose composes every item in between). Keys are looked for within a window around their last index; items are found by binary search over the intervals. An empty first layout (data still loading) keeps the initial position; an emptied list starts again at its top. Content shorter than the viewport is placed by the arrangement. The wheel and drags scroll it: the innermost scrollable takes a drag past the slop (8 dp from the press; scrolling what moved beyond it), and a wheel delta a list can't use goes on to the scrollables around it; `scroll_to_item` jumps; at the end, the last item ends the viewport.

**Constraints and grids.** `BoxWithConstraints` (as Compose's) gives its content the constraints it's measured with (`BoxWithConstraintsScope`: `max_width()` and friends in `Dp`). Compose composes it while measuring; here it first composes for the constraints it'll likely get (`LOCAL_CONSTRAINTS_HINT`: the window's at the root, a lazy list's items', a grid's cells'), and the measurement writes those it got as state, composing it again within the frame if they differ. `LazyVerticalGrid(columns, …)` (`GridCells::Fixed(n)` or `Adaptive(min)`, as Compose's) is a `LazyColumn` of rows of cells inside a `BoxWithConstraints`: cells are as wide as Compose's (the width without spacing divided evenly, the remainder a pixel each to the first cells), and `LazyGridState` counts in items, and a new column count keeps the first item in view. A grid keeps item state by row (a row keyed by its first item), not by each item's key (D144).

**Gestures.** `Modifier.pointer_input(key, |scope| async move { … })` (as `pointerInput(key) { … }`) runs a coroutine over the pointer events reaching its node: `scope.await_pointer_event(pass)` gives each one as a `PointerInputChange` it can `consume()`. The coroutine is an executor task polled at once as each event reaches the node (`executor::poll_now`, as Compose resumes it undispatched), so what it consumes the handlers after it see consumed; its timeouts are executor timers. It starts at the first event and starts over when its key changes, its gesture is cancelled or its node leaves; a block that returns stays done. Each change carries its pointer's id and time (`uptime_millis`), and `Enter`/`Exit` go through the three passes as other events. Compose's detectors are there, with their rules: `await_first_down`, `wait_for_up_or_cancellation` (up once no pointer is down; cancelled when a move is consumed, in the main pass or by a parent by the final pass, or leaves the node), `await_touch_slop_or_cancellation`, `with_timeout`, `detect_tap_gestures(TapGestures)` (tap, double tap within 300 ms but not sooner than 40 ms, long press after 400 ms, press; a cancelled or held second press still reports the first tap) and `detect_drag_gestures(DragGestures)` (past the 8 dp touch slop, following the pointer that crossed it, its first amount what's past the slop; a parent that takes the moves first keeps the gesture); their callbacks run once the event's dispatch is over. `PointerInputDriver` runs a block for custom pointer nodes. Foundation's `Modifier.draggable(state, orientation, …)` (its `on_drag_stopped` given the release's velocity, from the last 100 ms of moves as Compose's `VelocityTracker`) with `remember_draggable_state(on_delta)` reports drags along an axis as deltas, as Compose's: a node of its own that calls its newest callbacks, and calls `on_drag_stopped` when the drag is cancelled too.

**More clicks.** `combined_clickable(enabled, role, on_long_click, on_double_click, on_click)` (and `combined_clickable_indicated`), as Compose's `combinedClickable`: its presses go through `detect_tap_gestures` (with `on_double_click`, a click waits out the 300 ms double-click timeout; with `on_long_click`, holding 400 ms long-clicks), its indication shows while a press is held, and its keys, focus, hover and semantics are `clickable`'s, plus a long-click action (`SemanticsAction::OnLongClick`, `long_clickable`) with `on_long_click`. `selectable(selected, enabled, role, on_click)` is a clickable whose semantics say `selected`, and `selectable_group()` marks the group, as Compose's. `hoverable(interaction_source, enabled)` reports a mouse over the node to the source.

**Hover.** A mouse's hit path is tracked: when it changes, what the mouse left hears `PointerEventType::Exit` and what it came over `Enter`, as Compose's (not while a button is held: a drag stays with what it pressed); leaving the window (`UiHost::send_pointer_left`, from winit's `CursorLeft`) is an exit, and content moving under a resting mouse moves the hover (a hit test after each layout, as Compose Desktop's synthetic move). Clickables show Material's hovered state layer (8 %; 10 % pressed or focused). `Modifier.pointer_hover_icon(icon)` (as `pointerHoverIcon`) sets the mouse pointer's look over a node (`PointerIcon::Text`, `Hand`, `Crosshair`; the innermost on the hovered path wins); text fields show an I-beam, and the desktop window sets its cursor from `UiHost::pointer_icon`.

**Tooltips.** `TooltipArea(tooltip, …, content)` (as Compose Desktop's) shows `tooltip` in a popup at the mouse pointer, 16 dp below it (`TooltipPlacement`), or above it where there's no room below, once it has rested over the content for 500 ms (moving starts the wait again), and hides it when the pointer leaves the area (resting on the tooltip inside the area keeps it) or presses; Material's `PlainTooltip` is its look (the small body text on the inverse surface).

**Scrollbars.** `VerticalScrollbar` and `HorizontalScrollbar` (as Compose Desktop's) show a thumb for a `ScrollbarAdapter` (`remember_scrollbar_adapter(scroll_state)`, exact; `remember_lazy_list_scrollbar_adapter(list_state)`, from the average item size): its length the viewport's share of the content (at least 16 dp), dragged to scroll, a press on the track paging toward it, hidden while everything fits; `ScrollbarStyle` and `LOCAL_SCROLLBAR_STYLE` as Compose's defaults (8 dp, black at 12 %, 50 % while dragged). The thumb darkens while hovered or dragged.

**Layout direction.** Each layout node takes `LOCAL_LAYOUT_DIRECTION` (as `LocalLayoutDirection`) where it's composed; the host provides the window's (`UiHost::set_layout_direction`, `WindowOptions::layout_direction` on desktop), and `CompositionLocalProvider` changes it for a subtree. `MeasureScope::layout_direction`, `DrawScope::layout_direction` and `EventContext::layout_direction` read it. In right-to-left, as Compose: `place_relative` mirrors a child in the width its layout reports (once that's known); the root, `padding`, `offset`, the size modifiers, scrolling containers, lazy lists and Material's layouts place relatively; a `Row`'s arrangement and `Box`'s and `Column`'s alignments run from the right (a `Column`'s arrangement still runs from the top); a horizontal scroll or lazy row starts at the right and a drag, a wheel or a focused child's bring-into-view goes the other way; a text field lays its text out again when the direction changes; popups align with their anchor's start and offset toward its end, and menus try the anchor's right first; a slider and a switch are drawn mirrored (and the slider's pointer and arrow keys follow); text with no strong character runs in the layout's direction.

## Text

- **`TextMeasurer`** is the interface layout uses: it lays out a paragraph and returns a handle with its metrics. Each platform implements it with the text stack Compose uses there ([07](07-platforms.md)):
  - **desktop:** Skia's paragraph module (HarfBuzz shaping, ICU line breaking and bidi), as Compose Desktop;
  - **Android:** Android's own `StaticLayout`, as Android Compose.

  Kerning, ligatures, complex scripts, fallback fonts and emoji come from the platform stack.
- **Tests** use a fixed-advance measurer by default, so measurements are identical on every machine and don't depend on fonts; the Skia measurer (the system's fonts, no bundled ones: D94) can be given to a test host.
- `BasicText`/`Text` keep the paragraph handle on the node, keyed on text, style and width constraint, so a recomposition with the same text measures nothing.
- **Styles.** `TextStyle` has Compose's color, size, weight, style (italic), family (sans-serif, serif, monospace, cursive, or a system family by name, falling back to the default), letter spacing, decoration (underline, line-through), alignment (start, end, left, right, center, justify) and line height; what isn't set comes from the style it's merged over (`merge`), and Material's `Text` takes each as a parameter over `LOCAL_TEXT_STYLE`, as Compose's. `overflow` (as `TextOverflow`) clips by default, ends the last line with "…" (`Ellipsis`; one line without soft wrap, as Compose's), or draws past the bounds (`Visible`). **Styled spans** come from `AnnotatedString` (as Compose's): text with `SpanStyle`s (color, size, weight, style, family, letter spacing, decoration, background) over byte ranges, built with `AnnotatedString::build(|builder| { builder.append(…); builder.with_style(…, |builder| …); })`; `BasicAnnotatedText` and Material's `AnnotatedText` show one, each run laid out in its style (SkParagraph's styled runs). Link annotations aren't there yet.
- **Line bounds and layout results.** `min_lines` makes a text at least that many lines high (as `heightInLines`), and `on_text_layout` hears each new layout as a `TextLayoutResult` (as Compose's, a snapshot of its metrics without its queries: `size`, `line_count`, the baselines, `did_overflow_width`, `did_overflow_height` with the lines cut by `max_lines`, `has_visual_overflow()`), called after the layout as `on_size_changed` is (`MeasureScope::run_after_layout`), so what it writes is laid out within the frame; an intrinsic probe isn't reported. Whether lines were cut comes from `TextMeasurer::did_exceed_max_lines` (Skia's `didExceedMaxLines`; a measurer that can't tell says no, Android's for now) (D233).

## Drawing

A draw pass records a **display list**: a subset of the `Canvas` API (clips to rectangles, rounded rectangles and paths, transforms, rectangles, rounded rectangles, arcs, lines, paths, images, shadows, paragraphs drawn by handle, paints with gradient shaders; no blend modes yet). Draw modifier nodes record into it in chain order: `DrawModifierNode::draw` before the content (the rest of the chain and the children), `draw_after` after it, in reverse order, which is Compose's `drawContent()` split in two (`background` draws before, `border` after, `clip` saves and clips before and restores after). A node draws at the size of the layer its draw node is in, so `padding(8).background(…)` fills inside the padding. A platform `Renderer` replays the list: Skia on desktop, Android's `Canvas` on Android ([07](07-platforms.md)). Tests dump it as text or render it to PNG through Skia's CPU raster backend. The list is assembled whenever anything changed, into a buffer kept from frame to frame (so a warm frame allocates nothing): what's outside every repaint boundary is drawn again, and each boundary's operations come from what it kept unless something it drew from changed (below, "Repaint boundaries").

**Paths and vector images.** `Path` holds lines, curves and closes, built in code or parsed from SVG path data (`Path::from_svg`, arcs converted to curves), and draws with `DrawScope::draw_path` (a `DrawPath` op holding it in an `Arc`, with a scale and offset: an `ImageVector`'s viewport fitted to its size, nothing copied per frame). Material's `Icon` draws an `ImageVector`; `icons::filled::add()` and friends are material-icons-core's filled icons.

**Interactions.** `MutableInteractionSource` (as Compose's, with `collectIsPressedAsState`, `collectIsFocusedAsState` and `collectIsHoveredAsState` as `is_pressed`, `is_focused` and `is_hovered`, state reads) is where `Modifier.clickable_interaction` reports its press, focus and hover, so something else can show them: a navigation item's show on its pill only. A clickable's own indication (`Indication`, as Material's ripple without its animation) is a state layer over its bounds, or an unbounded circle (`Indication::unbounded(color, radius)`, as `ripple(bounded = false, radius)`: checkboxes and radio buttons).

**Custom drawing.** `Modifier.draw_behind(|scope| …)` draws under the content and `Modifier.draw_with_content(|scope| { …; scope.draw_content(); … })` around it, drawing the rest of the node and its children where `draw_content` is called (or not at all), as Compose's; foundation's `Canvas(modifier, |scope| …)` is a node to draw in. Their lambdas are observed: state they read draws again, without recomposing or measuring. `Modifier.draw_with_cache(|cache| cache.on_draw_behind(…))` (or `on_draw_with_content`), as Compose's `drawWithCache`, builds what it draws with (paths, brushes) from the `CacheDrawScope`'s size, and keeps it until the size, density or direction changes or state the build read does: the build runs under an observer of its own (whose write bumps a state the drawing reads, so the node draws again), and what the drawing lambda reads only draws again.

**`DrawScope`.** Besides rectangles, rounded rectangles, lines, paths and images: `draw_circle(center, radius, paint)`, `draw_oval(oval, paint)` (a whole turn of an arc, so no new operation) and `draw_arc_with(…, use_center, paint)` (a pie slice); `center()`; and the scoped transforms and clips of Compose's `DrawScope` extensions, each restoring after its block: `rotate(degrees, pivot, |scope| …)` and `scale(scale_x, scale_y, pivot, |scope| …)` (a save and a `Transform`), `translate(left, top, |scope| …)` and `inset(left, top, right, bottom, |scope| …)` (moving the scope's origin, and shrinking its size: no operation), `clip_rect(rect, |scope| …)` and `clip_path(&path, |scope| …)` (a `ClipPath` operation). Geometry comes before the paint, as the scope's other calls (Compose's put the color or brush first). `draw_path` takes a `&Path` (copied into the list) or a `&Arc<Path>` (shared). `Paint::with_alpha` multiplies a paint's opacity, as the draw calls' `alpha`.

**Brushes.** `Brush` is Compose's: `Brush::Solid`, `linear_gradient`, `horizontal_gradient`, `vertical_gradient`, `radial_gradient`, `sweep_gradient` (and `_stops` forms with each color's position), with a `TileMode`; positions are in the drawing's coordinates, `Offset::INFINITE`, `Offset::UNSPECIFIED` and an infinite radius standing for its size, center and half its smaller side, as Compose's. `DrawScope::brush_paint(&brush, alpha, style)` resolves it for the scope into a `Shader` the display list keeps (`DisplayList::shaders`) and returns a `Paint` naming it (`Paint::shader`, an index; `Paint` stays `Copy`), usable with any draw call; `Modifier.background_brush(brush, shape, alpha)` is Compose's `background(brush, shape, alpha)`. A repaint boundary's kept recording has its own shaders, appended to the list's when spliced (its paints' indices shifted). Skia paints the gradients (interpolated premultiplied, as Android's HWUI and Skiko's: D210). A brush paint's `color` is the gradient's average, what a renderer without the shader would paint; Android's replayer builds the gradient (D210).

**Arcs and caps.** `DrawScope::draw_arc` (as `drawArc`) draws part of an oval; a stroke's `cap` (`StrokeCap::Butt`, the default as Compose's `Stroke`, `Round` or `Square`) shapes open ends. Material's progress indicators draw with them: `CircularProgressIndicator(progress)` and `LinearProgressIndicator(progress)` (40 dp and 240 × 4 dp, as Compose's), and `IndeterminateCircularProgressIndicator` and `IndeterminateLinearProgressIndicator` (Compose's no-progress overloads, named apart since Rust has no overloads), whose keyframed animations are computed from one infinite clock read while drawing, so each frame only draws again.

**Snackbars.** `SnackbarHostState::show_snackbar(message, action_label, with_dismiss_action, duration)` is a coroutine, as Compose's: snackbars asked for show one at a time, in order; it returns `ActionPerformed` or `Dismissed` (after 4 or 10 seconds, or never for `Indefinite`), and cancelling it takes its snackbar away. `SnackbarHost` shows the current one, faded and scaled in; `Scaffold`'s `snackbar_host` slot places it above the bottom bar and the FAB, centered. The color scheme has Material 3's inverse, container, scrim and bright/dim roles.

**Shadows.** `Modifier.shadow(elevation, shape, clip)` (as Compose's) records a `DrawShadow` op behind the content: the shape's outline, the elevation, and Compose Desktop's light (300 dp above the window's top, 600 dp up, 800 dp wide) and colors (black at 3.9 % ambient, 19 % spot); Skia draws it with `ShadowUtils`, as Skiko does. Material's `Surface` takes `tonal_elevation` (the surface color tinted with the primary color, summed through nested surfaces, as `surfaceColorAtElevation` and `LocalAbsoluteTonalElevation`) and `shadow_elevation`; the FAB has its 6 dp shadow and menus their 3 dp one.

**Images.** `ImageBitmap` holds premultiplied RGBA pixels in an `Arc`, made from raw pixels or decoded by the backend (`compose_skia::decode_image`, PNG, JPEG, WebP, …, as the desktop's `decodeToImageBitmap`). `DrawScope::draw_image` records a `DrawImage` op (a source and destination rect and an alpha); Skia makes its image once per bitmap and forgets it the frame after the bitmap is dropped; a source rect is sampled strictly (nothing from outside it bleeds in), and a header claiming more than 2^28 pixels isn't decoded. Foundation's `Image(bitmap, content_description, modifier, alignment, content_scale, alpha)` is its pixels' size within the constraints scaled by its `ContentScale` (as Compose's painter node), draws scaled by a `ContentScale` (`Fit`, `Crop`, `FillBounds`, `FillWidth`, `FillHeight`, `Inside`, `None`) and aligned, clipped to its node, and reads as `Role::Image` with its description.

**Graphics layers.** `Modifier.graphics_layer(|layer| …)` applies alpha, scale, rotation and translation to a node's drawing, as `graphicsLayer`: the display list saves, transforms around the layer's pivot and draws into an alpha layer (`Transform`, `SaveLayerAlpha`). Its block runs while drawing, so the state it reads (an animation's value) changes the drawing without recomposing or measuring. When the layer is its node's first drawing modifier (nothing drawn before it in the chain), its properties are its repaint boundary's, as a `RenderNode`'s: its block's reads are observed apart, and a write to them computes the properties again without drawing the layer's content again (no version changes). A layer after a drawing (`background(…).graphics_layer { … }`) applies its properties inside its node's content, which its block's reads draw again. `alpha`, `scale` and `rotate` are fixed layers. The block isn't memoized by the macro (its closure takes a `&mut` scope, which a `Callback` can't hold): remember the modifier for a callee to skip. Hit testing doesn't follow the transform yet.

**Repaint boundaries.** A graphics layer is a repaint boundary, as Compose's (a `RenderNode` on Android); so is `Modifier.repaint_boundary()`, a layer without properties, and every lazy item. What a boundary draws, its children included, is a group of the display list (`DisplayList::groups`), in its own coordinates: a renderer can keep the group's recording while its operations stay the same, so a scrolled item, or one beside an animation, isn't recorded again (Android's replayer does, D154, D157).

Each boundary keeps what it drew, as Compose's layers keep their recordings (D155): a draw records what's outside every boundary, the boundaries in it by reference, then splices in each boundary's kept operations, nested boundaries included, without running its draw code. A boundary is drawn again only when something it drew from changed: a state read while drawing a node in it (up to the boundaries inside it) is written; a node in it is measured, or moves inside it, or its modifier changes; a child is added or removed; a handler asks (`EventContext::invalidate_draw`: a press, a focus, a selection); the density changes; or `UiTree::invalidate_draw` asks for everything. Moving the boundary itself (a scroll) is its parent's operations and keeps it. State written while laying out (a lazy list's or a scroll's measured state, a hover the layout moved) is applied just before drawing, so it's drawn in the frame that wrote it; a measurement it invalidates waits for the next frame. Data passed from one node's measure to another node's drawing without state (an `Rc<Cell>`) is stale when the writer and the reader are in different boundaries: measuring the writer draws its own boundary again, not the reader's. Material's `TextField` (its label's width and start, for the outline's cut) and `TabRow` (its tabs' positions, for the indicator) keep the writer and the reader in one node. Its group's `version`, from a counter of the tree, changes when it's drawn again or a boundary inside it changed version, so a renderer keeps a recording by key and version without comparing operations. A graphics layer's properties are its group's `layer`, applied by the operations just outside the group's content (`layer_start..start`: `Save`, `Transform`, `ClipRect`, `SaveLayerAlpha`, each if needed; `end..layer_end`: their restores): Skia draws them as any operations; Android skips them and sets them on the group's render node, so a layer-only animation records nothing again (D157).

## Animation

`compose::animation` is Compose's `animation` and `animation.core`. An `Animatable` holds its value in state and animates it with tasks ([04](04-runtime.md)): `animate_to(target, spec).await` takes a step each frame (`with_frame_nanos`) along a spec, `tween` (duration, delay, easing), `spring` (Compose's damped-spring equations, keeping the velocity across interruptions), `snap`, `keyframes(duration, |frames| { frames.at(time, value).with(easing); })` (as Compose's `keyframes { value at time with easing }`; the spec stays `Copy`, its keyframes interned per thread and shared when equal, D150), `repeatable` or `infinite_repeatable` (of a tween or keyframes), per component of the value's vector (`f32`, `i32`, `Dp`, `Offset`, `IntOffset`, `Size`, and `Color` in Oklab, as Compose's converters). A new animation interrupts the running one, which ends with `AnimationEndReason::Interrupted` where Compose throws a cancellation. `animate_float_as_state(target)` and its siblings follow a target, `remember_infinite_transition()` animates forever, and `AnimatedVisibility(visible, enter = fade_in() + expand_vertically(), …)` animates content in and out, keeping it composed while it leaves; `Crossfade(target_state, …)` fades one state's content into the next's; `AnimatedContent(target_state, …)` has the new state's content enter as the old one's exits (`transition_spec(initial, target)` gives an `enter.together_with(exit)` `ContentTransform`, Compose's default fading and scaling in after 90 ms while the old fades out, the container's size animating, or as large as the largest content without a size transform; contents are measured with the container's constraints; each content keeps the enter and exit of the change that brought it in or took it out), keeping the last three states' contents while they animate; `update_transition(target_state, label)` animates several values together on one state's change (`transition.animate_dp(spec, |state| …)` and friends, each from its value for the state the transition is at), its `current_state` reaching the target once they all end (on an interruption, the state the change was heading for, which is where the next change's spec starts), `is_running` a state read, and a value interrupted mid-way going on along a default spring (unless its spec is a spring), as Compose's `interruptionSpec`; `Modifier.animate_content_size()` animates a node's size to its content's. Animated values are read where they are used: in a graphics layer's block (a redraw) or a layout (a re-measure), not in composition, so a frame recomposes nothing.

## Popups and dialogs

`Popup` and `Dialog` (`compose::ui`, as Compose's `ui.window`) show content over the rest of the window. Compose gives them windows or layers of their own; here they are **overlays**: nodes composed where they are called (so composition locals, state and remembered values follow) whose modifier (`Modifier.overlay(provider, …)`) makes the tree place them in the root after layout, with a position provider (`PopupPositionProvider`: `AlignmentOffsetPositionProvider` for `Popup(alignment, offset)`, a menu's below-or-above provider), from their anchor's bounds and the window's size. The anchor is the layout around the popup inside its modifiers (as `parentLayoutCoordinates`), and popups are measured with the window's size, again when it changes. They are drawn after everything else and hit before it (a point in an overlay is its, handled or not); in semantics they are roots of their own, never merged into what's around their anchor. A popup with `on_dismiss_request` gets an outside catcher under it, dismissing it on a press outside: a focusable popup takes that press (what's beneath gets nothing while it shows), a non-focusable one lets it through, as Android's non-focusable popup windows. A focusable popup is modal for input whatever its dismiss settings, takes the focus, and back (Escape on desktop) dismisses it (`dismiss_on_back_press`), as on Android a popup window that takes focus gets the back key; a non-focusable one doesn't take back. A dialog is modal: its content centered (24 dp from the window's edges) over a scrim that takes every event (a click on it dismisses), taking the focus. While a dialog or focusable popup shows, Tab cycles through its focusables only (the overlay itself isn't a stop), keys stay in it (they never reach the handlers around its host), and with nothing focused they go to it, as a window of its own; back goes to it before what's beneath (D220); opening it scrolls nothing around its host, and once it's gone, what had the focus before gets it back. Non-focusable popups take no focus. `LOCAL_DENSITY` (as `LocalDensity`) gives composition the window's density. Material's `AlertDialog`, `DropdownMenu` and `DropdownMenuItem` are built on them; a menu is as wide as its widest item (112 to 280 dp, asked with `MeasureScope::max_intrinsic_width`), scrolls when taller than the window, and is placed as Compose's `DropdownMenuPositionProvider` (at the anchor's start, else its end, else the window's; below, else above, keeping 48 dp from the window's top and bottom, and always within the window); its `scroll_state` is remembered where it's called, so a reopened menu keeps its scroll.

## Back, saved state and the platform's values

- **Back.** `BackHandler(enabled, on_back)` (`compose::ui`, as AndroidX's `BackHandler`) registers with the host's `OnBackPressedDispatcher` (`LOCAL_ON_BACK_PRESSED_DISPATCHER`) while it's in the composition; a back press goes to the innermost enabled one: those in dialogs and focusable popups first (the deepest first, as their own windows get back before the window beneath), then the one registered last (composed last), as AndroidX's dispatcher (D220). The platform calls `UiHost::on_back_pressed()` (Android's back gesture or button), and Escape that no focused node consumes goes back too (`send_key`), which is how desktop dialogs close on Escape. `has_enabled_back_handlers()` tells the platform whether to intercept back at all: Android lets the activity finish when no handler is enabled. A `Dialog` and a focusable `Popup` take back while they show (their own always-enabled handler), dismissing only if `dismiss_on_back_press`: back never goes past them.
- **Saved state.** `remember_saveable(|| mutable_state_of(0))` (`compose::runtime`, as Compose's `rememberSaveable`) remembers as `remember` does, and registers the value (a remembered `OwnedState`'s value) with the host's `SaveableStateRegistry` (`LOCAL_SAVEABLE_STATE_REGISTRY`) while it's in the composition. `UiHost::save_state()` collects every registered value as a `SavedState` (`to_bytes` encodes it: booleans, integers, floats, strings and lists, what an Android `Bundle` holds); a new host given it (`restore_state`, before its first frame) hands each value back to the `remember_saveable` at the same place, found by `current_composite_key_hash()` (the keys of the groups from the root, as Compose's `currentCompositeKeyHash`: a composable's key, a `key(…)`'s value, a branch's region), values at the same place told apart by their order (D223). Values convert with a `Saver` (`saver(save, restore)` with `remember_saveable_with(saver, init)`); the `Saveable` types (integers, floats, `bool`, `char`, `String`, `Option`, `Vec`, tuples) need none (`AutoSaver`, Compose's `autoSaver`). A value that can't be restored (saved by another version of the app) is computed again. `remember_lazy_list_state`, `remember_lazy_grid_state` and `remember_scroll_state` are saveable, as Compose's; text fields hold no state of their own to save (their value is the app's, which `remember_saveable` keeps, as in Compose).
- **The configuration.** `LOCAL_CONFIGURATION` (`Configuration`: the screen's width and height in dp, its orientation, the font scale, the density, and night mode: the parts of Android's `Configuration` apps read) is the host's (`UiHost::set_configuration`); foundation's `is_system_in_dark_theme()` reads its night mode, so `MaterialTheme!(color_scheme = if is_system_in_dark_theme() { dark_color_scheme() } else { light_color_scheme() }, …)` follows the system, as the gallery and feed examples do (D225).
- **Window insets.** The host's insets (`UiHost::set_window_insets`: status bars, navigation bars, caption bar, keyboard, display cutout, in pixels; zero on desktop) are what foundation's `WindowInsets` (`system_bars()`, `status_bars()`, `navigation_bars()`, `caption_bar()`, `ime()`, `display_cutout()`, `safe_drawing()`, with `union` and `only(WindowInsetsSides::…)`) resolve to. `Modifier.window_insets_padding(insets)` and its shorthands (`system_bars_padding`, `status_bars_padding`, `navigation_bars_padding`, `ime_padding`, `display_cutout_padding`, `safe_drawing_padding`, from `WindowInsetsModifiers`) read them while measuring (a change measures them again; nothing recomposes); `insets.as_padding_values()` reads them in composition (`LOCAL_PLATFORM_WINDOW_INSETS`). They don't consume what they pad: nested paddings of the same insets add up (D222).
- **Images.** `decode_image_bytes(bytes)` decodes an encoded image with the platform's `ImageDecoder` (Skia's codecs on desktop, `BitmapFactory` on Android; the host sets it with `set_image_decoder`), and `remember_image_resource(include_bytes!("icon.png"))` decodes a bundled one once where it's composed, as `ImageBitmap.imageResource` (named `remember_…` so the composable transform sees the slots it takes, D224).
- **Properties and events.** An app embedded in a platform UI reads the properties the platform passes (`LOCAL_HOST_PROPS`: `props.string("tab")`, `number`, `boolean`; read in composition, a change recomposes the reader) and sends it events (`LOCAL_HOST_EVENTS.current().send(name, payload)`); the host's side is `UiHost::props().set(…)` and `set_event_listener` (D226).

## Input, focus and semantics

- **Pointer input.** A pointer event hit-tests through the node tree as Compose does: each pointer-input node is hit inside its own layer's bounds, a node's bounds don't limit what's hit inside it (an `offset`'s content, children placed outside), a `clip` does (to its outline), and at each level the topmost child with a hit wins. It collects the pointer-input modifier nodes under it, outermost first. It is dispatched in Compose's three passes: `Initial` down the path, `Main` up from the target, `Final` down again, and a handler consuming it hides it from those after. A press captures the path: the pointer's moves and release go to the same nodes. `clickable` follows Compose's tap detection: it clicks on a release inside, and moving out, a release outside or another handler consuming the events cancels. `toggleable` builds on it.
- **Handlers run after dispatch.** Application callbacks a node triggers (`on_click`, `on_value_change`) are queued as actions and run once the tree is free, so they can do anything a callback may. `on_key_event` handlers run during dispatch, since their result decides where the event goes: they may write state but not reach the tree.
- **Focus.** One node has focus. A focus target is a modifier node (`focusable`, and `clickable`, which is focusable when enabled, as on desktop Compose). Tab and Shift-Tab move through the focus targets in tree order, wrapping around (Compose's one-dimensional focus search), stepping over those outside a clipping container's bounds (a lazy list's items beyond its viewport) unless the focus is already inside it, and Enter or Space clicks a focused clickable. `FocusRequester` (`remember(FocusRequester::new)`, attached with `Modifier.focus_requester`) moves focus from application code, as Compose's: `request_focus()` from a callback or an effect focuses its node's focus target, or the first below it, once the tree is free (after the event, or at the next frame); a requester on several nodes focuses the first attached. `LOCAL_FOCUS_MANAGER.current()` (as `LocalFocusManager`) is the tree's `FocusManager`: `clear_focus(force)` clears the focus (nothing captures it here, so `force` changes nothing), and `move_focus(direction)` moves it, `FocusDirection::Next` and `Previous` through Tab's order, `Up`, `Down`, `Left` and `Right` to the nearest focusable that way (Compose's two-dimensional search: a candidate in the focused node's beam beats one out of it, else the nearest by `13 × major² + minor²`; with nothing focused, from the window's top-left or bottom-right corner). It acts once the tree is free, as `FocusRequester`, and returns whether a tree was there to ask (Compose returns whether the focus moved). The local's value is the composing tree's (read from the composition's applier), so no host provides it (D230). `on_focus_changed` reports whether the focus target after it in the chain, or a node below, has focus (Compose's `FocusState.hasFocus`), once when it attaches and then on every change. A focus target that is removed or can no longer take focus (disabled) loses it, and is told. Key events go to every key input node of the focused node, those after its focus target included, as Compose's `lastLocalKeyInputNode`.
- **Keyboard and text.** Key events go to the focused node's key input nodes, from its focus target outward, then to its ancestors', until one consumes them; committed text follows the same path. `BasicTextField` is value-based, as Compose's `BasicTextField(value, onValueChange)` (D96): it consumes the keys that type text (down and up, so an ancestor's single-key shortcuts and a clickable row's Space don't take them), edits by grapheme clusters, and follows Compose Desktop's key mappings: arrows (visually in right-to-left text), Up and Down by visual line keeping the horizontal position, words with Option (macOS) or Ctrl, line ends with Cmd on macOS and Home/End, the text's ends with Cmd+Up/Down or Ctrl+Home/End, word and line deletion, select all, copy, cut and paste through the platform's clipboard, and undo and redo (Cmd/Ctrl+Z, Shift+Cmd/Ctrl+Z, Ctrl+Y; typing within 5 s is one step). A plain Tab types a tab in a multi-line field; Shift+Tab moves focus. On macOS, Ctrl moves and deletes as Cocoa's Emacs-style bindings (Ctrl+A, E, B, F, P, N, D, H, K). The pointer places the cursor and drags a selection; a double-click selects a word and a triple-click a line, and a drag after them extends by words or lines (there is no Shift+click yet: pointer events carry no modifiers). An input method's composition shows in place of the selection, underlined, until committed; keys are the input method's meanwhile (but Tab), and a click or a focus change commits it, asking the platform to reset its input method so it isn't committed twice. Losing focus collapses the selection to its end. A single-line field scrolls horizontally, a multi-line one vertically, to keep the cursor in view, and text that overflows is clipped, as Compose's. `SelectionContainer(content)` makes the texts in it selectable, as Compose's: a press and drag selects from where it went down to the pointer across the texts in order (placement order below the container), a double-click a word, a triple-click a text (a drag after them extending by words or texts); Cmd+A (Ctrl+A) selects all and Cmd+C (Ctrl+C) copies, joined by new lines; a click elsewhere in it or its losing focus clears the selection; `DisableSelection` leaves texts out. The texts are `Selectable` modifier nodes the tree finds below the container when a gesture asks, as it finds focus targets (D151); the selection's ends name their texts, so it stays on them as others come and go, and is dropped when a text it ends in changes or leaves. A press in a nested container is that container's. `keyboard_options` (`KeyboardOptions { capitalization, auto_correct_enabled, keyboard_type, ime_action }`, with `KeyboardCapitalization`, `KeyboardType` and `ImeAction` in `compose_ui::text_input`, as Compose's `ui.text.input`) and `keyboard_actions` (`KeyboardActions::new().on_done(…)`) are Compose's. The focused field gives its options to the host as `ImeOptions` (`KeyboardOptions::to_ime_options(single_line)`), for an on-screen keyboard. Enter in a single-line field, or the input method's action key (`UiHost::perform_ime_action`, any action the keyboard showed, a single line's `Default` being `Done` as on Android), performs the field's action for it; without one, as Compose's default actions, `Next` and `Previous` move the focus and `Done` hides the on-screen keyboard; `Default` on desktop does nothing. `LOCAL_SOFTWARE_KEYBOARD_CONTROLLER.current()` (as `LocalSoftwareKeyboardController`, `None` only outside a `UiTree`'s composition) shows or hides the on-screen keyboard (`show()`, `hide()`; `EventContext::show_software_keyboard` and `hide_software_keyboard` from a handler). A multi-line field is between `min_lines` and `max_lines` lines high (as `heightInLines`: the heights of one and two lines of "H" in its style give the first line's and each next one's), its text scrolling within; a single line is one line high. `visual_transformation` (`impl Into<VisualTransformation>`, so a `PasswordVisualTransformation` needs no `.into()`, D232) changes how the text shows without changing it, as Compose's `VisualTransformation` with an `OffsetMapping` (byte offsets here): `PasswordVisualTransformation` masks each character with •, its semantics say `password` with the masked text, and it can't be copied or cut. Its `decoration_box` lays out what surrounds the text (Material's container, label and placeholder) and calls `inner_text_field` where the text goes; the field's modifier, semantics node and taps are the decoration's, as `CoreTextField`'s (D102).
- **Semantics.** Semantics modifier nodes build a semantics tree, merged or unmerged as in Compose: a node merging its descendants (`clickable` does) takes their text and state and hides them, unless they merge themselves. Tests find nodes through it (`on_node_with_text`, as Compose testing does), and it feeds AccessKit on desktop, for screen readers. A node's own modifiers apply from the innermost to the outermost, so an outer one's values win, lists (text, content descriptions) included (as `collapsedSemantics` and `set`); a role never merges up into a parent. A dialog's content sits in a node of its own, as large as it, marked `is_dialog`. `Modifier.clear_and_set_semantics` (as `clearAndSetSemantics`) hides what's inside a node (an icon next to its label). Semantics actions (`SemanticsAction::OnClick`, `RequestFocus`, `SetProgress`, as `SemanticsActions`) are what screen readers and `perform_semantics_action` ask of a node instead of input: `clickable` and `toggleable` click, a node that's focusable (its own focus target, or a part's: a text field's inner field) takes the focus, and a slider (its own merged node, with its `ProgressBarRangeInfo`) moves to a value snapped to its steps. A dialog's node is marked `is_dialog`.

## The host

`UiHost` is a composition of a `UiTree` in a root of a given size and density, with its text measurer: the core every platform host wraps, and what tests drive headless. `frame()` recomposes invalid scopes, then measures and draws what changed; `send_pointer`, `send_key` and `send_text` dispatch events and run their actions; `needs_frame()` says whether a frame would do anything, and a waker tells the platform when state changes. It owns what the platform gives content: the back dispatcher, the saveable state registry, the configuration, the window insets, the properties and the event listener (above). Between frames, `has_prefetch_work()` says whether lazy lists wait for idle time, and `prefetch(deadline)` gives them the time until `deadline` (the next frame's start); it does nothing while a frame has work (`has_pending_work`: state changed, a scroll), asks for no frame itself (what it composes isn't placed, what it disposes wasn't), unless measuring wrote state for others, and returns whether work is left. `compose-test` builds Compose's test rule on it ([09](09-testing.md)).

What a platform with an on-screen keyboard reads from it (D234): `text_input_area()` is `Some` while a focused node takes text (its cursor, where a candidate window goes); `text_input_options()` gives that field's `ImeOptions` (keyboard type, action key, capitalization, auto-correction, single line), read when the field takes the focus to configure the keyboard (Android's `EditorInfo` in `onCreateInputConnection`: input type and IME options); `perform_ime_action(action)` is the keyboard's action key (Android's `performEditorAction`); `take_software_keyboard_request()` returns what the content last asked (`Some(true)` to show the keyboard for the focused field, `Some(false)` to hide it), taken after each frame and event, the asking having woken the host; `take_input_method_reset()` says a field committed its composition itself. Desktop reads the area and the reset; Android reads the area and the reset now, the options, the action key and the keyboard requests once its bridge does.

Parameter names, order and defaults follow Compose, in snake_case. Deviations Rust forces, documented per composable:
- text parameters take `impl Into<SharedString>` (a `#[format]` one, as `Text`'s, converts whatever it is given): a `&'static str` (kept as is), a `String` or `&String` (copied into an `Rc<str>`), an `Rc<str>`, `&Rc<str>` or `&SharedString` (shared). A borrowed `&str` converts through `to_string()`: `From<&'a str>` would conflict with the literals' conversion, which allocates nothing;
- scopes are explicit tokens;
- there are no overloads, so variants get distinct names or merged defaults.
